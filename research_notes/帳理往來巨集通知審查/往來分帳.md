## 1. Repository.saveWithSplits 是否符合規格（新增、編輯、own==0、加減人、改總額/幣別/帳戶/日期、刪除還原）

### Takeaway
新增時符合規格；編輯時只要日期毫秒不同就失效（P0-1），own==0 只在「新增」才不留 $0 列；帳戶與幣別變更會跟著代墊走（前提是日期沒變），日期變更不會；刪除/復原依賴同一個 splitsOf，因此同樣受毫秒與誤認影響。

### Cited Findings
- 規格符合部分：`own = 總額 − Σ別人`，主支出存 own，別人那份各存一筆 `TRANSFER accountId=付款帳戶 → toAccountId=對方往來帳戶`，key `SPLIT:主id:人id` — [R:758-779](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 新增且 own==0：不建支出，只建 externalKey=null、店名「代墊：店家」的轉帳（多人時互不關聯，回傳第一筆 id），分類、位置不保留 — [R:764-769](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 編輯且 own==0：條件 `t.id == 0L` 不成立 → `saveTxn(t.copy(amount = 0))` 留下 −$0 支出。重現：開一筆 300 的分帳支出（他欠 150），把他的部分改成 300 → 清單出現「−$0」— [R:764](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:770](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。修法：編輯時 own==0 → 刪主交易，代墊改掛到穩定 key（例如沿用 `SPLIT:舊主id:人id`），或允許保留隱藏的 0 元母單但清單不顯示。
- **日期**：`splitsOf(t)` 以新 t 的 `date` 做 `between(t.date, t.date)`（同一毫秒），不是同一天 — [R:745](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。編輯器載入把時間 `withSecond(0).withNano(0)` — [E:235](app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)；build 用截過的時間 — [E:489](app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)。
  - 重現 A（改日期）：房租 25,500（A 9,500、B 7,500）→ 編輯改成前一天 → 儲存：主支出日期改了、金額 8,500；`existing` 為空 → 對 A、B 各 insert 新轉帳，key `SPLIT:主id:A` 已存在 → 唯一索引衝突 → Room `@Upsert` 改 UPDATE WHERE id=0 → 0 列，不報錯；舊代墊仍在原日期 — [R:772-779](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [Daos.kt:101-102](app/src/main/java/com/enwei/moneymanager/data/Daos.kt), [Entities.kt:79](app/src/main/java/com/enwei/moneymanager/data/Entities.kt)。
  - 重現 B（什麼都沒改）：巨集「房租」執行時 `date = System.currentTimeMillis()`（帶秒與毫秒）— [R:827](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)；之後打開主支出直接按儲存 → 日期被截到分鐘 → 同重現 A。通知記帳的交易再多選分帳（T:1420 沿用原日期）也一樣。
  - 使用者可見效果：再打開時看不到分帳（金額欄只剩 8,500、往來空白）；若此時改了某人的金額，主支出改了但代墊沒改，帳戶總流出 ≠ 實付；刪除主支出不再連帶刪代墊，往來對象留下孤兒欠款。清單上因 advOf 用 key 比對（T:689），代墊仍併在主支出下，問題不易被察覺。
  - 修法：`splitsOf` 改為 `SELECT … WHERE externalKey = 'SPLIT:id' OR externalKey LIKE 'SPLIT:id:%'`（不看日期）；saveWithSplits 以 DB 中的原紀錄（`db.txns().get(t.id)`）找代墊；保留載入時的秒數（只有使用者改時間才截）。
- **帳戶**：有 key 的代墊會被更新成新帳戶（`accountId = t.accountId`）→ 跟著走（日期不變時）；舊式（externalKey=null）代墊的比對條件含 `accountId == t.accountId`，改帳戶後找不到 → 新建一組、舊的留著 → 欠款加倍 — [R:747](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:775](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- **幣別**：代墊 `currency = t.currency`、`toAmount = null`；餘額計算會依匯率換算到往來帳戶幣別（R:217-218），所以欠款金額正確；但 debtMoves 直接用原幣金額累加（見第 3 節）— [R:775](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:181](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- **加人／減人**：以 `toAccountId` 對應舊代墊、更新金額，沒對到的刪除 — 正確（前提是 splitsOf 找得到）— [R:773](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:780](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- **P0-2 誤認**：舊資料條款 `externalKey == null && date == t.date && accountId == t.accountId && merchant startsWith "代墊"` — [R:747](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。
  - 重現：市場買菜，第一樣「全幫室友付」150（own=0 → 建 externalKey=null 的「代墊：市場」轉帳），按「繼續」（分帳路徑不重設時間，E:570-575），第二樣自己的 80、把室友移除後存成一般支出（同一毫秒、同一張卡）。之後打開第二樣改分類 → 一般存檔呼叫 `saveWithSplits(t, emptyList())`（E:589）→ splitsOf 把第一樣的代墊當成這筆的 → `existing.forEach delete` 刪掉 → 室友欠的 150 消失。刪除第二樣也會連帶刪（R:379）。打開第二樣時編輯器還會顯示「室友欠你 150」、金額 230（E:240-245）。
  - 手動記帳的時間本來就只到分鐘（E:604），同一分鐘、同一帳戶兩筆並不少見；巨集所有步驟同一個 `now`（R:827）。
  - 修法：一次性遷移，替所有舊式代墊補上 `SPLIT:<母id>:<人id>`（找不到母單的補 `ADV:<自己id>`），之後拿掉這條日期比對；「整筆幫別人付」也給 key（例如 `ADV:<uuid>:<人id>`）。
- 刪除／復原：`deleteTxn` 把 splitsOf 結果刪掉並暫存在記憶體 `cascadedSplits`，復原時 upsert 回來；App 被殺掉後無法復原（只影響 Undo 期間）— [R:372-393](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)

### Inferences
- 「改日期，代墊跟著走嗎？」→ 不會；而且即使不改日期，凡是帶秒數的紀錄，第一次在編輯器儲存就會斷鏈。這是本次最重要的正確性問題。
- `saveWithSplits` 沒有包在 `db.withTransaction`，中途失敗會留下半套（主支出已改、代墊沒改）。

## 2. 一次性遷移 revertPayerExpense／dropZeroAdvanceExpenses 是否安全

### Takeaway
兩者都有旗標、而且 revert 的篩選條件（accountId==null）在跑過一次後自然不再命中，不會重複套用；但 revert 沒檢查「這台裝置是否真的跑過 2.2.77 的錯誤遷移」，dropZero 只處理有 key 的 $0、刪主單時不處理手續費／通知紀錄，而且它產生的 externalKey=null 代墊正是 P0-2 的誤認來源。

### Cited Findings
- 呼叫點：App 啟動時依序 `revertPayerExpense()`、`dropZeroAdvanceExpenses()`，各自 runCatching — [MoneyApp.kt:62-63](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)
- 歷史：2.2.77 的 `migratePayerExpense` 把代墊改成 `accountId = null`、把別人那份加回主支出，並替舊式代墊補 key（以「同毫秒同帳戶的第一筆支出」當母單）— `git show 6adddc8`（Repository.kt migratePayerExpense）
- revert：找 `TRANSFER && accountId == null && toAccountId ∈ 往來 && key 以 SPLIT: 開頭`，把 accountId 設回母單帳戶、母單金額減回 — [R:803-820](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 冪等性：跑完後這些轉帳 accountId 已非 null，即使旗標沒寫入（R:819 前當掉）再跑也不會重複扣 — 安全。
  - 風險：若使用者**從未裝過 2.2.77–78**，但有「帳戶為空的支出」（例如匯入資料，E:268 允許）在更早版本做過分帳 → 代墊 accountId 本來就是 null、母單已是 own → revert 會再扣一次，自己的支出被少算。母單帳戶為 null 時 revert 後 accountId 仍是 null，旗標沒寫入時還會再扣。修法：只在 `payerExpenseMigrated == true`（表示 2.2.77 遷移真的跑過）時執行；或只處理母單 accountId 非 null 的。
  - 若 2.2.77 遷移當時把舊式代墊配錯母單（同毫秒同帳戶取第一筆），revert 從同一個錯的母單扣回，金額對稱還原，但代墊 key 指向錯的母單 → 清單併錯列、刪錯母單會連帶刪掉（低機率）。
- dropZero：找 `EXPENSE && amount == 0` 且有 `SPLIT:id` key 的代墊 → 代墊改成 externalKey=null、補帳戶與說明 → 直接 `db.txns().delete(main.id)` — [R:789-801](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 漏網：$0 母單的代墊是舊式（key=null）時不處理，「−$0」仍留在清單 — [R:793-794](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 漏網：之後再產生的 $0（第 1 節 P1-1 編輯路徑）不會被清，因為旗標只跑一次 — [R:790](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 副作用：直接刪 DB 列，不經 `deleteTxn` → `FEE:<母id>` 的手續費變孤兒；通知紀錄仍標「RECORDED」指向不存在的 id；母單的分類、rawText、位置紀錄遺失 — [R:797](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), 對照 [R:374-386](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 產生的代墊 externalKey=null、店名「代墊：…」、同毫秒同帳戶 → 落入 splitsOf 舊式條款（P0-2）與 advOf 的日期 fallback（第 6 節）。
  - 冪等：已轉換的代墊 key 為 null，再跑找不到；且 `$0` 母單已刪 → 安全。

### Inferences
- 建議把 dropZero 改成「保留母單但標記隱藏」或「代墊改用 `ADV:` 類 key」，並經由一般刪除流程處理手續費與通知紀錄。

### Gaps
- 無法得知實際使用者中「帳戶為空的分帳支出」的數量；revert 重複扣減的實際影響未量化。

## 3. debtMoves（LEND/ADVANCE/COLLECT/BORROW/REPAY）標籤是否正確

### Takeaway
大部分情況正確（含別人幫付的支出計入欠款、代墊 accountId 為 null 時顯示「代墊」）；但「同一天先處理支出與代墊、再處理給錢」的排序會把當天較早的借出誤標成還款，跨幣別不換算，兩個往來對象之間的轉帳完全被排除。

### Cited Findings
- 納入：`(toAccountId ∈ 往來) xor (accountId ∈ 往來)` 的已確認交易；別人幫付（EXPENSE accountId=往來）會讓 bal 減少（我欠他）— [R:166-171](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 排序：依當地日期 → 非「給錢」的先（支出、收入、代墊）→ 毫秒 → id — [R:165-167](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - 誤標重現：餘額 0；今天 09:00 借他 1,000（轉帳），20:00 他幫我付午餐 300（支出記在他帳上）。排序先算 20:00 的支出 → bal = −300 → 09:00 的轉帳 `before < 0` → 標「還給 X」，實際是借出（或至少 700 是借出）— [R:177-178](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。修法：同日只把「同時間或之前」的支出排在前；或只在 `|before| ≥ amount` 時標還款，超過部分顯示「還款＋借出」。
- 超額：`before > 0` 就是 COLLECT、`before < 0` 就是 REPAY，不管金額是否超過欠款（超出部分其實是借入/借出）— [R:177](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:185](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 代墊判定：店名以「代墊」開頭或 key 以 `SPLIT:` 開頭 → ADVANCE；accountId 為 null 時 `otherId = null`，列表第二行顯示「代墊」— [R:176](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [T:763](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)
- 跨幣別：`bal[p] = before + (t.toAmount ?: t.amount)`、支出 `- t.amount` 都是原幣直接加減，而餘額（R:217-218）有換匯 → 美金代墊會讓 debtMoves 的 bal 與實際餘額不一致，影響之後的標籤 — [R:172](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [R:181](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 兩個往來對象之間的轉帳（例如「A 欠我的改由 B 付」）被 xor 排除：沒有標籤（列表顯示「轉帳 A → B」），且不更新 bal，之後的標籤可能錯 — [R:166](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- 支出由對方付（EXPENSE accountId=往來）不會出現在 debtMoves（只處理 TRANSFER），列表顯示成一般支出，帳戶欄是對方名字，沒有「由 X 付」字樣 — [T:1326-1329](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt), [T:764](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)
- `recordDebtMove` 用「目前餘額」（含未來日期）決定種類並寫入店名；列表標題另以 debtMoves 依時間序重算，兩者可能不同（店名被 debtItem 正則濾掉，所以通常看不到矛盾）— [R:2340-2347](app/src/main/java/com/enwei/moneymanager/data/Repository.kt), [T:1333-1337](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)

### Inferences
- 標籤錯誤只影響顯示（餘額由 computeBalances 獨立計算，正確），嚴重度 P2。

### Gaps
- 未檢查統計頁是否另有依 DebtKind 的彙總。

## 6. 交易清單列（MmTxnRow／IconTxnRow、advOf 合併）與帳戶明細

### Takeaway
有 key 的代墊能正確併在母單下；獨立代墊（own==0、dropZero 產生）靠「同毫秒同帳戶的第一筆支出」fallback，可能併到不相干的列，遇到手續費時兩列互相隱藏而一起消失；帳戶明細不合併，逐筆顯示且餘額正確。

### Cited Findings
- advOf：key `SPLIT:<母id>` → 母單；無 key → `txns.firstOrNull { EXPENSE && 同毫秒 && 同帳戶 }` — [T:686-693](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)
- feeOf：key `FEE:<id>` → 母單；否則同毫秒同帳戶、店名不同的轉帳或支出 — [T:675-683](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)
- **P1-6 兩列一起消失**：「整筆幫朋友轉帳付 1,000、手續費 15」→ own==0 新路徑建代墊轉帳，`saveFee(t, mid)` 以第一筆代墊 id 建 `FEE:<代墊id>`、日期帳戶同主單 — [E:567-568](app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt), [R:357-365](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。清單：feeOf 把手續費掛到代墊；advOf 的代墊沒 key → fallback 找到同毫秒同帳戶的「支出」＝那筆手續費 → `hidden` 同時含兩者 → 兩列都不顯示 — [T:694-696](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)。dropZero 轉換過、原本有手續費的也一樣。修法：advOf fallback 排除手續費（`FEE:` key 或店名以「手續費」結尾），並避免循環（已被當成子項的列不能再當母單）。
- 無 key 代墊被併到同毫秒的無關支出（例如「繼續」記的下一樣、巨集的其他步驟）→ 清單上看起來像那筆的分帳。
- 顯示：母單金額只顯示自己那份（−8,500），每位對象一行「代墊 A $9,500」灰字 — 符合規格；但 3 人以上右欄會變 4–5 行，列高不一致 — [T:796](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt), [T:851](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)。建議 2 人以上合併成一行「代墊 3 人 $17,000」。
- 獨立代墊列：標題「幫 A 代墊 · 店家」（debtItem 去掉「代墊：」前綴）、第二行「從 X 付」— 正確 — [T:760-763](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt), [T:1333-1337](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)
- 帳戶明細（ledger 模式）逐筆顯示，不做 advOf/feeOf 合併，每列帶執行餘額 — [T:660-671](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt), [AccountsTab.kt:693-700](app/src/main/java/com/enwei/moneymanager/ui/screens/AccountsTab.kt)；兩種清單呈現方式不同（主清單合併、明細展開），使用者可能困惑但數字一致。
- 每日合計只算 INCOME/EXPENSE，代墊轉帳不計入支出 — 符合規格 — [T:150-158](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)

### Inferences
- 只要代墊一律有 key（見第 1 節修法），advOf 的日期 fallback 就能移除，P1-6 與誤併同時消失。

## 7. LoanScreens／DebtScreens／AccountsTab 的往來彙總與標籤

### Takeaway
彙總數字（別人欠我、我欠別人、淨額）以 computeBalances 換匯後加總，正確且不算收入支出；入口不一致（「他幫我付」不開付款人 UI、「收回款項」走一般轉帳而非 LoanMoveDialog），部分非 debtPerson 建立的往來帳戶看不到收付按鈕。

### Cited Findings
- 往來頁彙總：`owedToMe`、`iOwe` 依匯率換成基準幣別加總，淨額＝兩者相減 — [DebtScreens.kt:73-77](app/src/main/java/com/enwei/moneymanager/ui/screens/DebtScreens.kt)；帳戶頁卡片同算法、顯示「N 人未結清」— [AccountsTab.kt:260-282](app/src/main/java/com/enwei/moneymanager/ui/screens/AccountsTab.kt)
