## 1. 監聽服務：批次、取消、補讀、重新綁定、文字擷取（TxnNotificationListener.kt）

### Takeaway
2fb2a32 修好了「新通知取消處理中批次」的問題（批次搶到手後才 launch `process`，L:96-107），但待處理通知仍只存在記憶體，`onDestroy` 會直接清空、行程被殺也全丟，且沒有任何紀錄；補讀只救得回「還留在通知列」的通知；斷線偵測不足；文字擷取的優先順序在 InboxStyle 會拿到摘要而非明細。

### Cited Findings
- 批次邏輯：`pendingNotes` key 為 `"$pkg:$key:$postTime"`，等 0.9 秒、累積 ≥20 則或第一則已等 ≥3 秒就立即處理；每次 enqueue 先 `flushJob?.cancel()` 再新開一個 job — [L:86-107](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L86)
- 取消安全性：job 在 `delay` 之後於 `synchronized` 內取走整批並把 `flushJob=null`，再以 `app.appScope.launch { process }` 處理；`process` 跑在 appScope，不受舊 job 被取消影響 — [L:96-107](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L96)
- 小競態（無資料遺失）：舊 job 已過 `delay`、正在等 `pendingLock` 時，新 enqueue 取消它並建立新 job；舊 job 拿到鎖後仍會把新進的那則一起取走，並把 `flushJob` 設成 null（蓋掉新 job 的參照），新 job 之後拿到空批次直接 return — [L:95-105](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L95)
- `onDestroy` 會 `flushJob?.cancel()` 並 `pendingNotes.clear()`，這段等待中的通知不寫紀錄、不處理 — [L:55-60](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L55)
- `process` 整批例外時會寫 ERROR 紀錄（好），但 `catch (e: Exception)` 也會接到 `CancellationException`，而批次內可能已有幾則成功記帳，這時會再多寫 ERROR 列 — [L:111-122](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L111)
- 補讀：`onListenerConnected` 延遲 2 秒後讀 `activeNotifications`，只取 24 小時內、非本 App 的通知，`countSame(pkg,title,text,postTime-60s)==0` 才重新 enqueue；`featureNotif` 關閉就不補讀 — [L:29-46](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L29)
- 斷線：只在 `onListenerDisconnected` 呼叫 `requestRebind` — [L:48-53](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L48)；全專案搜尋 `requestRebind` 只有這一處（MoreScreens/Setup 只用 `isEnabled`，[M:309-310](app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt#L309)）。`isEnabled` 只讀 `enabled_notification_listeners` 設定值 — [L:153-157](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L153)
- `textOf`：群組摘要（FLAG_GROUP_SUMMARY）直接跳過；內文取 `BIG_TEXT ?: TEXT`（非空白），沒有才用 `TEXT_LINES`，再沒有用 `tickerText`；只讀 `EXTRA_TITLE`；標題內文都空回傳 null — [L:66-76](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L66)
- `EXTRA_MESSAGES`（MessagingStyle）、`EXTRA_SUB_TEXT`、`EXTRA_SUMMARY_TEXT`、`EXTRA_TITLE_BIG`、`EXTRA_INFO_TEXT` 都沒讀 — [L:69-73](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L69)
- 測試頁用的 `activeNotes()` 自己另外擷取，只讀 BIG_TEXT/TEXT，不讀 TEXT_LINES、tickerText — [L:140-151](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L140)
- `featureNotif` 在 `onNotificationPosted` 開頭即檢查，關閉時完全不讀 — [L:78-84](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt#L78)

### Inferences
- **#7 遺失路徑（P1）**：重現：銀行通知進來後 0.9 秒內，系統因記憶體／省電重建監聽服務（或使用者關閉再開啟通知存取）→ `onDestroy` 清空 → 若使用者已滑掉該通知，補讀讀不到 → 通知與紀錄都不存在。同理，批次正在 `ingestLock` 內等 AI（#9）時行程被殺，該批與後面排隊的批次全部消失。**建議**：enqueue 時先同步寫一列 `QUEUED` 紀錄（含 sbn.key、postTime），處理完再 `setResult`；`onListenerConnected`／App 啟動時把殘留的 `QUEUED` 重新送進處理。這也讓「消失」至少看得到。
- **#8 斷線（P1，部分推測）**：`onListenerDisconnected` 不會在行程被殺時呼叫；部分廠牌（推測：MIUI、EMUI、One UI 的省電）殺掉後不會自動重綁。設定頁顯示「已開啟」只代表權限在。**建議**：(1) 在 `MainActivity.onResume`、`BOOT_COMPLETED`、每日背景工作中呼叫 `NotificationListenerService.requestRebind(...)`；(2) 用 `instance != null`（或記錄最後一次 `onNotificationPosted` 時間）在通知記帳頁顯示「監聽中／已中斷，點此重新連線」。
- **#13 文字擷取（P2）**：InboxStyle 的通知通常 `EXTRA_TEXT` 是摘要（如「您有 2 筆交易」），明細在 `EXTRA_TEXT_LINES`；目前 `TEXT` 非空就不讀 lines，金額會讀不到（推測，依各銀行實作）。MessagingStyle（例如 LINE 官方帳號訊息，推測 LINE Pay 訊息即屬此類）多則訊息合併在同一則通知時，只會讀到最後一句。**建議**：把 TITLE、TITLE_BIG、TEXT、BIG_TEXT、SUB_TEXT、SUMMARY_TEXT、TEXT_LINES、MESSAGES 去重後全部串起來存成 `text`（或另存 `fullText` 欄位），讓解析器與紀錄頁看到完整內容；`activeNotes()` 改為共用 `textOf`。
- **群組摘要**：一般 App 先發子通知再發摘要，跳過摘要合理；若某 App 只發一則帶 `setGroupSummary(true)` 的通知（不正確但存在的寫法），會被整個略過且無紀錄（推測、低機率）。**建議**：摘要通知若 `activeNotifications` 內同 group 沒有子通知，仍處理。
- **同 key 原地更新**：key 含 postTime，原地更新的每一版都會進批次，靠 Repository 的 countSame／rawText 去重；若 App 用同一個通知 id「覆蓋」顯示下一筆交易，而監聽在中間斷線，只能補讀到最後一版（前一筆遺失，推測）。
- **補讀與 #1 交互**：補讀依賴 `countSame`，被 #1 靜默吃掉的那則在補讀時同樣被跳過（因為第一則的紀錄存在）。

### Gaps
- 無法在本環境實機確認各銀行（國泰、玉山、台新、LINE Pay、街口）實際用哪種 Notification Style；InboxStyle／MessagingStyle 的影響需用「進階 → 測試辨識」實際通知驗證。
- `requestRebind` 在 `onListenerDisconnected` 中呼叫的實際成功率取決於 ROM，無法從原始碼判定。

## 2. Repository.ingestNotificationBatch / ingestNotification：去重、合併、無紀錄的 return

### Takeaway
使用者回報的兩個現象都能在程式中找到直接成因：**相同內容 1 分鐘內的第二則被 `countSame` 靜默丟棄（無紀錄）**；超過 1 分鐘則被 rawText／externalKey／3 分鐘 nearby 判成 DUPLICATE；而紀錄頁的「不是重複？點選記帳」因為 `force` 不略過這些去重，實際上救不回來。另外新加的 exactTime/distinct 判斷只看單邊，會造成反方向的「重複記帳」。

  - 重現：同一 App 3 分鐘內兩筆同額、內文不同的消費 → 第二筆以 secondSame 記成待確認（「請確認不是重複」，R:1786）→ 3 分鐘後 aiAutoTidy 把兩筆送 AI；兩筆時間同分鐘、同帳戶、同金額，AI 很可能判「同一筆」→ 刪除其中一筆。
  - 影響：使用者看到「兩筆變一筆」；紀錄頁那則顯示「交易已刪除・點選重新記帳」，但點了會因 keep 的 rawText 已含 drop 的原文而被 rawText 去重（R:1446）判 DUPLICATE，訊息還寫「看不出是交易」→ 無法復原。
  - 建議：(1) 兩筆都有**各自不同的通知紀錄、且來自同一個 App**（`countForTxnFromPkg`）時，視為兩筆不同交易，不送 AI 自動合併；(2) secondSame 產生的待確認交易不自動合併，只列在「可能重複」讓使用者決定；(3) 合併時在通知紀錄寫 `MERGED_BY_AI`（`setResultForTxn(drop.id, ...)`），紀錄頁顯示「AI 判定重複已合併・點選還原」，還原時從 keep 的 rawText 移除 drop 的原文；(4) 提供 AI 判斷依據時加上「兩則通知原文都存在且各自獨立」的資訊。
- QuickActions 不會造成資料遺失；但通知 id 依 `notifId(t.id)`，MERGED 時會覆蓋同一則「已自動記帳」通知，使用者只看到一則（屬正常）。

### Gaps
- 無法實測 AI（Groq/Gemini）對「同分鐘同額兩筆」的判斷傾向；「很可能判同一筆」為推論。
- `findDuplicates` 的 `dupVerdicts`/`dupDismissed` 記憶機制是否在使用者手動「不是重複」後確實阻止 AI 再合併，未逐行追蹤（R:633 寫入 dupVerdicts、R:650 排除已判過的組）。
