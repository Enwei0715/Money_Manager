# 巨集與記帳頁（帳戶列、店家推薦、金額輸入）原始碼審查

> 範圍：`ui/screens/MacroScreens.kt`、`ui/screens/TxnEditor.kt`（macroMode、帳戶列、withBest、amountFresh）、`data/Repository.kt`（runMacro、通知「套用巨集」）、`data/Settings.kt`（TxnMacro／MacroStep）、`MoneyApp.kt`、`ToolSettingsScreen.kt`、`MoreScreens.kt`、`MainActivity.kt`。
> 依據：只讀原始碼（HEAD = c52cb41，工作區無未提交修改）。下文路徑都以 `app/src/main/java/com/enwei/moneymanager/` 為前綴（簡寫為 `…/`）。沒有實機重現；「推論」與「不確定」都有標出。

## 整體嚴重度排序（先看這裡）

### Takeaway
最嚴重的是**巨集根本沒有寫進 SharedPreferences**：重開 App 或背景被系統殺掉後，所有巨集（和「通知自動套用」）都會消失。其次是通知觸發巨集時沒有跨通知去重（同一筆付款可能把整套巨集記兩次），以及畫面旋轉、程序被殺時巨集草稿和步驟編輯會被靜默覆蓋。

### Cited Findings
- **P0 嚴重｜巨集不會被保存**：`AppSettings.macros` 和 `macroToolAdded` 只在資料類別裡宣告（[Settings.kt:495-497](…/data/Settings.kt)），但 `read()`（[Settings.kt:590-764](…/data/Settings.kt)）沒有讀 `macros`，`update()`（[Settings.kt:829-961](…/data/Settings.kt)）也沒有 `putString("macros", …)`。在 Settings.kt 用 `grep -i macro` 只找到第 42-74 行和第 495、497 行。`update()` 只把值寫進記憶體的 `state.value`。`exportRaw()` 匯出的是 `prefs.all`，所以備份也不含巨集。
- **P0/P1｜旗標同樣沒保存**：`payerExpenseMigrated`、`payerExpenseReverted`、`zeroAdvanceCleaned`（[Settings.kt:499-503](…/data/Settings.kt)）也不在 read／update 裡。所以 `revertPayerExpense()`（[Repository.kt:803-820](…/data/Repository.kt)）和 `dropZeroAdvanceExpenses()`（[Repository.kt:789-801](…/data/Repository.kt)）每次啟動都會再跑一次（[MoneyApp.kt:62-63](…/MoneyApp.kt)）。`revertPayerExpense` 會挑 `accountId == null`、`externalKey` 以 `SPLIT:` 開頭的代墊轉帳，從主支出再扣一次，然後把轉帳的帳戶設成 `parent.accountId`。如果主支出本來就沒有帳戶，轉帳的帳戶仍是 null，下次啟動又會被扣一次，主支出會逐次減到 0。（推論，屬於往來／資料面，建議交給負責往來的研究者確認。）
- **P1｜通知觸發巨集沒有去重**：通知處理的巨集分支（[Repository.kt:1513-1524](…/data/Repository.kt)）在 `when (p.kind)` 和「10 分鐘內同金額通知合併」（`nearby`，[Repository.kt:1476](…/data/Repository.kt)、[1676](…/data/Repository.kt)）**之前**就直接 `runMacro` 並 return。它只受 `key`（含卡號末四碼或 App 套件名）和 rawText 完全相同兩種去重保護（[Repository.kt:1439-1449](…/data/Repository.kt)）。
- **P1｜旋轉、程序被殺時草稿遺失**：見「MacroDraft 生命週期」一節。
- **P1｜macroMode 存檔會默默丟掉欄位**：說明、幣別、跨幣別的轉入金額都會丟失；「別人付」不檢查自己的部分是否大於總額；分帳超過總額也不擋。見 macroMode 一節。
- **P2**：新增步驟會沿用上一步的往來帳戶，結果被當成「別人付」；還款步驟的商家名稱不會更新；amountFresh 遇到兩位小數時第一個數字被吞掉；分帳全額時復原會留下孤兒轉帳；文字會換行。詳見各節。

### Inferences
- 巨集是最近一次提交（bc4c5b8「巨集、通知全文展開…」）才加入的。Settings 的 read／update 都是逐欄手寫，很容易漏欄位。建議在 `SettingsTest` 加一個「每個 AppSettings 欄位都能往返存取」的測試，例如用 reflection 列出所有欄位比對。

### Gaps
- 沒有實機驗證，結論都來自讀碼。不過「巨集不保存」是由 grep 確認的確定事實。

## 巨集的序列化與舊版欄位（Settings.kt）

### Takeaway
`TxnMacro`／`MacroStep` 是 `@Serializable`，`allSteps()` 也有相容舊版單步欄位，但目前整個列表根本沒有序列化。另外 MacroStep 少了幾個欄位：幣別、轉入金額、說明、還款種類、「誰付」的語意。

### Cited Findings
- `TxnMacro` 有 `steps` 和舊版單步欄位 `type/amount/accountId/toAccountId/categoryId/merchant/shares`。`allSteps()` 在 `steps` 為空且 `amount > 0` 時，把舊欄位轉成一步（[Settings.kt:41-59](…/data/Settings.kt)）。邏輯正確，但存檔時 `TxnMacro(id, name, steps=…)`（[MacroScreens.kt:178](…/ui/screens/MacroScreens.kt)）不會清掉舊欄位（預設值本來就是空的，所以沒影響）。
- `MacroStep(type, amount, accountId, toAccountId, categoryId, merchant, shares)` 沒有 `currency`、`toAmount`、`note`、`repayKind`（[Settings.kt:62-71](…/data/Settings.kt)）。「別人付」用 `accountId = 往來對象(LOAN)` 表示，「他還你」用 `TRANSFER` 且 `accountId = 對象` 表示，兩者都是隱含編碼（[TxnEditor.kt:514-524](…/ui/screens/TxnEditor.kt)）。
- Json 設定為 `ignoreUnknownKeys = true`（[Settings.kt:557](…/data/Settings.kt)），之後新增欄位可以向後相容。

### Inferences
- 修法：在 `read()` 加 `macros = dec("macros", "[]", ListSerializer(TxnMacro.serializer()), emptyList())` 和 `macroToolAdded = prefs.getBoolean("macroToolAdded", false)`；在 `update()` 加對應的 `putString`／`putBoolean`。三個往來轉換旗標也要一起補。
- MacroStep 建議補上 `currency: String? = null`、`toAmount: Long? = null`、`note: String = ""`，以及明確的 `kind`（NORMAL／PAID_BY／REPAY／BORROW），不要靠「accountId 是 LOAN」去推斷。

### Gaps
- 不確定其他研究者是否會另外寫「旗標未保存」這一條。它影響往來資料，我只附帶列出。

## MacroDraft 生命週期與巨集編輯頁（MacroScreens.kt）

### Takeaway
用全域 `object MacroDraft` 搭配 `returning` 旗標，只能處理「正常點進步驟再按返回」這一條路。只要畫面重建（旋轉、深色模式、字級或語言變更）、程序被殺，或從底部分頁離開，未儲存的草稿都會被靜默重載或丟失。刪除步驟沒有確認也不能復原，「儲存」按鈕灰掉時也不說原因。

### Cited Findings
- 草稿的結構：`forId`、`name`、`steps`、`fromNotif`、`keyword` 是 Compose state，`editIndex` 和 `returning` 是普通 var（[MacroScreens.kt:141-159](…/ui/screens/MacroScreens.kt)）。`open()` 設 `editIndex` 和 `returning = true`，再導到 `txn/0?macro=true`（[MacroScreens.kt:157](…/ui/screens/MacroScreens.kt)）。
- 載入條件：`remember(id) { if (!d.returning || d.forId != id) d.load(id, orig); d.returning = false }`（[MacroScreens.kt:168-172](…/ui/screens/MacroScreens.kt)）。只要畫面重新進入組合而 `returning == false`，就會用已儲存的 `orig` 覆蓋草稿。
  - **旋轉或設定變更**：AndroidManifest 的 `<activity>` 沒有 `configChanges`（grep 確認），Activity 會重建，`remember` 重新執行，`returning` 是 false，於是改到一半的名稱和步驟回到儲存前的樣子。新巨集（id=0）會整個清空。（推論，邏輯明確。）
  - **程序被殺**：在記帳頁編輯步驟時 App 被回收，返回後 `MacroDraft` 是空的，`editIndex = -1`。`editing()` 回傳一個空白新步驟（[MacroScreens.kt:156](…/ui/screens/MacroScreens.kt)），儲存時被 `add` 進空的 steps，回到編輯頁又因 `returning == false` 被 `load()` 覆蓋。使用者的修改全部丟失，畫面上沒有任何提示。
  - **底部分頁**：`EDITOR_PREFIXES` 只有 `txn/`、`account/`、`trade/`、`recurring/{`、`search`（[MainActivity.kt:278](…/ui/MainActivity.kt)），所以 `macro/{id}` 頁面會顯示底部分頁列。點分頁離開再回來時，畫面重新組合，草稿被重載。（推論；分頁的 saveState 行為沒有逐行追。）
- 不存檔就返回：頂列返回鍵會把 `forId` 設成 null（[MacroScreens.kt:186](…/ui/screens/MacroScreens.kt)），系統返回鍵不會。但下次進入時 `returning == false` 一定會 `load()`，所以**不會**把舊草稿帶進下一次編輯。這條路是安全的。不過放棄修改時沒有「要捨棄修改嗎？」的確認。
- 移除步驟：「✕」直接 `d.steps.removeAt(i)`（[MacroScreens.kt:216](…/ui/screens/MacroScreens.kt)），沒有確認也不能復原，點擊範圍約 12dp padding 加一個字，緊貼整列的點擊區，容易誤觸。
- 驗證：`ready = 名稱非空 && steps 非空 && 每步 amount > 0`（[MacroScreens.kt:175](…/ui/screens/MacroScreens.kt)）。按鈕只是 `enabled = ready`（[MacroScreens.kt:239](…/ui/screens/MacroScreens.kt)），沒有說缺什麼。「別人付」步驟可能被存成 0 元（見 macroMode 一節），這時使用者只會看到按不下去。另外沒有檢查步驟引用的帳戶或分類是否已刪除或封存（`stepLine` 對找不到的帳戶直接省略，[MacroScreens.kt:75](…/ui/screens/MacroScreens.kt)）。
- 新巨集的 id：路由是 `macro/0`，存檔時用 `orig?.id ?: System.currentTimeMillis()`（[MacroScreens.kt:178](…/ui/screens/MacroScreens.kt)），沒問題。
- 刪除＋復原：復原時用 `s.macros + orig`（[MacroScreens.kt:190](…/ui/screens/MacroScreens.kt)），巨集會跑到列表最後，順序改變。刪除用的是進頁面時抓的 `orig`，如果先改了內容（還沒存）再刪，復原回來的是舊版，這點合理。
- 新增步驟的預設值：`editing()` 在 `editIndex = -1` 時回傳 `MacroStep(accountId = steps.lastOrNull()?.accountId)`（[MacroScreens.kt:156](…/ui/screens/MacroScreens.kt)）。如果上一步是「別人付」（accountId = 往來對象）或「他還你」（TRANSFER，accountId = 對象），記帳頁帶入時 `tp == EXPENSE && st.accountId in people` 成立（[TxnEditor.kt:216](…/ui/screens/TxnEditor.kt)），**新步驟會預設成「由 X 付」**。重現：巨集第 1 步選小明付午餐，按「＋ 新增步驟」，第 2 步一打開帳戶列就是「由 小明 付」。修法：只沿用非 LOAN 的帳戶，例如往回找最後一個 `type == EXPENSE/INCOME` 且帳戶不是 LOAN 的步驟。
- 沒用到的程式碼：`macroAmt`、`parseMinor`（[MacroScreens.kt:65-66](…/ui/screens/MacroScreens.kt)）、`Choice`（[MacroScreens.kt:243-251](…/ui/screens/MacroScreens.kt)），以及沒用到的 import（`OutlinedButton`、`AccountType`、`MacroShare`）。

### Inferences
- 建議把草稿改成用 `SavedStateHandle` 或 `rememberSaveable` 存 JSON，或改用 `navBackStackEntry.savedStateHandle` 傳步驟結果（記帳頁 `previousBackStackEntry?.savedStateHandle["macroStep"] = json`）。`editIndex` 用導航參數 `txn/0?macro=true&step=i` 傳，不要放全域。至少要讓 `returning` 和 `editIndex` 能撐過程序被殺。
- `macro/` 加進 `EDITOR_PREFIXES`；加 BackHandler，草稿有改動時跳出確認。
- 「✕」改成滑動刪除，或刪除後顯示 Undo。

### Gaps
- 沒有實測 Navigation 的分頁 saveState／restoreState 對這頁的實際影響。

## 記帳頁 macroMode：帶入、隱藏的欄位、各 LaunchedEffect 的干擾、寫回的 MacroStep

### Takeaway
帶入大致正確，總額和分帳的往返也一致（MacroStep.amount = 總額，runMacro 再交給 saveWithSplits 扣掉）。但有幾種情況會默默丟資料：說明、幣別、轉入金額會丟失；「別人付」可能存成 0 元或負向的結果；分帳超過總額不擋。旋轉時帶入的 LaunchedEffect 會再跑一次，蓋掉正在改的內容。

### Cited Findings
- **帶入**（[TxnEditor.kt:209-226](…/ui/screens/TxnEditor.kt)）：
  - 別人付：`EXPENSE && accountId ∈ LOAN` 時設 `paidBy = true`，`splitRaw = [對象, expr ""]`。總額 `expr` 帶入的是 `st.amount`（只有「我的那份」），對方自己的部分是空的。往返後金額一致，但原本的「整筆」和「他那份」資訊消失，使用者再打開時看到總額等於自己那份（語意流失，P3）。
  - 他還你：`TRANSFER && accountId ∈ LOAN` 時設 `type = INCOME`、`repayPerson`，`accountId = toAccountId`。沒有還原 `repayKind`（0 他還你／1 向他借），標題一律是「收到還款」。
  - 第 223 行：`if (st.shares.isNotEmpty())` 會覆寫 `splitRaw`。目前「別人付」步驟存檔時不帶 shares，所以兩者不會同時出現；舊版資料就難說（不確定）。
  - `panel = if (amount > 0) NONE else panel`。初始 panel 依 `id == 0` 是 CATEGORY 或 AMOUNT（[TxnEditor.kt:198-200](…/ui/screens/TxnEditor.kt)），所以修改既有步驟時，鍵盤會先閃一下再收起。
  - **旋轉**：`LaunchedEffect(macroMode)` 在 Activity 重建後會重跑，用 `MacroDraft.editing()` 的原值蓋掉已由 rememberSaveable 還原的修改（推論，邏輯明確）。修法：用 `rememberSaveable { mutableStateOf(false) }` 記一個 `prefilled` 旗標，只帶入一次。
- **隱藏的部分**：「往來」類型分段本來就沒有（[TxnEditor.kt:689-693](…/ui/screens/TxnEditor.kt)）、股票分段、當天備註（[TxnEditor.kt:673](…/ui/screens/TxnEditor.kt)）、手續費（[TxnEditor.kt:739](…/ui/screens/TxnEditor.kt)）、預算（[TxnEditor.kt:767](…/ui/screens/TxnEditor.kt)）、日期列（[TxnEditor.kt:781](…/ui/screens/TxnEditor.kt)）、「繼續」（[TxnEditor.kt:986](…/ui/screens/TxnEditor.kt)）、定位推薦（[TxnEditor.kt:358](…/ui/screens/TxnEditor.kt)）都隱藏了。
  - **沒有隱藏但會被丟掉**：
    - 「說明」欄（[TxnEditor.kt:929](…/ui/screens/TxnEditor.kt)）照常顯示，MacroStep 卻沒有 note，打的字存檔後就不見。
    - 鍵盤的幣別切換（`currencies = base, sub`，[TxnEditor.kt:1027](…/ui/screens/TxnEditor.kt)），以及選外幣帳戶時自動換成該帳戶幣別（[TxnEditor.kt:248-250](…/ui/screens/TxnEditor.kt)），都沒有存進 MacroStep。runMacro 一律用 `settings.value.baseCurrency`（[Repository.kt:832](…/data/Repository.kt)）。重現：步驟選 USD 帳戶、輸入 100，執行後在 USD 帳戶記成 TWD 100。
    - 跨幣別轉帳的「轉入金額」（[TxnEditor.kt:823](…/ui/screens/TxnEditor.kt)）不存，runMacro 的 toAmount 是 null。
    - 首次教學 `PageTour("editor")` 在 `id == 0` 時也會在巨集模式跑，第一步說「右上角可加入手續費」（[TxnEditor.kt:253-255](…/ui/screens/TxnEditor.kt)），但巨集模式沒有手續費。這句的位置描述本來就不對：手續費在金額右邊，不在右上角。
- **其他 LaunchedEffect 的干擾**：
  - 自動分類（[TxnEditor.kt:275-282](…/ui/screens/TxnEditor.kt)）：`id == 0 && (categoryId == null || catAuto)`。帶入後 `categoryId` 非 null、`catAuto` 是 false，所以不會覆蓋。只有在帶入的 `repo.accounts.first()` 比 300ms 延遲加上 `suggestCategory` 還慢時，才可能先被設成 `catAuto = true`，之後再被覆蓋（低機率競態，不確定）。
  - 依習慣帶帳戶（[TxnEditor.kt:287-299](…/ui/screens/TxnEditor.kt)）：帶入後 `accountId` 不是 `autoAccount`，所以 return，不干擾。「別人付」步驟的 accountId 是 null，會被帶成習慣帳戶，但存檔走 payer 分支、不用這個值，無害。
  - 定位推薦：巨集模式直接 return，符合預期。
- **寫回 MacroStep**（[TxnEditor.kt:512-530](…/ui/screens/TxnEditor.kt)）：
  - payer：`amount = 總額 − min(他那份, 總額)`、`accountId = 對象`、不帶 shares，符合「別人付時只算我那份，也是我欠他的」。但**少了一般模式的檢查** `his >= t0.amount`（[TxnEditor.kt:538](…/ui/screens/TxnEditor.kt)）：他那份大於或等於總額時，會存成 0 元步驟，回到巨集頁只看到「支出 $0」，儲存鈕灰掉而且不說原因。
  - repay：`TRANSFER(amount, accountId = 對象, toAccountId = 我的帳戶, merchant = t0.merchant ?: "X 還你/借給你")`。商家欄在還款模式是隱藏的（`isRepay`，[TxnEditor.kt:848-849](…/ui/screens/TxnEditor.kt)），帶入時 `merchant = st.merchant`（例如「小明 還你」）。如果把對象改成小華再存，`t0.merchant` 仍是「小明 還你」，**標籤過期而且使用者改不到**。用詞也和一般模式不一致：巨集寫「X 借給你」，一般模式寫「向 X 借」（[TxnEditor.kt:557](…/ui/screens/TxnEditor.kt)）。
  - 一般／收入／轉帳：`MacroStep(type, amount, accountId, toAccountId, categoryId, merchant, shares)`。收入的分類有正確存（`build()` 只有 TRANSFER 會把分類設 null，[TxnEditor.kt:480-490](…/ui/screens/TxnEditor.kt)），轉入帳戶也有存。
  - shares：`splitParts`（[TxnEditor.kt:494-497](…/ui/screens/TxnEditor.kt)）只收大於 0 的金額，新名字會呼叫 `repo.debtPerson(name)` **立即建立往來對象**，就算之後沒儲存巨集也一樣（副作用，P3）。**沒有檢查分帳總和是否小於等於總額**（一般模式靠 `splitReady`，[TxnEditor.kt:498](…/ui/screens/TxnEditor.kt)）。超過時 runMacro 的 `saveWithSplits` 會算出 `own = 0`，只記轉帳，對方欠款被高估。
- **一般模式也有同類問題（記帳頁）**：分帳超過總額時 `splitReady = false`，`save()` 會落到一般存檔（[TxnEditor.kt:564-579](…/ui/screens/TxnEditor.kt) 之後），**整筆記成我的支出、分帳全部丟掉**，只有分帳區顯示紅字「超過總額」（[TxnEditor.kt:1590-1593](…/ui/screens/TxnEditor.kt)），`trySave` 不會擋。

### Inferences
- 巨集模式存檔前應該和一般模式走相同的檢查（他那份小於總額、分帳總和小於等於總額），並把 `trySave` 擴充成能指出錯誤欄位。
- 巨集模式要嘛隱藏「說明」和幣別切換，要嘛把它們存進 MacroStep（建議存，房租這類巨集常需要說明）。
- 還款步驟存檔時，如果 `merchant` 等於帶入時自動產生的名稱，就依新的對象和 repayKind 重新產生。

### Gaps
- 帶入和自動分類之間的競態沒有量測實際時間，僅屬理論。

## runMacro 與通知「套用巨集」（Repository.kt）

### Takeaway
手動執行的邏輯正確（每步依序記，有分帳的支出交給 saveWithSplits）。通知觸發則有幾個問題：沒有跨通知去重、命中哪一步時忽略收支類型、「他還你」步驟永遠不會被入帳通知觸發、帳戶不確定時仍強制記成已確認。復原只刪主交易 id，分帳全額的步驟會留下孤兒。

### Cited Findings
- `runMacro`（[Repository.kt:826-845](…/data/Repository.kt)）：`now = base?.date ?: 現在`。`hit = indexOfFirst { it.amount == b.amount }` 只比金額、**不比類型**（[Repository.kt:828](…/data/Repository.kt)）。命中的那步用 `base`（通知的日期、帳戶、rawText、externalKey、source），其他步驟用 `now`，幣別一律是 baseCurrency（[Repository.kt:832](…/data/Repository.kt)），狀態強制 CONFIRMED，`merchant` 空白時用巨集名稱。
- 通知分支（[Repository.kt:1513-1524](…/data/Repository.kt)）：
  - 符合條件：`fromNotif`；關鍵字比對時移除半形逗號和空白並忽略大小寫，**但不處理全形「，」、全形空白、NBSP**；任一步 `amount == p.amountMinor && (st.type == "INCOME") == (p.type == INCOME)`。
  - TRANSFER 步驟會被當成「非收入」，所以**支出／轉出通知可以命中轉帳步驟**。「他還你」步驟（存成 TRANSFER）**永遠不會被入帳通知命中**，這和規格「通知金額相符某一步」不符。
  - `hitStep = first { amount == … }` 也不比類型。同一巨集有相同金額的支出步和收入步時，收入通知會把通知的帳戶和日期套到支出步上。
  - 只取 `firstOrNull` 的一個巨集，多個巨集金額相同時永遠是第一個，存檔時也沒有衝突提示。
  - 不比較幣別：USD 25.00 和 TWD 25 的最小單位都是 2500，會互相命中（P3）。
  - 通知判讀不確定時 `status` 可能是 PENDING（[Repository.kt:1462-1468](…/data/Repository.kt)），但 runMacro 會強制寫成 CONFIRMED，跳過「不確定就待確認」的原則。
  - **去重**：只靠 `key`（金額、時間、卡號末四碼或套件名）和 rawText 相同。同一筆付款由兩個來源發通知時（例如銀行 App 加 LINE Pay，或刷卡通知加簡訊），套件名不同、rawText 也不同，**整套巨集會執行兩次**。一般流程有 `nearby` 的 3／10 分鐘合併（[Repository.kt:1476](…/data/Repository.kt)、[1676](…/data/Repository.kt)），巨集分支在那之前就 return 了。巨集分支也在 `when (p.kind)` 之前，所以提款、儲值、自轉等通知只要金額相符也會觸發巨集。
  - 命中的步驟如果是「幫別人全付」（own == 0），`saveWithSplits` 會走 [Repository.kt:764-768](…/data/Repository.kt) 的分支，新建的 TxnEntity 不帶 `externalKey`、`rawText`，所以 key 和 rawText 去重都失效，同一則通知重送就會再跑一次。
- **手動執行與復原**（[MacroScreens.kt:113-118](…/ui/screens/MacroScreens.kt)）：`ids` 是每步主交易的 id。`deleteTxn` 會連帶刪手續費和代墊（[Repository.kt:374-386](…/data/Repository.kt)）。但 own == 0 而且有多人分帳時，`saveWithSplits` 只回傳 `.first()`（[Repository.kt:768](…/data/Repository.kt)），而 `deleteTxn` 對 TRANSFER 不會連帶刪除（`splitsOf` 只處理 EXPENSE），所以**復原後其他人的代墊轉帳會留著**。其他問題：「執行」不防連點，第二次的 Undo 會蓋掉第一次的，第一次就無法復原；沒有確認，也不能選日期（例如補記上個月的房租）；在 `rememberCoroutineScope` 裡依序寫入，執行中離開頁面會被取消，只記了一部分而且沒有 Undo（推論）。
- 步驟引用的帳戶被刪除：`deleteAccount`（[Repository.kt:865-880](…/data/Repository.kt) 附近）會 detach 交易，但不會處理 `settings.macros`，runMacro 仍會寫入已不存在的 accountId（不確定 Room 有沒有 FK 會擋）。

### Inferences
- 通知分支應該：(1) 在 runMacro 前檢查 `nearby` 裡是否已有本巨集 10 分鐘內產生的交易（例如給每次執行一個 `MACRO:<macroId>:<分鐘>` 的 externalKey 前綴）；(2) 命中判斷改成同一個函式，同時比金額和類型（入帳通知要能命中 INCOME 或「TRANSFER 從 LOAN 轉入」的步驟）；(3) `status` 不確定時至少讓命中的那步保持 PENDING，或整套都進待確認；(4) own == 0 時也要把 base 的 externalKey 和 rawText 帶到第一筆轉帳。
- `saveWithSplits` 的 own == 0 分支應回傳所有 id，或讓 runMacro 自己收集。

### Gaps
- 沒有追通知列「刪除／撤銷」的快捷動作（QuickActions）對巨集多筆的處理：它只拿到 `IngestResult.id`（第一步），推測只會刪第一步。

## 記帳頁帳戶列（付款／存入／由 X 付／自動）

### Takeaway
標籤和「由 X 付」「自動」都照規格做了。「自動」標籤在改了商家而新商家沒有使用習慣時會留在舊值上；點「由 X 付」會直接切回自己付，但對方那一列會變成平分的「X 欠你」，可能出乎意料。

### Cited Findings
- 標籤：英文介面是 `Account`，中文收入是「存入」、其他是「付款」；有付款人時顯示「由 X 付」，點了會 `paidBy = false` 並打開帳戶面板（[TxnEditor.kt:833-845](…/ui/screens/TxnEditor.kt)）。
- 「自動」：條件是 `accountId == autoAccount`（[TxnEditor.kt:840](…/ui/screens/TxnEditor.kt)）。手動選帳戶會把 `autoAccount` 設成 null（[TxnEditor.kt:1074-1075](…/ui/screens/TxnEditor.kt)）。
- **過期的自動值**：習慣帶入只會「找到就改」，`pick == null` 時不清掉（[TxnEditor.kt:296-298](…/ui/screens/TxnEditor.kt)）。重現：打「全聯」被自動帶成信用卡 A，再把商家改成沒記過的店，帳戶仍是 A 而且標著「自動」，但這已經不是依這家店的習慣。修法：`pick == null && accountId == autoAccount` 時把 accountId 和 autoAccount 一起清成 null。
- 點「由 X 付」後，`splitRows` 仍保留該對象（通常 `auto = true`），SplitSection 的平分邏輯（[TxnEditor.kt:1532-1541](…/ui/screens/TxnEditor.kt)）會把他變成「X 欠你」總額的一半。使用者本意可能只是「我自己付」，卻多出一筆代墊（P3，UX）。巨集帶入的「別人付」列是 `auto = false`、expr 為空，切換後是 0，又不會產生代墊，行為不一致。

### Inferences
- 點「由 X 付」可以考慮改成打開「付款人」選擇，或切回自己付時把那個人移除，並顯示 Undo 提示。

### Gaps
- 無。

## 店家推薦（withBest）：不自動帶入、最可能的排第一

### Takeaway
確認已經**不再自動帶入**店名：搜尋整個檔案，沒有任何 `merchant = best` 或 `merchantAuto = true`。`best` 只透過 `withBest` 排在推薦列第一個。剩下的問題是：推薦列會隨網路結果多次重排，容易點錯；第一個沒有任何「最可能」的標示；程式裡留有過期註解和沒用到的變數。

### Cited Findings
- `best` 的來源依序是 `storeHere`（只限支出）、Mapbox 30 公尺內單一對應、Google 最近一家。`withBest = (best + list).distinct().take(8)`（[TxnEditor.kt:380-415](…/ui/screens/TxnEditor.kt)）。
- `nearby` 在同一個 effect 內會被賦值 2-4 次（[TxnEditor.kt:382](…/ui/screens/TxnEditor.kt)、[402](…/ui/screens/TxnEditor.kt)、[403](…/ui/screens/TxnEditor.kt)、[413](…/ui/screens/TxnEditor.kt)、[415](…/ui/screens/TxnEditor.kt)）。第一次是本機紀錄，幾秒後換成 Mapbox 或 Google 的結果，**推薦列整排換掉**，使用者正要點的時候位置可能會跳。
- 推薦 chip 只在 `merchant == n` 時有底色（[TxnEditor.kt:860-866](…/ui/screens/TxnEditor.kt)），第一個（最可能的店）沒有任何標示，例如圖示或「這裡」。
- 判斷 `best` 時用的 `type` 是 effect 啟動時的值（`LaunchedEffect(Unit)`）。打開後才切換收支類型不會重算；切到收入時推薦列仍會顯示店名（條件只有 `type != TRANSFER`，[TxnEditor.kt:853](…/ui/screens/TxnEditor.kt)）。
- 過期註解：[TxnEditor.kt:369-372](…/ui/screens/TxnEditor.kt)（「店名直接帶入」）、[409-410](…/ui/screens/TxnEditor.kt)（「直接帶入你現在所在的店」）、[388](…/ui/screens/TxnEditor.kt)（「還沒依位置帶入店名」）都和現在的行為相反。`val stalls`（[TxnEditor.kt:399](…/ui/screens/TxnEditor.kt)）沒被使用。
- 關閉定位提示時的教學文字說「並帶入上次使用的分類與帳戶」（[TxnEditor.kt:258-259](…/ui/screens/TxnEditor.kt)）。實際上點自動完成只會在沒有分類時帶分類（[TxnEditor.kt:915-918](…/ui/screens/TxnEditor.kt)），帳戶要靠「最近 10 筆至少 2 筆、六成以上」的習慣規則，不是「上次使用」，文字與程式不符。

### Inferences
- 建議第一次得到 `best` 後就固定在第一個，之後的結果只往後追加、不重排。第一個 chip 加上小圖示（定位點）。

### Gaps
- `PlaceHints.storeHere` 本身的準確度不在本次範圍。

## 金額欄位 amountFresh（點了以後第一個數字取代舊值）

### Takeaway
主流程正確：點金額、手續費或分帳列都會設 fresh，第一個數字取代舊值，運算符號則接在原值後面。但因為取代是「先 append 再取尾巴」，被 `Calculator.append` 拒絕的按鍵會讓第一個數字消失。另外以小數點開頭會得到「.」。

### Cited Findings
- 設 fresh 的地方：點金額（[TxnEditor.kt:716](…/ui/screens/TxnEditor.kt)）、手續費（[TxnEditor.kt:746](…/ui/screens/TxnEditor.kt)）、分帳列（[TxnEditor.kt:970](…/ui/screens/TxnEditor.kt)），以及 `LaunchedEffect(panel, splitIdx)` 在 panel 切到 AMOUNT／FEE／SPLIT 時（[TxnEditor.kt:1023](…/ui/screens/TxnEditor.kt)）。
- 取代邏輯（[TxnEditor.kt:1031-1038](…/ui/screens/TxnEditor.kt)）：`v0 = append(old, key)`。如果 `v0` 以 `old` 開頭、而且多出的部分以數字或 `.` 開頭，就取多出的部分，然後 `amountFresh = false`。
- **兩位小數被吞**：`Calculator.append` 遇到小數已經兩位時直接回傳原字串（core `Calculator.append` 的 `decimals.length >= 2 -> expr`）。這時 `add` 是空字串，`v = v0 = old`，`amountFresh` 卻已被設成 false，第一個按鍵沒有反應，之後的按鍵也被擋。重現：編輯一筆 12.99 的外幣交易（`minorToExpr` 會給出 "12.99"），點金額按 5，金額不變，再按 5 還是不變，只能先按退格。分帳列的 "33.33" 也一樣。
- 舊值已經有小數點時按「.」也一樣被吞。舊值是整數時按「.」會得到 `"."`（不是 `"0."`），金額顯示「$ .」。按「00」會得到 `"00"`。
- 計算機模式按「=」以後（[TxnEditor.kt:1369](…/ui/screens/TxnEditor.kt)），fresh 不會重新設定，下一個數字會接在結果後面（例如 150 變 1505）。一般計算機會在按「=」後重新開始（P3）。
- 視覺回饋：fresh 時金額有底色（[TxnEditor.kt:733](…/ui/screens/TxnEditor.kt)），分帳列也有（[TxnEditor.kt:1584](…/ui/screens/TxnEditor.kt)），做得好。但手續費 chip 沒有 fresh 的底色。

### Inferences
- 修法：fresh 時把數字和小數點直接從空字串開始，`v = key 經 Calculator.append("", key) 後的結果`（`.` 會變成 `"0."`、`00` 會變成 `"0"`）；運算符號或退格才用目前的邏輯。按「=」後重新把 fresh 設成 true。

### Gaps
- 沒有逐鍵實測。
