# 互動陷阱與手勢衝突（原始碼審查）

範圍：`app/src/main/java/com/enwei/moneymanager/ui/`。已修好的兩個問題（日曆與 SubTabs 切換時叫回 Chrome、工具格長按才拖曳）不再列出，只拿來當比對模式。
來源標示方式：以「檔案:行號」當出處（路徑都相對於 `ui/`）。截圖證據：`/tmp/claude-0/-home-user-Money-Manager/00d836e8-a7fc-54e2-bce1-8a1c58ffbc65/scratchpad/shots3/02_txns_calendar.png`。

背景機制（後面各項都會用到）：
- 收起標題和分頁列的機制有三層，彼此獨立：
  1. `Chrome.bottomHidden / topHidden`（components/CollapsingTop.kt:59-79）：控制底部分頁列和 `BackTopBar`。
  2. 各分頁自己的 `TopAppBarDefaults.enterAlwaysScrollBehavior()`：TransactionsTab.kt:248、StatsTab.kt:177、AccountsTab.kt:158、AdvisorScreen.kt:182。
  3. `CollapsingTop` 內部的 `offset`（components/CollapsingTop.kt:26-27）：用 `remember` 存，沒有對外重設的方法。
- 已做的修正只會重設第 1 層：SubTabs.kt:40、TransactionsTab.kt:194、TransactionsTab.kt:366-369（日曆的 `detectVerticalDragGestures` 只改 Chrome 旗標）。第 2、3 層只能靠子元件發出的 nested scroll 叫回來。日曆的 `detectVerticalDragGestures` 不會發出 nested scroll。
- nested scroll 的 pre-scroll 是外層先處理。所以手指往上滑時，`enterAlways` 的 TopAppBar（第 2 層）會先收，收完才輪到 CollapsingTop 的頁首（第 3 層，裡面放分頁 TabRow）。
- `enterAlwaysScrollBehavior()` 預設用 `rememberTopAppBarState()`，這是 rememberSaveable。NavHost 切分頁時用了 `restoreState = true`（MainActivity.kt:302-306），所以「收起」狀態在切回分頁時會被還原。CollapsingTop 的 offset 用的是 `remember`，切回時會歸零。

## 哪些畫面會留下收起的標題列或分頁列，而內容捲不動、叫不回來

### Takeaway
最嚴重的兩個陷阱都在「交易」分頁：
- 切到日曆時只叫回了底部分頁列，沒有叫回月份標題列。
- 小螢幕或大字級時，日曆捲動會讓頁首收起，收起後日曆變成「放得下、不能捲」，三層 chrome 都卡住。

其他用 TabRow（不是 SubTabs）切換的頁面，因為內容都是 LazyColumn 或 verticalScroll，大多還能叫回，只有少數空狀態例外。

### Cited Findings

**[高] H1. 交易分頁：切到「日曆」時，月份標題列（上一期／下一期、地圖、搜尋、待確認）卡在收起狀態**
- 出處：TransactionsTab.kt:194 只重設 Chrome，沒有重設 `topScroll.state.heightOffset`；TopAppBar 在 TransactionsTab.kt:248-264；日曆的下拉補救在 TransactionsTab.kt:366-369，同樣只改 Chrome 旗標。
- 對照：StatsTab.kt:178-179 做法正確，`LaunchedEffect(view) { topScroll.state.heightOffset = 0f }`，註解寫明「分析內容短、不能捲動時，否則就找不到切換期間的箭頭」。交易頁漏了同樣的處理。
- 日曆在一般手機上放得下、不能捲：
  - TransactionsTab.kt:845-847 只有 `fit == false` 時才加 `verticalScroll`。
  - 截圖 02_txns_calendar.png（1080×2400）顯示整月剛好放滿，沒有捲軸。
- 重現步驟：
  1. 在「每日」往上輕滑約一個標題列高度。外層先吃掉滑動量，所以 TopAppBar 收起，但每日／日曆 TabRow 還在。
  2. 點「日曆」。
  3. 標題列不見，在日曆上往下拉也叫不回來。`detectVerticalDragGestures` 不產生 nested scroll，`enterAlways` 收不到事件。
  4. 使用者無法換月份。若沒開滑動換月（`settings.swipe == 1`），只能先切回「每日」再往下拉。
- 修正方式（擇一或並用）：
  - 改成 `LaunchedEffect(tab, calSpan) { topScroll.state.heightOffset = 0f; …Chrome 重設… }`。
  - 日曆外層的 `Box(Modifier.pointerInput{detectVerticalDragGestures…})` 改成 `Modifier.scrollable(rememberScrollableState { 0f }, Orientation.Vertical)`。這樣即使內容捲不動，也會發出 nested pre-scroll，三層（Chrome watcher、topScroll、CollapsingTop）都能被往下拉叫回。

**[高] H2. 交易日曆在「可捲動」和「放得下」之間切換：捲一下就讓頁首、月份列、TabRow 全部卡住**
- 出處：
  - 月曆：TransactionsTab.kt:845-847（`fit = (maxHeight - headerH) / weeks >= 64.dp`，只有 `!fit` 才 `verticalScroll`）。
  - 年曆：TransactionsTab.kt:1188-1190（`fit = (maxHeight - 28.dp) / 4 >= 110.dp`）。
- 機制：
  1. 螢幕矮、字級大、橫向或分割畫面時 `fit = false`，日曆可以捲。
  2. 往上捲會依序收起 TopAppBar、CollapsingTop 頁首（每日／日曆 TabRow、SetupBanner、SummaryBar）和底部分頁列。
  3. 收起後 `BoxWithConstraints` 拿到的 `maxHeight` 變大，`fit` 變成 true，`verticalScroll` 被拿掉。
  4. 內容變得捲不動，再也收不到 nested scroll。
- 結果：
  - 只有底部分頁列能靠 366-369 行的下拉補救叫回。
  - 月份列和每日／日曆 TabRow 都叫不回，使用者連切回「每日」都辦不到。
  - 必須按底部分頁切走再回來：CollapsingTop 的 offset 是 `remember`，會重設；但 topScroll 是 saveable，還原後月份列仍是收起的。
- 重現步驟（年曆最容易觸發，需要 maxHeight < 468dp 才會不 fit）：
  1. 系統字級調到最大，或用小螢幕、橫向。
  2. 交易 → 日曆 → 年。
  3. 往上捲年曆。
  4. 頁首全部收起，年曆變成剛好放滿，從此捲不動。
- 補充：年曆點某個月會執行 `calSpan = 0`（TransactionsTab.kt:375-376 的 `YearCalendar(...) { ym -> month = ym; calSpan = 0 }`）。這也是一次沒有重設 topScroll 和 CollapsingTop 的內容切換。
- 修正方式：
  - 同 H1，用 `Modifier.scrollable(...)` 讓不能捲的日曆也發出 nested scroll。
  - 或者計算 `fit` 時改用「頁首全部展開時」的固定高度，例如在 BoxWithConstraints 外先量好，避免收起後判斷結果翻轉。
  - 並在 `calSpan` 改變時重設 topScroll 和 CollapsingTop。

**[中] H3. `CollapsingTop` 沒有重設方法，是 H1、H2 的根本原因之一**
- 出處：CollapsingTop.kt:26-27 的 `offset` 由 `remember` 持有，沒有提升成可傳入的 state。
- 用 CollapsingTop 而且把切換器放在 header 裡的頁面：
  - 交易：TransactionsTab.kt:316-341，每日／日曆 TabRow。
  - 統計：StatsTab.kt:229-238，收入／支出 TabRow。
  - 資產：AccountsTab.kt:237-245，帳戶／股票 TabRow。
  - 股票助理：AdvisorScreen.kt:153-158，今日／問 AI／新聞／紀律 TabRow。
  - 新聞頁首：AdvisorScreen.kt:1159。
  - 搜尋：TxnScreens.kt:132，搜尋框與期間列。
  - 篩選：FilterScreen.kt:144-174，收入／支出／帳戶 TabRow。
- 這些 TabRow 都是 Material `Tab`，不是 `SubTabs`，所以連 Chrome 都不會重設。
- 目前只要切換後的內容是 LazyColumn 或 verticalScroll（經檢查：AccountsTab 的帳戶和 StockContent 都是 LazyColumn，InvestScreens.kt:159；助理四個分頁是 verticalScroll 或 LazyColumn，AdvisorScreen.kt:238、810、1214、1555），往下拉就能叫回，所以實際風險集中在交易日曆。
- 修正方式：
  - 新增 `class CollapsingTopState { var offset }`，加上 `rememberCollapsingTopState()`，以及 `CollapsingTop(state = …)`。
  - 在 tab、calSpan、view 改變時呼叫 `state.offset = 0f`。
  - 也可以寫一個共用的 `ResetChromeOnChange(key, topScroll, collapsing)`，把三層一起重設，取代各處散落的 `Chrome.bottomHidden = false`。

**[低] H4. 股票助理：關閉股票功能後，標題列可能永遠收著**
- 出處：AdvisorScreen.kt:182-209。`featureStocks == false` 時只顯示 `EmptyHint`（不能捲）。
- 重現步驟：
  1. 在助理頁往上捲，標題列收起。
  2. 到設定關掉股票功能。
  3. 回到助理頁：topScroll 是 saveable，還原成收起；EmptyHint 捲不動。
  4. 「股票助理」標題和搜尋鈕叫不回來。
- 修正方式：`LaunchedEffect(settings.featureStocks) { topScroll.state.heightOffset = 0f }`；或空狀態也包一層 `verticalScroll`。

**[低] H5. 股票助理的 TabRow 切換不叫回 chrome；問 AI 分頁的工具列和輸入列都不能捲**
- 出處：AdvisorScreen.kt:154-158 是 TabRow。ChatTab 只有中間的 LazyColumn 能捲（AdvisorScreen.kt:809-810），上方「新對話／過去的對話」那列（:776-806）和下方輸入列（:894-906）不能捲。
- 重現步驟：
  1. 在「新聞」往上捲，助理標題列和 TabRow 收起。
  2. 往下拉一點讓 TabRow 出現（外層 TopAppBar 先展開），切到「問 AI」。
  3. 在輸入框附近往下拉沒有反應，必須在對話清單區拉。
- 能叫回，但不直觀。
- 修正方式：TabRow 的 onClick 同時重設 Chrome、topScroll 和 CollapsingTop。

**沒問題、可以當正面對照的地方**
- 支出地圖：SpendMapScreen.kt:193-260。上方期間、地圖固定不動，只有下方 LazyColumn 捲動；收起後在清單往下拉就能叫回。
- `MapPreview`：SpendMapScreen.kt:685-692 在地圖上蓋一層 clickable，不搶頁面捲動，做法正確。

### Inferences
- H1、H2 和使用者剛回報的 bug 1 是同一個模式。前一輪只修了第 1 層（Chrome），第 2、3 層的 TopAppBar 和 CollapsingTop 漏修。
- 只要有任何「不能捲的內容」，最穩的修法是讓它也發出 nested scroll（`scrollable` 搭配 consume 0），而不是在各處手動把旗標設成 false。
- H2 是否觸發取決於裝置高度和字級。shots3 的 `26_bigfont_*` 只有交易每日、資產、記帳，沒有大字級日曆截圖，所以 H2 是依程式碼推論，沒有實機證據。

### Gaps
- 沒有在模擬器實測 H1、H2；兩者都是依 nested scroll 的分派順序和程式碼推得。建議用小螢幕（360×640dp）或最大字級的模擬器重現。
- AccountDetail（AccountsTab.kt:533-560）的 TopAppBar 沒有 scrollBehavior，不會收起，不列入。

## 水平手勢與拖曳，是否吃掉垂直捲動（或反過來）

### Takeaway
K 線和地圖的手勢處理大致正確。真正會擋住頁面捲動的是：
- 工具格編輯模式的「右下角改大小把手」：立即拖曳，和 bug 2 同一個模式。
- 交易頁的滑動換月在年曆模式下行為錯誤。

### Cited Findings

**[中] G1. 工具格編輯模式：每格右下角 32dp 的改大小把手一碰就拖，在那裡開始上下滑會改大小，頁面不會捲**
- 出處：ToolGrid.kt:219-238 用的是 `detectDragGestures`，裡面有 `ch.consume()`，沒有長按門檻。移動整格已經改成 `detectDragGesturesAfterLongPress`（ToolGrid.kt:184-198）。
- 外層是 `verticalScroll`（MoreScreens.kt:156），編輯提示寫著「上下滑動可捲動頁面」（MoreScreens.kt:158）。
- 重現步驟：
  1. 工具 → 編輯。
  2. 手指從任一格的右下角往上滑。
  3. 結果是那格的高度在 1 和 2 列之間變動（ToolGrid.kt:231 的 `coerceIn(1, 2)`），頁面不捲。
- 每格都有一個把手，格子排滿時，把手占可觸控面積的比例不小。
- 修正方式（擇一）：
  - 改成 `detectDragGesturesAfterLongPress`。
  - 只在被選取的那格（`selected == t.id`）顯示把手並掛上 pointerInput。
  - 或者把手只回應水平為主的拖曳，例如自訂 awaitEachGesture，只有在 |dx| > |dy| 時才 consume。

**[中] G2. 交易頁滑動換月（設定 swipe = 1）在年曆模式只會移動一個月，看起來沒反應**
- 出處：TransactionsTab.kt:304-312 用的是 `month.minusMonths(1) / plusMonths(1)`，而且 `yearly` 固定是 false（:211）。正確的分期邏輯 `step()`（:214-222）已經處理 `tab == 1 && calSpan == 2 -> plusYears`，滑動卻沒有用它。
- 重現步驟：
  1. 設定開啟滑動換月。
  2. 交易 → 日曆 → 年。
  3. 左右滑：標題的「2026年」不變，因為 range 以 `month.year` 計算，要滑到跨年才會變。
- 修正方式：`onDragEnd` 改成呼叫 `step(-1) / step(1)`。

**[低] G3. 滑動換月的 pointerInput 包住整個內容 Column，包含頁首 TabRow 與日曆格**
- 出處：TransactionsTab.kt:314，`Column(...then(swipeModifier))`。
- `detectHorizontalDragGestures` 要先超過水平觸控門檻才觸發，對垂直捲動影響不大。但日曆格是 `combinedClickable`（長按記帳，:894）：在格子上斜滑可能換月而不是捲動或長按。屬於輕微誤觸。
- 修正方式：滑動換月只掛在內容區（CollapsingTop 的 content），不要涵蓋頁首；並把觸發門檻從 160px 改成以 dp 計算（:308-309 用的是 px，高密度螢幕上距離偏短）。

**[低／推論] G4. K 線雙指縮放：第一根手指先垂直移動時，可能被外層頁面捲動搶走**
- 出處：StockDetailScreen.kt:767-788。縮放的 awaitEachGesture 只有在 `pressed >= 2` 才 consume；`detectHorizontalDragGestures` 會 consume 水平拖曳；`detectTapGestures` 點選 K 棒。
- 單指上下滑仍能捲頁（註解 :766），這部分正確。
- 推論的問題：雙指沒有同時落下、第一指先移動超過垂直門檻時，外層 verticalScroll 已開始拖曳，捏合就變成捲頁。這是依 Compose 手勢分派推得，未實測。
- 修正方式：在 `PointerEventPass.Initial` 偵測到第二根手指就 consume；或者縮放、平移改用 `detectTransformGestures`，搭配「兩指才處理」的自訂 awaitEachGesture。

**[無問題] G5. 支出地圖的 `detectTransformGestures`**
- 出處：SpendMapScreen.kt:520-527。單指拖曳會被地圖完全吃掉，但地圖區塊固定不捲（:193-217，註解「上方…固定不動，只有下方的地點清單捲動」），不構成衝突。
- MapPicker 是 Dialog 裡的 460dp 地圖（:677），同樣沒有外層捲動。

**[無問題] G6. 排序清單的拖曳**
- 出處：Reorder.kt:68-89。`detectDragGestures` 只掛在 48dp 的把手上（Reorder.kt:142），列的其他區域可以正常捲動，不會重現 bug 2。

### Inferences
- G1 和使用者回報的 bug 2 是同一個模式：在可捲動的容器裡，對大量小區域使用立即型的 `detectDragGestures`。
- 全專案用 `detectDragGestures` 的只有 Reorder.kt（把手）和 ToolGrid.kt（改大小把手），其中只有後者需要改。

### Gaps
- `horizontalScroll` 的列（ReviewScreen.kt:121、398；AdvisorScreen.kt:457、505、889、1537、1674、2250；StockDetailScreen.kt:433）都是單純的晶片列，沒有發現和外層衝突的程式碼，但沒有實測斜滑的手感。

## 點擊目標太近或巢狀，造成誤觸

### Takeaway
沒有發現嚴重的巢狀 clickable 錯誤。主要是幾個小目標或「整片可點」造成的誤觸：
- 新手導覽遮罩點任何地方都會前進。
- 標題文字點一下就跳回本月。
- 颱風假切換的觸控範圍太小。
- 工具格移除鈕太小，而且沒有復原。

### Cited Findings

**[中] T1. 新手導覽／頁面導覽遮罩：整個畫面可點，點任何地方（包括被圈起來的目標）都會進入下一步；系統返回鍵不關閉導覽**
- 出處：Coach.kt:149 的 CoachOverlay。最外層 `BoxWithConstraints(Modifier.fillMaxSize().clickable { Coach.next() })`（約 :160），整個 Coach.kt 沒有 `BackHandler`（grep 結果為空）。
- 重現步驟：
  1. 第一次進支出地圖，出現頁面導覽。
  2. 使用者照著說明去點地圖上的圓點，結果只是跳到下一步。
  3. 按返回鍵：NavHost 會返回上一頁，但 `Coach.step` 仍然有效，遮罩跟到上一頁，挖空位置也是錯的。
- 另一個風險：說明卡在目標下方的位置是 `hole.bottom + 12dp`（約 :178），沒有限制在螢幕內。目標很大時（例如 `map.list`、`st.pie`），說明卡和「略過」按鈕可能被擠出畫面。不過點空白處仍會前進，所以不至於卡死。
- 修正方式：
  - 加上 `BackHandler { Coach.stop() }`。
  - 點到挖空區域時穿透給目標，或者至少不要前進。
  - 說明卡的 y 座標用 `coerceAtMost(screenH - cardH)` 限制在畫面內。

**[低] T2. 交易、統計頁的月份標題文字可點，點了會跳回本月或今天，而且夾在兩個箭頭中間**
- 出處：TransactionsTab.kt:279（`Modifier.clickable { month = Periods.monthOf(LocalDate.now(), startDay) }`）；StatsTab.kt:193-194。
- 重現：連續按「上一期」翻到半年前，手指稍微偏一點點到標題，直接跳回本月，沒有提示也不能復原。
- 修正方式：改成明確的「今天」小按鈕，或標題旁加上 ↺ 圖示，並加 `Role.Button` 和 contentDescription；或者只在長按時回到本月。

**[低] T3. 日曆當日底部面板的「標記颱風假／取消颱風假」只有約 20dp 高，點下去立即切換**
- 出處：TransactionsTab.kt 約 :960-961，`Text(...).clickable { repo.setTyphoonDay(day, !typhoon) }.padding(horizontal = 6.dp, vertical = 2.dp)`。它和信用卡日程標籤放在同一排 FlowRow。
- 誤觸會讓信用卡結帳、繳款、扣繳日期順延（註解 :958），影響金額和提醒。
- 修正方式：加大到 48dp（例如 `minimumInteractiveComponentSize()`），切換後顯示 Undo（專案已有 `components/UndoBar.kt`）。

**[低] T4. 工具格編輯模式的移除鈕 24dp，點了立即移除，沒有復原**
- 出處：ToolGrid.kt:205-212；MoreScreens.kt:172（`onRemove = { id -> setOrder(shown.map { it.id } - id) }`）。
- 移除鈕在格子右上角，和格子本體的 combinedClickable（點一下是選取）緊鄰。
- 可以從下方「可加入」清單加回，但原本的位置和大小會遺失。
- 修正方式：觸控範圍擴到 48dp，移除後用 `Undo.show(...)` 恢復原本的排列。

**[低] T5. 工具格編輯模式沒有 BackHandler**
- 出處：MoreScreens.kt:133（`var editing by remember`）、:150。
- 按返回鍵不是離開編輯，而是直接離開工具頁或 App。

## 無法關閉的對話框或面板，以及鍵盤遮住儲存鈕

### Takeaway
沒有找到無法關閉的對話框或面板。記帳的儲存鈕不會被鍵盤蓋住，但位在長表單的最底端，需要捲動才找得到。

### Cited Findings
- 全專案 grep `onDismissRequest = {}`、`dismissOnBackPress = false`、`dismissOnClickOutside = false`、`confirmValueChange`，結果都是零。
- 4 個 ModalBottomSheet 都有 `onDismissRequest`：AdvisorScreen.kt:1326、1355、1419；TransactionsTab.kt:940。
- 搜尋頁的圖表篩選是全螢幕 Dialog，有 `BackHandler`（TxnScreens.kt:254-266）和「關閉」按鈕（FilterScreen.kt:139）。
- MapPicker（SpendMapScreen.kt:665-681）頂部有「取消／設定」，返回鍵或點外面會呼叫 `onDone(null)`。
- 記帳編輯（TxnEditor.kt）：
  - 表單在 `Column(weight(1f).verticalScroll().imePadding())`（:597）裡，「儲存／繼續」在表單最後（:856-871）。
  - 金額鍵盤是 BottomPanel，放在捲動區外（:899），面板打開時表單被壓縮，儲存鈕要往下捲才看得到。
  - 面板開著時，返回鍵先關面板（:213）。
  - 按儲存但缺欄位時，會直接打開那一欄並提示（:531-536）。
  - 結論：不會卡住，但儲存鈕不固定在下方。
- 鍵盤打開時底部分頁列會隱藏（MainActivity.kt:316、328），不會擋住輸入框。
- **[低] K1. 記帳表單的儲存鈕在長表單底部，金額鍵盤或系統鍵盤開著時要捲到底才看得到**
  - 出處：TxnEditor.kt:597、856-871、899。
  - 修正方式：「儲存」移到 Scaffold 的 bottomBar，或者放在 BottomPanel 的標題列上，加一個「完成並儲存」。

### Inferences
- 這一類目前沒有高風險項目。比較值得處理的是 K1 的可發現性，屬於效率問題，不會讓人卡住。

### Gaps
- AdvisorScreen.kt:1419-1439 的 ModalBottomSheet 裡面有 OutlinedTextField 和 `LazyColumn(heightIn(max = 460.dp))`。鍵盤打開時，Material3 ModalBottomSheet 是否把清單推到可見範圍，取決於 Material3 版本的 inset 處理，程式碼看不出來，需要實機確認。
- shots3 的截圖都是靜態畫面，沒有手勢操作過程的錄影或記錄，所以本節所有手勢結論都來自程式碼。
