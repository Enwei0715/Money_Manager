## Q2. splitsOf 只認編號後：所有建立代墊的路徑都有編號嗎？keyLegacyAdvances 與三個遷移的順序是否安全？

### Takeaway
所有會建立代墊的程式路徑（編輯器、巨集、多選分帳）都經過 `saveWithSplits`，新資料一律有 `SPLIT:` 或 `ADV:`（或沿用通知的 `N:`）編號；往來頁、借貸頁、定期交易、通知 debtMatch 都不直接建代墊。`keyLegacyAdvances` 用 `used` 集合避免唯一索引衝突、三個遷移互不踩到對方的資料；但它挑母單的條件太寬，會把手續費或無關支出選成母單（N2）。

### Cited Findings
- 建立代墊的呼叫點只有三處：編輯器 [E:573](app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)、巨集 [R:873](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、多選分帳 [T:1430](app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)；全程式搜尋 `"代墊`／`saveWithSplits` 無其他建立處（`grep -rn "代墊：\|saveWithSplits"`）。
- 往來頁「記錄代墊」與借貸頁「記一筆代墊」都只是導到編輯器 `txn/0?type=EXPENSE&split=<id>` — [DebtScreens.kt:152](app/src/main/java/com/enwei/moneymanager/ui/screens/DebtScreens.kt)、[LoanScreens.kt:142](app/src/main/java/com/enwei/moneymanager/ui/screens/LoanScreens.kt)。
- 有分帳時：主單 key 不變，代墊 `externalKey = old?.externalKey ?: "SPLIT:$mainId:$pid"` — [R:778-787](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。整筆代墊：第一人沿用原筆（`t.externalKey ?: "ADV:${System.nanoTime()}"`），其餘 `ADV:<nanoTime>:<pid>` — [R:766-775](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。
- 巨集執行時 own==0 的步驟回傳第一筆 id；巨集的「復原」只刪回傳的 id — [MacroScreens.kt:115-116](app/src/main/java/com/enwei/moneymanager/ui/screens/MacroScreens.kt)，多人整筆代墊的第 2 人以後不會被復原（舊行為，c52cb41 已如此，非新引入）。
- keyLegacyAdvances：只處理 `TRANSFER && externalKey == null && toAccountId ∈ 往來 && merchant 以「代墊」開頭`；母單＝`all.firstOrNull { EXPENSE && date 相同 && accountId 相同 && accountId != null }`；key 若已在 `used` 就退回 `ADV:<自己id>` — [R:796-809](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。`db.txns().all()` 是 `SELECT * FROM transactions`，沒有 ORDER BY — [D:88-89](app/src/main/java/com/enwei/moneymanager/data/Daos.kt)（實務上多為 id 遞增，但不保證）。
- 啟動順序：`ensureSeedData → runRecurring → runFeeRebates → moveAutoDividendsToBroker → keyLegacyAdvances → revertPayerExpense → dropZeroAdvanceExpenses` — [M:57-64](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)；`runRecurring`、`runFeeRebates` 沒包 runCatching（[M:59-60](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)）。
- revert 只處理 `accountId == null` 且 key 以 `SPLIT:` 開頭的代墊 — [R:838](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)；keyLegacy 對 `accountId == null` 的代墊一定補 `ADV:`（因母單條件要求 `accountId != null`）→ 兩者不重疊。revert 內部又呼叫一次 dropZero（[R:847](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），dropZero 有自己的旗標（[R:818](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。
- 備份還原：`importRaw` 先 `prefs.edit().clear()` 再寫入備份的設定 — [data/Settings.kt:809](app/src/main/java/com/enwei/moneymanager/data/Settings.kt)；舊備份沒有 `advancesKeyed` → 變回 false，但 keyLegacy 只在 `MoneyApp.onCreate` 跑（[M:62](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)），還原後到下次重開 App 之前，舊代墊沒有編號。

### Inferences
- **唯一索引衝突**：`used` 包含所有既有 key，同一母單同一人的第二筆舊代墊會退成 `ADV:<id>`；`ADV:<id>` 每列不同；與 `ADV:<nanoTime>` 撞號實務上不可能 → 不會衝突。若真的衝突，`@Upsert` 的 UPDATE 會丟例外 → `runCatching` 吞掉、整個 transaction 回滾、旗標不寫，每次開 App 重試（推論）。
- **三個遷移的順序**沒有互相覆寫的問題；唯一交互是：keyLegacy 可能把舊式代墊掛到一筆 $0 支出上，而大多數既有使用者 `zeroAdvanceCleaned` 已是 true，dropZero 不會再跑 → 那筆「−$0」仍留在清單（舊審查 P1-8 的漏網情況仍在，但使用者打開那筆再存一次會走 own==0 路徑自我修復）。
- **母單挑選錯誤**是唯一實質問題（N2）：舊審查 P0-2 的誤認、P1-6 的手續費互相隱藏，在舊資料上被「固化」成正式的 SPLIT 編號。
- 啟動鏈前段若 `runRecurring`／`runFeeRebates` 丟例外，keyLegacy 當次不會跑（appScope 的處理器只記 log）→ 舊代墊在該次執行期間找不到（編輯時不會顯示分帳、刪主單不連帶刪代墊）（推論，低機率，P3）。

### Gaps
- 無法確認還原備份後 App 是否強制重啟（未找到 UI 端的重啟程式碼），因此「還原後到重開前」的視窗大小不確定。

## Q3. saveWithSplits own==0 把既有支出就地改成 TRANSFER 的後果

### Takeaway
手續費、通知紀錄、刪除與復原都因為保留原 id 而正常；但改型別是經 `saveTxn` 寫入，會觸發「店名對照學習」把 `X店 → 代墊：X店` 學起來並改寫所有通知記的同名交易（N1，新引入、P1）。轉換後無法在編輯器改回分帳支出、原分類被清空、多人時其他人的代墊與原筆沒有連結（N3）。`ADV:` 不被 debtMoves 認為是代墊，只靠店名前綴（N4）。

### Cited Findings
- 轉換本身：`saveTxn(t.copy(type = TRANSFER, amount = v0, toAccountId = p0, categoryId = null, merchant = label, externalKey = t.externalKey ?: "ADV:…"))` — [R:767-768](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)；`label = "代墊：" + 店名` — [R:763](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)。

## Q4. LIKE 前綴 'SPLIT:12:%' 會不會配到 SPLIT:123:…？

### Takeaway
不會。查詢是 `externalKey = 'SPLIT:12' OR externalKey LIKE 'SPLIT:12:%'`，`12` 後面必須是字面冒號，`SPLIT:123:…` 第 9 個字元是 `3` 不是 `:`；id 只含數字，沒有 `_`／`%` 萬用字元。

### Cited Findings
- 查詢 — [D:98-100](app/src/main/java/com/enwei/moneymanager/data/Daos.kt)；呼叫 — [R:751](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)（`"SPLIT:${t.id}"`, `"SPLIT:${t.id}:%"`）。
- 舊格式 `SPLIT:<主id>`（無對象）以精確比對處理；`ADV:` 開頭的不會被任何主單的 splitsOf 找到（設計如此）。

### Inferences
- 效能（P3）：SQLite 預設 LIKE 不分大小寫，無法使用 externalKey 的唯一索引 → 每次 `splitsOf` 全表掃描；`deleteTxn` 每刪一筆、BatchSplit 每筆、通知巨集判斷 `sameFromOther` 對每筆附近交易（[R:1549-1550](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）都會呼叫。幾千筆內影響不大；可改 `externalKey >= 'SPLIT:12:' AND externalKey < 'SPLIT:12;'` 走索引。
