## Q2. TxnNotificationListener：recentKeys 去重、enqueue／process、requestRebind、textOf

### Takeaway
`recentKeys` 以 `sbn.key → 標題\0內文` 判斷「同一則通知更新且內容沒變」，只存在記憶體，執行緒同步沒有問題。但它沒有時間上限、不寫紀錄，也會收進所有 App 的通知。遇到「固定通知 id、內文不含時間或餘額」的 App 時，第二筆真實消費會被無聲吞掉。enqueue／process、requestRebind、textOf 都沒有改。

### Cited Findings
- 新邏輯：`sig = "$title\u0000$text"`，在 `synchronized(recentKeys)` 內比對 `recentKeys[sbn.key] == sig` 就 `return`，否則寫入，超過 300 筆就移除最早插入的鍵（L:83-89、L:92）。
- 這段放在 `featureNotif` 檢查與 `textOf` 之後、`enqueue` 之前，**不分 App**：LINE 聊天、其他 App 的通知也會佔用 300 個名額（L:79-90）。
- 略過時沒有寫任何 `notificationLog`（L:86）。
- 重新連線時的補讀不經過 `recentKeys`，仍用 `countSame(..., sbn.postTime - 60_000) == 0` 判斷（L:41-43）。
- `countSame` 的 SQL 是 `postedAt > :since`，**沒有上限**（D:278-279）。
- `enqueue`、`process`、`onDestroy` 清空 `pendingNotes` 都沒有改（L:94-139、L:55-60）。`requestRebind` 只在 `onListenerDisconnected` 呼叫（L:52）。`textOf` 仍取 `BIG_TEXT ?: TEXT`，兩者都沒有才讀 lines 或 ticker（L:66-76）。

### Inferences
- **執行緒安全**：`onNotificationPosted` 在主執行緒執行，存取都包在 `synchronized(recentKeys)` 內，沒有競態。`LinkedHashMap` 採插入順序，重新 put 既有鍵不會改變順序，`keys.first()` 移除的是最早插入的那筆，正確。宣告在使用處之後（L:92）不影響初始化順序。
- **只存在記憶體**：服務重建（`onDestroy`，例如省電機制殺掉或使用者重開權限）或程序重啟後 `recentKeys` 會清空。之後若 App 再更新同一則、內容相同的通知，就會重新處理一次：`countSame(postedAt-1)` 因為 postTime 不同而攔不到（推論）。有寫時間的會被 externalKey 判成 DUPLICATE（安全）；沒寫時間的變成待確認的重複一筆（sameText／secondSame）。補讀進來的通知也沒有寫入 `recentKeys`，有同樣情況。
- **和補讀的交互**：補讀仍用 60 秒視窗，語意和新的「只略過同一則」不一致。斷線期間 60 秒內兩筆同額同內文消費，若第一則已經記錄，第二則在補讀時會被無聲略過（見 N5）。
- 300 筆上限由所有 App 共用，群組聊天大量通知時，銀行那則的鍵幾分鐘內就可能被擠掉，之後的更新又會被重新處理（P3）。

### Gaps
- 沒有實機確認 `activeNotifications` 的排序（推論依重要性與時間由新到舊），這會影響 N5 的發生機率。

## Q3. Repository.ingestNotification 的變更是否正確

### Takeaway
`recordAnyway`、`countSame(postedAt-1)`、sameText 改成待確認、要求雙方都有秒數的 distinct、巨集的 sameFromOther，以及 findDuplicates 略過同 App 不同內文，各自的方向都對，但都有破口。sameText 不影響提早 return 的路徑。sameFromOther 讓出巨集後，nearby 對不到「主支出＋代墊」。distinct 的正規式會被卡號末四碼騙過。countSame 沒有上限。

### Cited Findings
- `recordAnyway` 參數在 R:1350-1351，同時略過 countSame（R:1363）、externalKey（R:1473）、sameText（R:1481）、nearby（R:1510）。沒有略過的有：股利重複（R:1484-1492）、交割款（R:1391-1396）、巨集分支（R:1549-1563）、往來還款（R:1566-1577）。
- sameText：`!recordAnyway && between(occurred±rawWindow).any { rawText.contains(raw0) }`；有交易時間才 DUPLICATE（R:1478-1482）。沒有時間時，只在最後的 `unsure` 清單把狀態改成待確認（R:1827、R:1831）。但 `unsure` 只取第一個成立的原因，「沒有分類」等原因排在前面時，附註不會寫「內容相同」，狀態仍是待確認。
- 提早 return 而不經過 `unsure`／`finalStatus` 的路徑：巨集（R:1557-1562）、往來（R:1568-1575，`sure` 只看 named、account、status）、提款（R:1579-1585，完全不看 nearby）、儲值（R:1586-1623）、轉帳配對（R:1624-1649）、卡費（R:1650-1675）。
- sameFromOther：`s.macros.any { it.fromNotif } && between(occurred±180_000).any { source == NOTIFICATION && (amount == p.amountMinor || splitsOf(it).sum + it.amount == p.amountMinor) }`（R:1549-1550）。`splitsOf` 現在是單一 `externalKey = ? OR LIKE ?` 查詢（R:750-752、D:98-100），只在金額不相等時才查（`||` 短路），每則通知最多查 6 分鐘內的幾筆，成本可以忽略。
- nearby 只收 `source == NOTIFICATION && amount == p.amountMinor`（R:1510-1512），後面比對還要求 `it.type == type`（R:1716）。
- hitStep 與 runMacro 的 hit 都改成同時比金額和收支方向（R:1557、R:858），並把 `type` 傳進 base（R:1558-1559），兩邊選出的是同一步。
- distinct：`exactTime && o.externalKey.startsWith("N:") && Regex("""T\d{2}:\d{2}:\d{2}""").containsMatchIn(o.externalKey) && |Δ| >= 1000`（R:1714-1715）。externalKey 的格式是 `"N:$sign${amount}:${it.withNano(0)}:${p.cardLast4 ?: pkg}"`（R:1473）。
- findDuplicates 的略過條件在 R:581-586。`byTxn` 是 `ORDER BY postedAt DESC LIMIT 1`（D:263-264）。
- 紀錄頁的點擊處理在 M:676-683：`recordAnyway = e.result == "DUPLICATE" || gone`；成功後 `Undo.show { repo.deleteTxn(id) }`；原列沒有更新。

### Inferences
- `countSame(postedAt-1)` 的本意是「只比對同一個 postedAt」，但 SQL 沒有上限，實際比對的是「postedAt ≥ 本則」的所有紀錄。正常依序處理時沒有影響；亂序處理時（例如補讀時新的先處理），舊的那則會被更晚的相同內容無聲吞掉。應改成 `postedAt = :postedAt`（N5）。
- 「巨集與 sameFromOther 是否會漏掉其他路徑記下的同一筆」：只看 `source == NOTIFICATION`。同一筆先由錢包畫面（SCREEN）或手動記下，巨集照樣執行（P3）。sameFromOther 也不分收支方向與 App，3 分鐘內有任何同額通知交易（例如入帳）就不跑巨集，改記成一般交易（P3）。
- findDuplicates 的 `byTxn` 對已合併的交易（銀行＋LINE 兩列紀錄）只回傳最新那列的 App，判斷「同一個 App」可能失準。失準的方向是「不略過」，也就是仍交給 AI 判斷（P3）。

### Gaps
- 沒有追 `absorbIntoAutopay`、`resolveAccount` 在 `recordAnyway` 下的行為。

## Q4. 放寬去重之後，同一筆真實消費會不會被記兩次

### Takeaway
會，而且比修正前多了幾種直接記成「已確認」的情況。最主要的是：沒寫時間的通知重送超過 3 分鐘時，巨集會整套再跑一次；提款、卡費、具名還款也會再記一筆已確認的交易。巨集代墊的情境下，銀行加 LINE Pay 雙通知會多出一筆全額支出。卡號末四碼讓錢包加銀行的組合仍可能記兩筆。

### Cited Findings
- 修正前，沒寫時間的通知 30 分鐘內內文相同就是 DUPLICATE（13f77df R:1443-1448，見 diff）；HEAD 改成只有寫了時間才判 DUPLICATE（R:1482）。
- 巨集分支沒有檢查 sameText（R:1549-1563），sameFromOther 的視窗只有 ±3 分鐘（R:1550）。
- 提款分支直接 `insert(base.copy(...))`，status 沿用 base（R:1581-1584）。
- 巨集代墊的主支出金額是 `own`（R:777），代墊轉帳的 source 是 MANUAL（R:783）。

### Inferences（逐一情境）
- **銀行用新的 sbn.key 和新的 postTime 重送同一則**：有寫時間時，externalKey 或 sameText 判成 DUPLICATE，安全。沒寫時間時：10 分鐘內同 App 會走 secondSame，記成待確認；10～30 分鐘走 sameText，也記成待確認；但若這則命中巨集、提款、卡費或具名還款，就直接記成**已確認**的第二筆（N2）。超過 30 分鐘時，修正前後都會記成新的一筆（不是回歸）。
- **App 重啟重新送達**：補讀以紀錄判斷，已經寫過紀錄的會略過，不會重記。服務重建後 App 再更新同一則通知，則會重處理（見 Q2，沒寫時間時記成待確認的重複，推論）。
- **同一段文字、沒寫時間、10 分鐘後又到**：設計上就是待確認的第二筆（R:1827）。但若這則會觸發巨集，巨集整套再跑一次，全部已確認（N2）。
- **LINE 錢包＋銀行**：錢包只到分鐘、銀行到秒時，已改為合併。銀行只到分鐘且帶末四碼時，key 被誤認為有秒數，錢包若寫到秒就記兩筆（N4）。兩邊都寫到秒、相差 ≥1 秒時，仍記兩筆（20 號的剩餘部分）。巨集代墊情境下，第二個 App 的通知會多記一筆全額支出（N3）。

### Gaps
- 不知道實際銀行與錢包通知寫不寫秒數、多常重送，所以機率無法量化。

## Q5. 巨集：設定保存、MacroDraft、幣別、說明欄與其餘項目

### Takeaway
保存已修正，幣別可以存、執行、顯示，旋轉不再覆蓋草稿。但程序被殺時草稿仍會遺失；說明欄是隱藏而不是保存；分帳金額的顯示仍用主幣別；報告列的 P2 項目一項都沒處理。

### Cited Findings
- `loaded` 的邏輯在 MS:169-170：`if (!loaded || d.forId != id) { if (!loaded || d.forId == null) d.load(id, orig); loaded = true; d.returning = false }`。存檔、返回、刪除時把 `d.forId = null` 再 `popBackStack`（MS:179、184、190）。
- 帶入步驟時先 `if (st.currency.isNotBlank()) currency = st.currency`（E:222）；寫回時用 `step.copy(currency = t0.currency)`（E:530）。
- 執行時，非命中步驟用 `st.currency.ifBlank { base }`（R:862），命中步驟沿用通知幣別（R:861）。
- 步驟摘要用步驟自己的幣別（MS:72），但分帳列（MS:124、MS:209）與「你的支出」仍用 `base`。
- 說明欄在巨集模式隱藏（E:939-940）；說明推薦只在 `noteFocused` 時出現，巨集模式下不會出現（E:944）。

### Inferences
- **旋轉**：`loaded` 由 `rememberSaveable` 還原成 true，`MacroDraft` 是同一個程序裡的全域物件，`forId == id`，不會重新載入。已修正。
- **程序被殺**：`loaded` 還原成 true，`forId` 是 null，所以 `load(id, orig)` 回到已儲存版本，改到一半的內容遺失（比修正前清空好，但仍會遺失）。在步驟編輯頁被殺時，`editIndex = -1`，`put` 會把步驟加進空草稿，返回後又被 `load` 清掉。
- **離開頁面的動畫**：`d.forId = null` 之後，退場動畫期間這個 composable 還會重組，條件成立就會呼叫 `d.load(id, orig)`，在組合期間寫入快照狀態。結果只是把全域草稿重設成舊版本，下次進入會重新載入，目前無害，但屬於組合中的副作用（P3）。
- **步驟幣別**：命中判斷不比幣別（R:858、R:1554），USD 100 的步驟可能被 TWD 100 的通知命中（低機率，P3）。

### Gaps
- 沒有確認底部分頁切換時 NavHost 是否 `saveState`。若沒有，`macro/` 不在 `EDITOR_PREFIXES`，草稿仍會被重新載入。

## Q6. 0e3ff7a／5d3a863 新引入的問題（依嚴重度）

### Takeaway
新引入 4 項 P1：通知編號去重無聲吞掉第二筆、sameText 只在最後一條路徑生效、巨集讓出後無法合併、distinct 正規式誤判。另有 2 項 P2 與數項 P3。修法多半只要改一兩行。

### Cited Findings
- **N1｜P1｜L:83-89**：同一個 `sbn.key`、同內容的通知，在服務存活期間**永遠**無聲略過，沒有時間上限，也不寫紀錄。
  - 重現（推論，取決於 App）：某銀行或支付 App 用固定的通知 id，內文不含時間與餘額。8:00 在同一家店付 NT$50，15:00 又付 NT$50，第二則通知取代第一則、內容完全相同，被 `recentKeys` 擋下。
  - 影響：第二筆消費沒有記帳，通知紀錄頁也找不到，正是報告第 7 項的「消失」。
  - 修法：記下上次的 `postTime`，只有間隔 ≤ 數秒（例如 5 秒）才略過；或略過時寫一列 DUPLICATE（原因：「同一則通知更新」），讓紀錄頁可以救回。
- **N2｜P1｜R:1481-1482、R:1549-1563、R:1566-1585、R:1650-1675**：sameText（沒寫時間、內文相同）不再判成 DUPLICATE，但只在最後一條一般路徑改成待確認；巨集、提款、卡費、具名還款等提早 return 的路徑照樣寫入已確認的交易。
  - 重現：房租巨集開啟通知自動套用，銀行通知「轉帳 NT$25,500 成功」沒寫時間；10 分鐘後同一則以新的通知 id 重送，巨集整套再跑一次（主支出、兩筆代墊全部已確認）。修正前會被 30 分鐘 rawText 視窗擋下。提款通知重送同樣會多一筆已確認的「提款」。
  - 影響：重複記帳，往來欠款重複，而且不在待確認裡，不容易發現。
  - 修法：sameText 為真時，巨集分支直接跳過（或記一列 DUPLICATE），其他提早 return 的路徑一律把 status 改成 PENDING；或把 sameText 和 nearby 的判斷移到所有分支之前。
- **N3｜P1｜R:1549-1551 配合 R:1510-1512、R:777**：sameFromOther 讓出巨集、「交給下面合併」，但巨集命中的那一步若有代墊，主支出金額是 own（例如 8,500），nearby 要求 `amount == 25,500`，對不到；own==0 時則是 TRANSFER，`type` 也不符。
  - 重現：房租 25,500，A 欠 9,500、B 欠 7,500 的巨集。銀行通知先觸發巨集；1 分鐘後 LINE Pay 也通知 25,500，sameFromOther 為真，跳過巨集，走一般路徑，新記一筆 25,500 支出（有帳戶證據時直接確認）。
  - 影響：支出多算 25,500。修正前是巨集跑兩次；現在錯法不同，但仍然重複。
  - 修法：sameFromOther 命中時，直接寫一列 DUPLICATE 或 MERGED（指向那筆主支出）並 return，不要往下走一般路徑。
- **N4｜P1｜R:1714-1715 配合 R:1473**：判斷對方有沒有秒數的正規式 `T\d{2}:\d{2}:\d{2}` 會匹配到「分鐘:卡號末四碼」。例如 `N:-12000:2026-11-21T12:30:1234` 會被當成 `T12:30:12`。另外 `LocalDateTime.toString()` 在秒數為 0 時省略 `:00`，真正到秒、但剛好 00 秒的鍵反而會被當成只到分鐘。
  - 重現：信用卡通知「末四碼1234 11/21 12:30 消費 NT$120」先記（只到分鐘）；接著支付 App 通知「12:30:42 付款 NT$120」。exactTime 為真，distinct 為真，記成兩筆。
  - 影響：同一筆消費記兩次，第二筆可能直接確認，因為不是 secondSame。
  - 修法：不要從字串推斷，在交易上另存「時間精度」，或用 `p.occurredAt.second != 0 || 原文有 hh:mm:ss`，在寫入時把精度編進 key（例如 `N:...:S:` 和 `N:...:M:` 前綴）；並加上「同一 App」條件。
- **N5｜P2｜D:278-279、R:1363、L:43**：`countSame` 只有下界。新的 `postedAt - 1` 想表示「同一則」，實際上變成「本則或更晚的相同內容」。補讀仍用 60 秒視窗。
  - 重現（推論）：服務斷線期間 30 秒內兩筆同額同店消費，各一則通知，內容相同、id 不同。重新連線補讀時，若新的那則先處理（`activeNotifications` 推論由新到舊），舊的那則因為 `countSame(舊 postedAt-1)` 看到新的那列而無聲 `return null`；或第一則已記錄時，第二則在補讀階段就被 60 秒視窗略過。
  - 影響：漏記一筆，而且沒有紀錄。
  - 修法：DAO 改成 `postedAt = :postedAt`（或 `BETWEEN :p AND :p`）；補讀改用同一個判斷，並先依 postTime 由舊到新排序。
- **N6｜P2｜M:673-683**：`recordAnyway` 略過所有去重，但原本那列 DUPLICATE 或「交易已刪除」不會更新，整列點擊沒有確認、沒有防連點。每點一次就多記一筆，快速連點兩次會記兩筆，而 `Undo` 只保留最後一次。之後的 AI 自動整理會把這筆「仍要記帳」的交易和內文相同的原交易配對（R:581-586 只略過內文不同的），AI 可能再把它合併刪掉，因為沒有寫入 `dupDismissed`。
  - 修法：記下後把原列 `setResult(e.id, "RECORDED")` 並寫入 txnId；動作改成展開後的按鈕加確認；成功後把這組配對加進 `dupDismissed`。
- **N7｜P3｜L:79-92**：`recentKeys` 收進所有 App 的通知，300 個名額可能被聊天通知擠掉，之後同一則銀行通知更新時會被重新處理（沒寫時間時變成待確認的重複）。修法：只對已啟用的來源寫入，或改用依時間過期的快取。
- **N8｜P3｜MS:124、MS:209、MS:226 一帶**：步驟摘要用步驟幣別（MS:72），但分帳列「A 欠你 …・你的支出 …」與「通知金額為 …」仍用主幣別符號。USD 步驟會顯示「USD 100」加上「A 欠你 NT$30」。修法：一律用 `st.currency.ifBlank { base }`。
- **N9｜P3｜MS:169-170**：在組合期間呼叫 `d.load`，會寫入快照狀態；退場動畫期間會重設全域草稿（目前無害）。修法：改成 `LaunchedEffect(id)`，或用 `remember(id)` 包住並只在 `!loaded` 時載入。
- **N10｜P3｜R:1549-1550**：sameFromOther 不分收支方向、App、幣別，也忽略 SCREEN 或 MANUAL 來源。3 分鐘內有任何同額通知交易就不跑巨集；同一筆若先由錢包畫面記下，巨集照跑。

### Inferences
- N1 與 N5 會讓報告第 7 項的「消失、而且看不到紀錄」以新的形式重現；N2、N3、N4 會讓報告的「記兩次」在巨集和跨 App 情境下持續發生。建議先補三個 Repository 層的測試：(1) 同內文、無時間、間隔 10 分鐘、命中巨集的第二則不會再跑巨集；(2) 巨集代墊加第二個 App 同額通知，總支出不變；(3) 「12:30」加末四碼的卡片通知，再加「12:30:42」的錢包通知，只產生一筆。

### Gaps
- N1、N5 的實際發生率取決於各 App 的通知 id 策略與系統排序，沒有實機驗證，嚴重度依推論評定。
