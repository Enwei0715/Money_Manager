# 資安與隱私合規（帳理 Ledgerly）

> 研究範圍：/home/user/Money_Manager（commit 1cdba40）原始碼為主，輔以 Android／Google Play／OSM 官方說明與台灣個資法資料。
> 程式碼出處以 `檔案:行號` 表示（相對於 repo 根目錄；`…/moneymanager/` = `app/src/main/java/com/enwei/moneymanager/`）。
> 限制：本次雲端環境無法連到 support.google.com 與 law.moj.gov.tw，政策與法條內容來自搜尋摘要與官方頁面網址，未能逐字核對全文（見各節 Gaps）。

## 一、敏感資料處理（金鑰、密碼、生物辨識、Room、備份、Log、閃退檔）

### Takeaway
所有敏感資料都以「明文」存在 App 私有空間：AI／地圖金鑰與 GitHub Token 放在一般 SharedPreferences、Room 資料庫未加密、4 位數 PIN 用「固定鹽 + 單次 SHA-256」雜湊（可瞬間暴力破解），而且這個雜湊會被寫進備份檔；`.lgbak` 備份是未加密的 gzip JSON，含全部交易、帳戶、通知原文與定位；`allowBackup="true"` 又沒有 dataExtractionRules，金鑰會跟著 Google 雲端備份／換機搬移。正面：完整備份刻意排除了金鑰與 Token、Log 只有 3 處且不含個資。

### Cited Findings
**API 金鑰與 Token**
- Groq／Gemini 金鑰（含多把備援 `groqKeysExtra`/`geminiKeysExtra`）與 `githubToken` 以 `getSharedPreferences("settings", MODE_PRIVATE)` 明文存取 — `…/moneymanager/data/Settings.kt:468`、`:596-599`、`:794-797`
- Google Places 金鑰明文存在 `gplaces` prefs — `…/moneymanager/net/GooglePlaces.kt:21-25`；Mapbox token 存在 `mapbox` prefs — `…/moneymanager/net/Mapbox.kt:17`；自架 AI 伺服器網址存在 `local_ai` prefs — `…/moneymanager/net/LocalAi.kt:22`
- 全專案沒有使用 EncryptedSharedPreferences／Android Keystore／SQLCipher（以 grep `Encrypted|KeyStore|SQLCipher` 無結果）— repo 全文搜尋
- 金鑰傳輸方式正確：Gemini 用 `x-goog-api-key` header、Groq 用 `Authorization: Bearer` — `…/moneymanager/net/GroqAi.kt:376`、`:492`；Places 用 `X-Goog-Api-Key` header — `…/moneymanager/net/GooglePlaces.kt:52`；但 Mapbox token 放在 URL query（`access_token=`）— `…/moneymanager/net/Mapbox.kt:102`（Mapbox 公開 token 本來就設計為放 URL，風險較低，但會出現在代理／伺服器 log）
- 完整備份與設定匯出刻意排除金鑰：`exportRaw()` 過濾 `githubToken, groqKey, geminiKey, groqKeysExtra, geminiKeysExtra, openRouterKey, nvidiaKey, autoBackupUri…` — `…/moneymanager/data/Settings.kt:664-666`；FullBackup 說明「不含 GitHub Token 與各種 API 金鑰」、「金鑰類的 mapbox、gplaces 只存在手機，不備份」— `…/moneymanager/data/FullBackup.kt:15`、`:49`
- Android 官方建議：敏感儲存資料應依密碼學指引加密，並用 Android Keystore 保護金鑰 — [Android Developers: Backup best practices](https://developer.android.com/privacy-and-security/risks/backup-best-practices)

**密碼鎖（passcode）**
- `hashPasscode(pin) = SHA-256("mm-salt:$pin")`：所有使用者共用固定字串鹽、單次雜湊、無迭代 — `…/moneymanager/data/Settings.kt:464-465`
- PIN 固定 4 位數（10,000 種組合）— `…/moneymanager/ui/screens/ConfigScreens.kt:467-472`、`:483-490`
- 輸錯沒有次數限制或延遲，只是清空重來 — `…/moneymanager/ui/screens/ConfigScreens.kt:472`
- `passcodeHash` 存在 `settings` prefs（`Settings.kt:539`、`:740`），且**不在** `exportRaw()` 的排除名單（`Settings.kt:666`）→ 會被寫進 `.lgbak` 備份；還原時 `importRaw` 會用備份檔的值覆蓋（`Settings.kt:683-707`）
- 密碼鎖只是 UI 層：`MainActivity` 依 `passcodeHash` 顯示 `LockScreen`，離開超過 `lockDelaySec` 才重新上鎖 — `…/moneymanager/ui/MainActivity.kt:137`、`:190-199`；資料本身未以 PIN 衍生金鑰加密
- 全專案沒有 `FLAG_SECURE`（grep 無結果）→ 最近使用畫面縮圖、截圖、螢幕錄影都看得到金額

**生物辨識**
- 使用 `BiometricPrompt`，允許 `BIOMETRIC_WEAK`（Class 2），沒有綁 `CryptoObject` — `…/moneymanager/ui/screens/ConfigScreens.kt:635-654`。即純 UI 閘門，非 Keystore 加密解鎖

**Room 資料庫**
- `Room.databaseBuilder(context, AppDatabase::class.java, "money.db")` 未設定 `openHelperFactory`（無 SQLCipher）— `…/moneymanager/data/AppDatabase.kt:31`
- `notification_log` 表保存通知原文（packageName、title、text、postedAt）— `…/moneymanager/data/Entities.kt:186-197`；`ingestNotification` 中凡 `enabled` 的通知（含 PROMO、DUPLICATE、SETTLE 等）都會寫入 — `…/moneymanager/data/Repository.kt:1072-1078`、`:1088`

**備份**
- `.lgbak` = 「gzip 壓縮的 JSON，包含所有資料表與所有設定」，含店家位置、記帳定位 — `…/moneymanager/data/FullBackup.kt:12-16`、`:31-37`；匯出內容含 accounts、transactions、trades、rules、**notificationLog** — `FullBackup.kt:93-105`；程式中無任何加密或密碼（grep `encrypt|Cipher|password` 於 FullBackup/BackupWorker/MmbakIO 無結果）
- `BackupWorker` 每 12 小時檢查，到期就把整份備份以 `openOutputStream(Uri.parse(autoBackupUri), "wt")` 寫到使用者選的 SAF 資料夾（可能是 Google Drive、Downloads、SD 卡）— `…/moneymanager/work/BackupWorker.kt:22-31`、`:43-45`
- Manifest `android:allowBackup="true"`，沒有 `android:dataExtractionRules`／`fullBackupContent` — `app/src/main/AndroidManifest.xml:24`。因此 Auto Backup 會把 `money.db` 與所有 prefs（含 API 金鑰、GitHub Token）上傳到使用者的 Google 雲端備份並在換機時搬移
- Android 官方：若 App 處理敏感資訊可考慮停用備份；Android 12+ 用 `dataExtractionRules` 指定內容；高度敏感資料應排除或要求端對端加密；Android 9 起標準備份在傳輸與儲存時加密；Android 12+ 即使 `allowBackup=false` 仍允許裝置對裝置傳輸 — [Android Developers: Backup best practices](https://developer.android.com/privacy-and-security/risks/backup-best-practices)、[Auto Backup](https://developer.android.com/training/backup/autosyncapi.html)
- 靜態掃描工具（OWASP MASTG、SonarSource RSPEC-6358）都會把 `allowBackup="true"` 列為發現項 — [OWASP MASTG-DEMO-0034](https://mas.owasp.org/MASTG/demos/android/MASVS-STORAGE/MASTG-DEMO-0034/MASTG-DEMO-0034)、[RSPEC-6358](https://rules.sonarsource.com/xml/type/Security%20Hotspot/RSPEC-6358)

**Log 與閃退檔**
- 全專案僅 3 處 `android.util.Log`：`MoneyApp` 背景例外、通知批次失敗、新聞更新失敗，只記例外不記通知內容 — `…/moneymanager/MoneyApp.kt:29`、`…/moneymanager/notify/TxnNotificationListener.kt:75`、`…/moneymanager/work/NewsWorker.kt:75`。但 `Log.e(tag, msg, e)` 會印出 stack trace，若例外訊息內含通知文字仍可能外洩（未發現實例）
- 閃退處理：寫入 `filesDir/CRASH_FILE`，內容為版本、Android 版本、時間、執行緒名、stack trace（截 6000 字），下次開啟以對話框顯示並可複製 — `…/moneymanager/MoneyApp.kt:35-45`、`…/moneymanager/ui/MainActivity.kt:162`、`:492-510`。存於私有目錄、由使用者主動複製，風險低

### Inferences
- **PIN 雜湊等於明文**：固定鹽 + 4 位數 + 單次 SHA-256，拿到 `.lgbak` 或 prefs 的人可在毫秒內窮舉 10,000 組還原 PIN；許多人 PIN 與手機或提款卡密碼重複，外洩傷害超出本 App。建議：改用 PBKDF2/Argon2（每裝置隨機鹽、高迭代）、PIN 至少 6 位、連續錯誤遞增延遲，並把 `passcodeHash` 加入 `exportRaw()` 排除名單。
- **備份檔是最大的外洩面**：使用者選 Google Drive／共享資料夾作自動備份目的地時，完整財務資料＋通知原文＋定位軌跡以明文存放在雲端。建議：`.lgbak` 支援以使用者密碼做 AES-GCM 加密（PBKDF2 衍生金鑰），自動備份預設加密。
- **allowBackup**：建議新增 `dataExtractionRules`（cloud-backup 與 device-transfer 都排除 `settings.xml` 中金鑰、`gplaces.xml`、`mapbox.xml`），或把金鑰移到 Keystore 加密儲存（Keystore 金鑰不會被備份，還原後自然失效）。
- 加入 `FLAG_SECURE`（可做成設定項，預設在開啟密碼鎖時啟用）避免最近使用畫面露出餘額。
- Room 加密（SQLCipher）為中長期選項；以本機私有儲存 + Android 檔案加密，對一般威脅已足，優先順序低於 PIN 與備份。

### Gaps
- 未實機驗證 Auto Backup 是否真的上傳了 prefs（取決於使用者是否開啟 Google 備份）。
- `MainActivity` 為 exported 且接受 `EXTRA_ROUTE`，未完整檢查外部 Intent 帶 route 是否會在鎖定畫面前導航（初步看鎖定是全域 state，但未逐行驗證）。

## 二、權限與敏感能力（通知監聽、背景定位、Shizuku、無障礙、匯出元件、PendingIntent、debug receiver）

### Takeaway
權限面整體設計合理（元件大多 `exported=false`、PendingIntent 多數 IMMUTABLE、debug receiver 只在 debug source set），但有三個合規地雷：(1) 背景定位用於「通知到來時順便定位猜店家」，在 Play 很難被認定為核心功能；(2) Shizuku 一鍵 `appops set … RECEIVE_SENSITIVE_NOTIFICATIONS allow` 是在繞過 Android 15 的 OTP 通知保護；(3) 無障礙服務 `WalletScreenReader` 已從 Manifest 移除，但程式碼、設定字串、`wallet_reader.xml` 與隱私權政策仍在描述它。

### Cited Findings
**通知監聽**
- `TxnNotificationListener` exported=true，但受 `BIND_NOTIFICATION_LISTENER_SERVICE` 保護（標準做法）— `app/src/main/AndroidManifest.xml:48-56`
- Listener 本身只檢查 `featureNotif` 開關，**所有 App** 的通知（自己除外）都會被讀進記憶體批次 — `…/moneymanager/notify/TxnNotificationListener.kt:48-61`；過濾在 Repository：`notifPackages` 勾選的、LINE 且看起來像 LINE Pay 的、或來源銀行名稱能對上使用者帳戶名稱的（**不必勾選**）— `…/moneymanager/data/Repository.kt:1035-1037`、`:1069-1071`（註解：「來源 App 是你有帳戶的銀行…不用另外勾選」）
- 揭露對話框寫「其他 App 的通知不會被讀取或保存」— `…/moneymanager/ui/components/AccessDisclosure.kt:23-26`；有「同意／不同意」按鈕才跳系統設定 — `AccessDisclosure.kt:41-42`、`…/moneymanager/ui/screens/MoreScreens.kt:416-419`

**背景定位**
- Manifest 宣告 `ACCESS_COARSE/FINE/BACKGROUND_LOCATION` — `app/src/main/AndroidManifest.xml:8-10`
- 實際用途：收到「剛跳出（10 分鐘內）」的付款通知且開啟 `locationHints` 時，在背景取得目前位置猜店家並記錄交易定位 — `…/moneymanager/data/Repository.kt:1398-1403`、`:1457`；`hasBackground()` 判斷 — `…/moneymanager/data/PlaceHints.kt:345-346`；設定頁顯示「背景位置：一律允許／未設為一律允許（App 沒開著時讀不到）」— `…/moneymanager/ui/screens/MoreScreens.kt:1223`
- `AccessDisclosure` 只有通知（kind 0）與無障礙（kind 1）兩種，沒有定位的顯著揭露（grep「位置/定位」於該檔無結果）— `…/moneymanager/ui/components/AccessDisclosure.kt:22-31`
- Google Play 背景定位：只允許核心功能所需；送審需權限聲明表、示範影片、App 內顯著揭露（需在系統權限提示前，且要出現在影片中）、App 內與商店頁的隱私權政策 — [Android Developers: Access location in the background](https://developer.android.com/training/location/background)、[Radar: Play Store background location approval guide](https://radar.com/blog/guide-to-play-store-background-location-approval)（第三方整理）

**Shizuku 與敏感通知**
- `ShizukuProvider` exported=true，受 `INTERACT_ACROSS_USERS_FULL`（signature 級）保護，為 Shizuku 官方建議設定 — `app/src/main/AndroidManifest.xml:150-156`
- 以反射呼叫非公開 `Shizuku.newProcess` 執行 `appops set com.enwei.moneymanager RECEIVE_SENSITIVE_NOTIFICATIONS allow` — `…/moneymanager/net/ShizukuHelper.kt:16`、`:43-48`
- App 自己說明：「Android 15 起，系統判斷含驗證碼（OTP）的通知會對第三方 App 隱藏內容…可在電腦用 adb 執行下方指令開放」— `…/moneymanager/data/Repository.kt:755-756`

**無障礙服務（WalletScreenReader）**
- `WalletScreenReader : AccessibilityService` 程式碼仍在 — `…/moneymanager/notify/WalletScreenReader.kt:23`；`wallet_reader.xml` 設定 `canRetrieveWindowContent=true`、`flagIncludeNotImportantViews`，無 `isAccessibilityTool` — `app/src/main/res/xml/wallet_reader.xml:2-8`
- 目前 main／debug／github 三個 Manifest 都**沒有**註冊此 service（grep 無結果），commit `beb1eba` 訊息為「remove wallet reader」— `git log` 輸出
- Google Play：非輔助工具（未宣告 isAccessibilityTool）須有獨立顯著揭露與肯定同意，不可只靠 service description 字串；建議改用範圍更窄的 API — [Play Console Help: AccessibilityService API](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)、[Policy preview](https://support.google.com/googleplay/android-developer/answer/13986130)

**匯出元件與 PendingIntent**
- `QuickActions$TxnActionReceiver` 與 6 個 Widget receiver 皆 `exported=false`；FileProvider `exported=false`、只開放 `cache/updates/` 與 `cache/photos/` — `app/src/main/AndroidManifest.xml:33-35`、`:59-139`、`:140-148`；`app/src/main/res/xml/file_paths.xml`
- `MainActivity` exported=true（launcher，必要）— `AndroidManifest.xml:37-46`
- 通知「輸入說明」PendingIntent 用 `FLAG_MUTABLE`（RemoteInput 必須可變），Intent 為明確指定 `TxnActionReceiver` 類別 — `…/moneymanager/notify/QuickActions.kt:85-89`；分類按鈕用 `FLAG_IMMUTABLE` — `QuickActions.kt:96-100`
- Android 平台規定以 RemoteInput 回覆的 PendingIntent 需 mutable；明確 Intent 可避免被攔截改寫（一般 Android 安全建議；本次未取得官方頁面全文）

**Debug receiver**
- `DebugHooks` exported=true、可灌假資料與模擬通知，只存在 `app/src/debug/`，註解「正式版不含」— `app/src/debug/AndroidManifest.xml:1-12`、`app/src/debug/java/com/enwei/moneymanager/DebugHooks.kt:21-37`。CI 只建 `assembleGithubRelease` 與 `bundlePlayRelease` — `.github/workflows/android.yml:73-74`，因此不會出貨

**`<queries>`**
- 以 MAIN/LAUNCHER intent 查詢已安裝 App，用途為讓使用者勾選銀行 App — `app/src/main/AndroidManifest.xml:14-19`（不需 QUERY_ALL_PACKAGES，屬合規做法）

### Inferences
- 通知揭露文字與實作不一致：所有通知都會進入程式處理（雖未保存）、LINE 與「名稱對得上帳戶的銀行 App」不需勾選即會被處理與記錄。建議揭露改為「會檢查所有通知是否來自銀行／支付 App，只保存勾選或與你帳戶相符的」，或讓未勾選 App 一律在 listener 層直接丟棄。
- 背景定位在 Play 送審風險高：「猜店家」屬便利功能，審查常認定可改成前景定位。建議 Play 版移除 `ACCESS_BACKGROUND_LOCATION`（僅 github 版保留），或改為使用者點通知時（前景）再補定位；若保留，必須補定位專用顯著揭露、影片與聲明表。
- Shizuku 解除 OTP 保護：雖需使用者主動、但等於讓 App 讀到銀行 OTP；結合 AI 傳送（第三節）有 OTP 外流風險。建議 Play 版移除此功能；github 版加上明確警告，並確保 OTP 類文字不送 AI、不寫入 notification_log。
- WalletScreenReader 為死碼：建議刪除 `WalletScreenReader.kt`、`WalletScreenAiWorker.kt`、`wallet_reader.xml` 與相關字串，並同步修正隱私權政策；若未來恢復，Play 送審需無障礙聲明且極可能被拒（非輔助工具用途）。

### Gaps
- 無法連到 Play 政策原文，無法確認 2026 年版本對通知監聽（Notification Listener）是否另有聲明表要求；目前 Play 對 `BIND_NOTIFICATION_LISTENER_SERVICE` 未列在權限聲明表清單（依個人知識，未經本次來源驗證）。
- 未檢查 `Setup.kt:154` 是否一次同時請求前景與背景定位（Android 11+ 需分兩步）。

## 三、傳送給第三方的資料與網路安全設定

### Takeaway
App 會把相當完整的財務資料傳給使用者自選的 AI（Groq／Gemini／自架 Ollama）：無法解析的通知原文、交易明細、持股股數均價損益、現金餘額；把即時 GPS 座標傳給 Google Places／Mapbox／Nominatim／Photon／Overpass；這些在隱私權政策中大部分沒寫。全 App `cleartextTrafficPermitted="true"`，只為了讓區網 Ollama 用 http。

### Cited Findings
**AI 提供者**
- AI 端點：`api.groq.com`、`generativelanguage.googleapis.com`、自架 Ollama — `…/moneymanager/net/GroqAi.kt:376`、`:428-432`、`:492`；`…/moneymanager/net/LocalAi.kt:24`、`:83`
- 傳送通知原文：`parseNotification`、`parseNotificationBatch`（排除 Gmail、被系統隱藏的、規則已能解析的）— `…/moneymanager/net/GroqAi.kt:603`、`:638`；`…/moneymanager/data/Repository.kt:1022-1041`
- 傳送交易明細做消費檢討：`review(input, base, txnIds)` — `…/moneymanager/net/GroqAi.kt:819`；分類建議、重複判斷 — `GroqAi.kt:541`、`:555`、`:583`
- 傳送投資資料：股票助理的 context 包含「持股（代號 名稱｜股性｜股數｜均價｜現價｜損益%…）」與以帳戶餘額計算的現金 — `…/moneymanager/data/Advisor.kt:134-138`、`:276-277`；`advise`、`dailyReport`、`advisorChat` — `GroqAi.kt:874`、`:1000`、`:1047`
- 教學建議會送帳戶清單（id 與名稱）— `GroqAi.kt:712`
- 通知揭露只提到「規則看不懂的通知文字會傳給你設定的 AI 服務（Groq 或 Gemini）」，沒提交易明細、持股、自架伺服器 — `…/moneymanager/ui/components/AccessDisclosure.kt:25`
- Google Play：User Data 政策同樣適用於第三方 AI 整合，開發者負責取得同意；資料移出裝置即屬「分享」，須在 Data safety 揭露；例外為使用者主動發起且可合理預期的傳送 — [Play Console Help: User Data](https://support.google.com/googleplay/android-developer/answer/10144311)、[Data safety section](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)

**定位相關服務**

**網路安全設定**
- `<base-config cleartextTrafficPermitted="true" />`，註解說明是為了區網 Ollama `http://192.168.x.x` — `app/src/main/res/xml/network_security.xml:1-8`
- `LocalAi` 接受 `http://` 或 `https://` 網址 — `…/moneymanager/net/LocalAi.kt:83`

### Inferences
- 全域允許明文流量會讓任何誤寫成 http 的請求（或第三方函式庫）在公共 Wi-Fi 被竊聽；且使用者若填入公網 http 的 Ollama，財務資料以明文過網。建議：base-config 改回 `false`；明文需求改為在 `LocalAi` 中驗證主機為私有 IP（10/8、172.16/12、192.168/16、`.local`）才允許，或使用 `domain-config` 搭配 `cleartextTrafficPermitted` 列出 `localhost`／區網（無法用萬用字元 IP 時，在程式層用 OkHttp 檢查）。
- AI 傳送需要「資料最小化」：交易送 AI 前可去除帳號末四碼、卡號、人名；持股可只送比例而非股數；OTP 樣式（6 位數字＋「驗證碼」）應在送出前遮罩。
- Data safety 表單至少要勾選：財務資訊（購買紀錄、其他財務資訊）、精確／概略位置、App 內訊息或其他使用者內容（通知文字）→「分享」給 AI 與地圖服務（除非能主張全部為使用者主動觸發）；並標示「傳輸加密」只在關閉 cleartext 後才能誠實勾選。
- 通用 UA 偽裝 Chrome 可能違反部分服務條款（Nominatim 已改用自訂 UA，其他 OSM 服務如 Overpass／tile 也有類似要求）；建議統一用可識別 UA。

### Gaps
- 未逐一核對每個 AI prompt 的實際欄位（如 review 的 input 是否含帳戶名稱、備註）；只確認函式介面與 Advisor 組 context 的片段。
- 未能取得 Groq／Gemini 免費層的資料使用條款（Gemini 免費 API 可能用於改進產品，需另查），這會影響揭露文字。

## 四、自我更新機制（Updater）與 CI 簽章

### Takeaway
GitHub 版 App 內更新只從 `api.github.com/repos/Enwei0715/Money_Manager/releases/latest` 取第一個 `.apk` 下載並交給系統安裝器，沒有雜湊或簽章預先驗證，完全依賴 Android 的「同簽章才能覆蓋」機制；真正的風險在 CI：簽章金鑰若無 Secrets 就自動產生並存成草稿 Release 資產，且 keystore 密碼 `mm-release-key` 明寫在公開 workflow 中，沒金鑰時 release 甚至會以 debug key 簽章。

### Cited Findings
- 更新來源：`BuildConfig.UPDATE_REPO = "Enwei0715/Money_Manager"` — `app/build.gradle.kts:22`；查 `releases/latest`，取第一個 `.apk` 資產 — `…/moneymanager/net/Updater.kt:43-56`
- 下載後直接寫入 `cacheDir/updates/` 並以 FileProvider 交給 `ACTION_VIEW` 安裝，無 SHA-256／簽章比對，只用 `sizeBytes` 算進度 — `…/moneymanager/net/Updater.kt:83-128`、`:139-145`
- 支援私人庫 GitHub Token（明文存於 prefs），帶 Token 失敗會自動改不帶 Token 重試 — `Updater.kt:38-41`、`:62-67`
- `REQUEST_INSTALL_PACKAGES` 只在 github flavor — `app/src/github/AndroidManifest.xml:1-4`；play flavor `SELF_UPDATE=false` — `app/build.gradle.kts:39-49`
- CI：若無 `KEYSTORE_BASE64` Secret，設 `KEYSTORE_PASSWORD=mm-release-key`，從草稿 Release「signing-key」下載 `signing.jks`，沒有就 `keytool -genkeypair … -storepass mm-release-key -keypass mm-release-key` 產生並上傳成草稿 Release — `.github/workflows/android.yml:34-61`
- 若找不到 keystore，release buildType 會退回 `signingConfigs.getByName("debug")` — `app/build.gradle.kts:56`
- PR 與非預設分支不還原金鑰（條件只限預設分支 push 或 workflow_dispatch）— `.github/workflows/android.yml:37`；`permissions: contents: write` 為整個 workflow — `android.yml:8-9`
- 同一份 CI 輸出的 `.aab` 會上傳 Play internal track（有 `PLAY_SERVICE_ACCOUNT_JSON` 時）— `android.yml:107-116`

### Inferences
- APK 本身的完整性：Android 安裝更新時會驗證新 APK 與已安裝 App 簽章相同，所以 HTTPS + GitHub 被入侵前提下，中間人無法換成他人簽的 APK；缺點是驗證發生在系統安裝畫面，App 無法事先拒絕並提示。建議下載後用 `PackageManager.getPackageArchiveInfo(..., GET_SIGNING_CERTIFICATES)` 比對憑證 SHA-256 與目前安裝版本相同，並在 Release 附上 SHA-256。
- **簽章金鑰保護不足是最高風險之一**：金鑰檔放在草稿 Release（任何有寫入權的協作者、或拿到有 `contents: write` 權限 token 的工作流程都能下載），密碼又公開在 repo；一旦外洩，攻擊者可發出能覆蓋安裝、讀取所有財務資料的惡意更新。建議：立即改用 GitHub Secrets（`KEYSTORE_BASE64` + 隨機強密碼）、刪除草稿 Release 資產；長期改 Play App Signing（Play 版）並考慮 APK Signature Scheme v3 金鑰輪替。
- debug key 退回：若 CI 某次未取得金鑰，release 會以公開已知的 debug 金鑰簽章並仍被發布，應改為「無金鑰就讓 release 建置失敗」。
- 更新說明會把 commit 訊息當 release notes（`android.yml:96-97`），需避免在 commit 中寫入內部資訊。

### Gaps
- 無法確認目前 repo 是否已設定 `KEYSTORE_BASE64` Secret（若已設定，草稿 Release 路徑不會被走到，但密碼字串仍公開）。
- repo 是否為公開庫未確認；若為私人庫，`latest` 查詢需要 Token，代表使用者手機上存放具 Contents 讀權的 Token。

## 五、法規與平台合規（個資法、Google Play、隱私權政策是否相符）

### Takeaway
開發者不經手資料、資料只在手機，因此個資法對「開發者」的直接義務有限，但 App 會蒐集通知中第三人資訊（轉帳對象姓名）並把資料送到境外 AI 與地圖服務，仍建議比照個資法第 8 條告知事項撰寫隱私權政策；Google Play 方面，隱私權政策與實際行為有多處不符（缺定位、缺第三方地圖服務、缺 Shizuku、仍描述已移除的無障礙服務、AI 傳送範圍描述過窄），是上架最直接的退件風險。

### Cited Findings
**台灣個資法**
- 個資法第 51 條第 1 項第 1 款：自然人為單純個人或家庭活動目的蒐集、處理或利用個資，不適用本法 — [全國法規資料庫 個人資料保護法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021)（本次無法直接連線，依搜尋摘要）；主管機關解釋舉例社交、建立親友通訊錄 — [臺北市法規查詢系統 函釋](https://laws.gov.taipei/Law/Interpretation/Content/FE367127)
- 國發會函釋：若資料可供不特定人瀏覽，即可能超出單純個人或家庭活動範圍 — [臺北市法規查詢系統 函釋](https://laws.gov.taipei/law/Interpretation/ContentExport/FE367127?type=5)
- 個資法於 114 年 11 月 11 日修正，新增第 51-1 條，施行日期由行政院另定（搜尋摘要，未核對全文）— [全國法規資料庫](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021)
- 本 App 宣稱「開發者沒有伺服器，也不會收到你的資料」— `PRIVACY_POLICY.md:5`；程式中確實無開發者自有端點（端點清單只見第三方服務與 GitHub）— 全文 grep

### Inferences
- **個資法**：使用者自己記帳屬第 51 條家庭活動除外；開發者不經手資料，原則上不是個資法上的蒐集者。但 (a) App 把資料送往境外 AI（Groq 美國、Google）屬使用者自行選擇並自備金鑰，傳輸由使用者發起，開發者責任低；(b) 若未來加入任何遙測、當機回報伺服器、雲端同步，就會立即成為「非公務機關」，須履行第 8 條告知、第 27 條安全維護義務。目前建議仍以第 8 條格式（蒐集目的、類別、利用期間地區對象方式、當事人權利、不提供之影響）撰寫政策，可大幅降低爭議。
- **Google Play**：建議送審前完成：(1) 重寫 PRIVACY_POLICY.md 使其與實作一致（上表每列）；(2) 定位加顯著揭露或 Play 版拿掉背景定位；(3) AI 首次啟用時加同意對話框，列出會送出的資料類別；(4) Play 版移除 Shizuku 敏感通知與 `ShizukuProvider`；(5) Data safety 表單如實勾選財務資訊、位置、使用者內容的「分享」；(6) 刪除 WalletScreenReader 死碼避免審查掃描誤判。
- 金融類 App：Play 對「個人貸款」「加密貨幣」等金融服務有額外規定；本 App 為記帳與股票資訊工具，不提供交易或借貸，原則上不落入金融服務聲明的強制類別，但股票助理的「建議」可能需免責聲明（非投資建議）。此點未取得官方原文佐證。

### Gaps
- Google Play Financial Services 政策、Permissions 政策與 Accessibility API 政策全文無法從本環境取得（support.google.com 被網路設定阻擋），只能依搜尋摘要；要逐字核對需在環境允許 support.google.com 後再查。
- 個資法第 8、27 條原文未能直接取得（law.moj.gov.tw 被阻擋），上述義務內容依一般法律知識，需以全國法規資料庫現行條文確認。
- 未確認 App 內是否有連到隱私權政策的入口（Play 要求 App 內亦須提供）。
