## 優先修補清單（依使用者影響排序）

### Takeaway
整體容錯水準中上：AI 呼叫有斷路器、冷卻、Retry-After；報價有多來源備援；Room 交易、Mmbak 匯入、新聞資料集原子寫入都有做。最大的風險集中在「備份/還原」與「設定檔損毀」這兩條會造成**永久資料遺失**的路徑，以及通知記帳批次失敗時「整批通知直接丟掉」。

### Cited Findings
依影響度排序（P0 = 可能永久遺失使用者資料；P1 = 資料錯誤或功能靜默失效；P2 = 體驗/邊角）：

- **P0-1 自動雲端備份先截斷再寫**：`openOutputStream(uri, "wt")` 會先把使用者唯一的雲端備份檔清成 0 byte，再把整份 JSON 編碼寫入；若 export 中途失敗（OOM、雲端提供者 I/O 例外、程序被殺），雲端上只剩殘缺/空檔，而且下一輪成功前沒有任何舊版可用。 — [APP/work/BackupWorker.kt:29-31](app/src/main/java/com/enwei/moneymanager/work/BackupWorker.kt)
  - 建議修法：先 export 到 `cacheDir/backup.tmp`，用 `FullBackupIO.read()` 驗證可讀回、筆數一致，再一次 `copyTo` 到目標 URI；或採輪替（`帳理自動備份-A/B.lgbak`）保留上一份。
- **P0-2 export 把整份資料一次編成 String**：`json.encodeToString(...)` 整份字串進記憶體後才寫入 GZIP，資料量大時有 OOM 風險，且是在背景工作中發生。 — [APP/data/FullBackup.kt:111](app/src/main/java/com/enwei/moneymanager/data/FullBackup.kt)
  - 修法：改用 `json.encodeToStream(FullBackup.serializer(), b, gzipOut)`（kotlinx-serialization 的 stream API）。
- **P0-3 還原不是全有或全無**：DB 部分在 `withTransaction` 內（原子），但之後的 `settings.importRaw`、各 extras SharedPreferences（`edit().clear()` 後 `commit`）、地點樣本、新聞/AI 報告都在交易之外逐一寫入；任何一步拋例外，結果是「交易已換成備份、設定還是舊的（或已被 clear 一半）」的混合狀態，UI 只顯示「還原失敗：…」。 — [APP/data/FullBackup.kt:123-144](app/src/main/java/com/enwei/moneymanager/data/FullBackup.kt)
  - 而且還原前**沒有自動建立還原前快照**，使用者無法 undo。 — [APP/ui/screens/MoreScreens.kt:975-995](app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt)
  - 修法：還原前先自動 export 一份到 `filesDir/pre_restore.lgbak`；失敗時提示「已自動回復到還原前狀態」並提供一鍵回復。
- **P0-4 還原在 `rememberCoroutineScope` 中執行**：使用者在還原進行中按返回離開畫面，coroutine 被取消；DB 交易會回滾，但若已過 DB 階段，設定/extras 會停在中途。 — [APP/ui/screens/MoreScreens.kt:835-836, 984-996](app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt)
  - 修法：改在 `MoneyApp.appScope`（或 `NonCancellable`）執行，並顯示不可取消的進度對話框。
- **P0-5 設定 JSON 解碼失敗會被靜默清空並寫回**：`budgets`、`loans`、`priceAlerts`、`watchlist`、`pendingTrades`、`brokerRebates` 等 30+ 欄位都是 `runCatching { decode }.getOrDefault(emptyMap())`；下一次任何 `update()` 會把整份 AppSettings 寫回，空值覆蓋原本（只是暫時解不開的）JSON，造成**永久遺失**，且不留紀錄。 — [APP/data/Settings.kt:542-659](app/src/main/java/com/enwei/moneymanager/data/Settings.kt)（讀）；[APP/data/Settings.kt:746, 812, 817](app/src/main/java/com/enwei/moneymanager/data/Settings.kt)（寫回 budgets/loans/priceAlerts）
  - 對照：新聞資料集對同樣情況有做「壞檔改名 `.bad-時間戳` 隔離」，設定檔卻沒有。 — [APP/data/NewsDataset.kt:301-303](app/src/main/java/com/enwei/moneymanager/data/NewsDataset.kt)
  - 修法：解碼失敗時把原字串搬到 `"$key.corrupt"` 鍵保存、記一筆 Log，並在設定頁顯示「部分設定讀取失敗」。
- **P1-1 通知記帳整批失敗即丟棄**：`ingestNotificationBatch` 拋例外時只 `Log.e` 後 `return@launch`，該批銀行/支付通知不會寫進 `notification_log`、不會排入 OFFLINE 重試，使用者完全不知道漏記。 — [APP/notify/TxnNotificationListener.kt:72-77](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)
  - 另外通知是先放在記憶體 `pendingNotes` 等 900ms 再處理，這段時間程序被殺也會遺失。 — [APP/notify/TxnNotificationListener.kt:60-70](app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)
  - 修法：收到通知立即寫一筆 `result="RECEIVED"` 的 log（Room 寫入很快），批次完成後再更新結果；失敗時標 `FAILED` 並在 App 內提示「有 N 則通知未能判讀」，可手動重試。
- **P1-2 離線重試先標 RETRIED 再處理**：`retryOfflineNotifications` 先 `setResult(e.id, "RETRIED")`，再 `runCatching { ingestNotification(...) }.getOrNull()`；若重試時 AI 又失敗（回傳 null 或例外），該通知不會回到 OFFLINE 佇列，等於只有一次機會。 — [APP/data/Repository.kt:1000-1013](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
  - `onAvailable` 在網路抖動時可能連續觸發，兩個 coroutine 可能同時讀到同一批 OFFLINE（讀取與 setResult 之間沒有鎖）。 — [APP/MoneyApp.kt:66-72](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)
  - 修法：用 `Mutex` 包住整個函式；成功才改 RETRIED，失敗則累加嘗試次數，超過 3 次標 `FAILED` 並通知使用者。
- **P1-3 報價時間只顯示 HH:mm**：投資頁顯示「報價 13:30 · 每 30 秒更新」，沒有日期；若同步已失敗數天，舊報價看起來仍像當日最新。 — [APP/ui/screens/InvestScreens.kt:150](app/src/main/java/com/enwei/moneymanager/ui/screens/InvestScreens.kt)
  - 修法：非今日時顯示日期並加「報價可能過時」標示（超過 1 個交易日用錯誤色）。
- **P1-4 自動備份失敗原因只在備份頁看得到**：`lastAutoBackupError` 只在「備份與還原」頁顯示，沒有通知；若 URI 權限被撤銷（使用者移除雲端 App），會每 12 小時一直 retry、一直失敗而無人察覺。 — [APP/work/BackupWorker.kt:33-39](app/src/main/java/com/enwei/moneymanager/work/BackupWorker.kt)；[APP/ui/screens/MoreScreens.kt:916-923](app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt)
  - `takePersistableUriPermission` 失敗被 `runCatching` 吞掉，仍照樣把 URI 存起來。 — [APP/ui/screens/MoreScreens.kt:902-908](app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt)
  - 修法：`SecurityException` 時回傳 `Result.failure()` 並發系統通知「自動備份位置失效，請重新選擇」；連續失敗 ≥2 次或超過 2×週期未成功也發通知。
- **P1-5 備份沒有版本相容檢查**：`FullBackup` 記錄了 `dbVersion`/`version`，但 `read()` 只檢查 `format`；搭配 `ignoreUnknownKeys = true`，新版 App 產生的備份在舊版還原時，新欄位會被**靜默丟棄**。 — [APP/data/FullBackup.kt:47, 115-120](app/src/main/java/com/enwei/moneymanager/data/FullBackup.kt)
  - 修法：`b.dbVersion > 目前 DB 版本` 時拒絕並提示「請先更新 App」。
- **P2** 見下方各章（Migration 無測試、金額溢位、Worker 的 CancellationException 被 runCatching 吞掉等）。

### Inferences
- P0 類問題的共同點是「單一副本 + 非原子覆寫」。最小成本的整體改法是：所有寫到外部或整份覆寫的流程都改成「寫暫存 → 驗證 → 取代」，並在破壞性操作（還原、mmbak 取代匯入）前自動做一份本機快照。
- 這個 App 在 AI 這條路徑的容錯明顯比資料保存路徑成熟（見下一章），推測是因為 AI 問題比較常被實際碰到；備份失敗屬於低頻高傷害，建議優先投資。

### Gaps
- 沒有在實機上做故障注入（飛航模式、殺程序、塞滿儲存空間），以上屬靜態分析；實際觸發機率未知。
- 無法得知目前使用者資料量（交易筆數），因此 P0-2 的 OOM 門檻只能推測。

## 網路失敗、逾時、限流：報價、AI、地圖/地點 API

### Takeaway
網路層有統一逾時（一般 15s 連線/30s 讀取；報價 6s 總時限），報價有多來源 fallback、地點有快取與多主機備援，AI 有完整的 429/503/Retry-After 處理與斷路器。弱點在於：報價/匯率失敗多半「靜默沿用舊值」，使用者只看到不含日期的時間；Overpass/Nominatim/Google 等免費服務沒有退避。

- **統一 HTTP 客戶端**：`connectTimeout 15s`、`readTimeout 30s`；報價用 `fast` 客戶端 `callTimeout 6s`、`connectTimeout 4s`；非 2xx 一律 `throw IOException("HTTP code")`。沒有任何 OkHttp 層的重試 interceptor。 — [APP/net/Http.kt:17-28, 46-62](app/src/main/java/com/enwei/moneymanager/net/Http.kt)
  - `resp.body!!` 在 OkHttp 4 的 `execute()` 回應中實務上不為 null，風險低。 — [APP/net/Http.kt:52, 60](app/src/main/java/com/enwei/moneymanager/net/Http.kt)
- **報價多來源備援**：台股先打 TWSE MIS（失敗回空清單），再逐檔改用 Yahoo `.TW` → `.TWO`；美股 Yahoo；每檔各自 `runCatching`，單檔失敗不影響其他。 — [APP/net/MarketData.kt:52-59](app/src/main/java/com/enwei/moneymanager/net/MarketData.kt)
- **匯率**：每日匯率失敗時改用即時報價，兩者都失敗才拋出；成功才更新 `lastFxUpdate`。 — [APP/work/SyncWorker.kt:58-68](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)

### Inferences
- 建議修法（依序）：
  1. 報價/匯率失敗時把「部分失敗的代號」與「最後成功時間（含日期）」存起來，在投資頁與帳戶總覽顯示「X 檔報價取得失敗・最後更新 11/10 13:30」並附「重試」按鈕（目前只有 InvestScreens.kt:150 的 HH:mm）。
  2. GooglePlaces/Mapbox 第二條路徑：失敗結果不要放進快取（參照 Mapbox.kt:81 的 `if (lastOk)` 寫法統一）。
  3. Overpass 是公益服務，有明確的限流；遇到 HTTP 429/504 應延後再試（例如記住冷卻時間），而不是立刻打下一個主機。這屬建議，未在本次查到 Overpass 官方限流數值。
  4. LocalAi 可沿用 AiHealth 的冷卻機制，避免自架伺服器離線時每次都等 5 秒連線逾時。
- 報價、地圖這類「讀取」失敗大多不會造成資料錯誤，只會讓顯示過時，影響度屬 P1/P2；真正需要注意的是使用者據此判斷投資（報價過時沒標示）。

### Gaps
- 沒有實測各來源的真實失敗率或 Yahoo/TWSE 的限流行為。
- `Nominatim` 的呼叫點本次 grep 未在 PlaceHints.kt 明確找到（只有 Geocoder 與 Overpass），可能已被移除或在其他檔案，未確認。

## 背景工作：失敗處理、暫停/恢復、冪等、被系統殺掉、重複執行

### Takeaway
所有週期工作都用 `enqueueUniquePeriodicWork(KEEP)`，避免重複排程；新聞/報告工作有時間預算（8 分鐘）分段接續、看門狗、已完成部分即時保存，設計相當周全。主要缺口：部分 worker 用 `runCatching` 吞掉 `CancellationException`；SyncWorker 的「立即同步」沒有網路條件；BackupWorker 對不可恢復錯誤也一直 retry。

### Cited Findings
- **唯一工作名稱**：`sync`、`typhoon`、`news`、`stock-alerts`、`auto-backup` 皆為 `enqueueUniquePeriodicWork(..., KEEP)`；一次性的 `sync-now`、`auto-backup-now` 用 `REPLACE`；新聞接續用 `APPEND_OR_REPLACE`。 — [APP/work/SyncWorker.kt:38-55](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)；[APP/work/BackupWorker.kt:43-51](app/src/main/java/com/enwei/moneymanager/work/BackupWorker.kt)；[APP/work/NewsWorker.kt:138-152](app/src/main/java/com/enwei/moneymanager/work/NewsWorker.kt)；[APP/work/StockAlertWorker.kt:43-46](app/src/main/java/com/enwei/moneymanager/work/StockAlertWorker.kt)
- **SyncWorker**：週期 4 小時、需網路、`EXPONENTIAL 15 分鐘` backoff；`refreshMarket` 失敗時 retry，`runAttemptCount > 2` 就放棄回 success（避免無限重試）。 — [APP/work/SyncWorker.kt:28-32, 45-49](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)
  - 但 `warnFunding`、`warnLoans`、`checkUpdate` 在每次（含 retry）都會先跑；是否會因 retry 重複發通知取決於其內部去重，本次未逐一驗證。 — [APP/work/SyncWorker.kt:28-30](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)
  - `syncNow` 用 `OneTimeWorkRequestBuilder<SyncWorker>().build()`，**沒有網路約束**，離線時按下會立即失敗並進入 retry。 — [APP/work/SyncWorker.kt:53-54](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)

## 輸入驗證：金額、日期、匯入檔、通知解析

### Takeaway
金額輸入走自製計算機，回傳 `BigDecimal?`，不完整或除以零回 null、UI 擋存檔；通知解析全用 `toDoubleOrNull`；Mmbak 匯入對每個欄位容錯。唯一明顯缺口是金額轉成分（minor unit）時 `BigDecimal.toLong()` 不檢查溢位。

### Cited Findings
- **計算機**：去除千分位、尾端運算子；數字解析用 `toBigDecimalOrNull`，失敗回 null；除以零回 null。 — [CORE/Calculator.kt:46-75](core/src/main/kotlin/com/enwei/moneymanager/core/Calculator.kt)
- **金額必須 > 0 才能存**：`amountMinor = Calculator.evaluate(expr)?.abs()?.let(Money::toMinor)?.takeIf { it > 0 }`；`canSave` 需金額非 null、帳戶有效、轉帳需目標帳戶；按下存檔時金額為 null 會跳 snackbar「請輸入金額」並打開鍵盤。 — [APP/ui/screens/TxnEditor.kt:228, 235, 523](app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)
- **溢位風險**：`Money.toMinor(value: BigDecimal) = value.setScale(2, HALF_UP).movePointRight(2).toLong()`；`BigDecimal.toLong()` 超出 Long 範圍時會靜默截斷高位元（Java 規格），計算機沒有大小上限，例如輸入 `99999999999×99999999` 可能產生錯誤金額甚至通過 `> 0` 檢查。 — [CORE/Money.kt:9](core/src/main/kotlin/com/enwei/moneymanager/core/Money.kt)
- **通知解析**：股數、價格以 `replace(",", "").toDoubleOrNull()`，失敗回 null 不記帳。 — [CORE/NotificationParser.kt:326-363](core/src/main/kotlin/com/enwei/moneymanager/core/NotificationParser.kt)

### Inferences
- 修法建議：
  1. `Money.toMinor` 改用 `longValueExact()`，捕捉 `ArithmeticException` 回 null；計算機結果加上限（例如 ≤ 1e12 元），超過顯示「金額過大」。
  2. Mmbak 匯入摘要加「N 筆資料格式錯誤未匯入」。
  3. 還原錯誤訊息映射：`ZipException/EOFException` →「檔案損毀或不完整」；`SerializationException` →「備份格式不相容，請更新 App」；`SecurityException` →「無法讀取此位置，請重新選擇檔案」。
  4. 還原改為串流解碼（`decodeFromStream`）避免 `readBytes()`。

### Gaps

## 離線模式：沒網路時什麼能用、通知佇列

### Takeaway
核心記帳（手動記帳、規則型通知解析、統計、預算、週期交易、本機備份）完全離線可用；AI 判讀的通知在離線時標記為 OFFLINE 排隊，網路恢復 3 秒後重判，但只在 App 程序存活時觸發、只重試一次、只回溯 48 小時。

### Cited Findings
- **離線排隊條件**：網路不通、AI 已啟用、文字未被遮蔽、不像促銷時，通知結果記成 `OFFLINE`。 — [APP/data/Repository.kt:1122](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- **恢復網路觸發**：App 啟動時註冊 `registerDefaultNetworkCallback`，`onAvailable` 延遲 3 秒呼叫 `retryOfflineNotifications`；整段 `runCatching`，註冊失敗不會有任何提示。 — [APP/MoneyApp.kt:65-72](app/src/main/java/com/enwei/moneymanager/MoneyApp.kt)
- **重試範圍**：只取 48 小時內、AI 啟用、通知功能開啟、網路類型符合（`networkProblem(background=false)`）時才跑；結果為 RECORDED 則發通知（待確認）。 — [APP/data/Repository.kt:1000-1013](app/src/main/java/com/enwei/moneymanager/data/Repository.kt)
- **網路相關背景工作皆帶 `NetworkType.CONNECTED`（或 Wi-Fi 限定）約束**，離線時不會白跑（例外：`sync-now`、BackupWorker）。 — [APP/work/SyncWorker.kt:39, 46, 53-54](app/src/main/java/com/enwei/moneymanager/work/SyncWorker.kt)；[APP/work/NewsWorker.kt:132](app/src/main/java/com/enwei/moneymanager/work/NewsWorker.kt)；[APP/work/BackupWorker.kt:44](app/src/main/java/com/enwei/moneymanager/work/BackupWorker.kt)
- **新聞背景工作**：`AiHealth.networkProblem() != null` 時直接 success 跳過（不會累積失敗）。 — [APP/work/NewsWorker.kt:34](app/src/main/java/com/enwei/moneymanager/work/NewsWorker.kt)
- **報價離線**：沿用 DB 中的 `QuoteEntity`（含 `updatedAt` 欄位），但 UI 顯示的是 settings 的 `lastQuoteUpdate` 且只有 HH:mm。 — [APP/data/Entities.kt:167, 176](app/src/main/java/com/enwei/moneymanager/data/Entities.kt)；[APP/ui/screens/InvestScreens.kt:150](app/src/main/java/com/enwei/moneymanager/ui/screens/InvestScreens.kt)
- **地點搜尋離線**：`PlaceSearch.online` 為 false 時延遲 1 秒（推測為等待網路），失敗則回空清單；錯誤字串如「連不上 Google / 連不上 Mapbox」。 — [APP/data/PlaceHints.kt:152](app/src/main/java/com/enwei/moneymanager/data/PlaceHints.kt)；[APP/net/GooglePlaces.kt:119](app/src/main/java/com/enwei/moneymanager/net/GooglePlaces.kt)；[APP/net/Mapbox.kt:116](app/src/main/java/com/enwei/moneymanager/net/Mapbox.kt)

### Inferences
- 修法建議：
  1. 把離線重試改成 WorkManager 一次性工作（`enqueueUniqueWork("offline-notif", KEEP)` + `NetworkType.CONNECTED`），在記錄 OFFLINE 時就排入；這樣即使 App 程序被殺，網路恢復時系統也會喚醒處理，不依賴 `NetworkCallback` 存活。
  2. 超過 48 小時仍未處理的 OFFLINE 通知不要默默放棄，改成「待確認」清單並附原文，讓使用者手動補記。
  3. 在交易頁或 AI 狀態列顯示「有 N 則離線通知待判讀」，讓使用者知道有東西在排隊。
- 整體而言離線體驗對「記帳」本身是完整的；離線對投資頁的主要影響是報價過時沒有明確標示。

### Gaps
- 未確認不使用 AI 的使用者，在離線時規則解析不了的通知會怎麼處理（Repository.kt:1122 的條件要求 `GroqAi.enabled`，推測直接記為無法判讀而不排隊）。
- 未實測 Android 14+ 上 `registerDefaultNetworkCallback` 在背景程序被凍結（cached app freezer）時是否仍會收到回呼。
