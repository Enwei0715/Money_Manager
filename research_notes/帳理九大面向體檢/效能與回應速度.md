# 帳理（Ledgerly）效能與回應速度體檢

> 範圍：啟動、捲動、重組（recomposition）、資料庫、網路、記憶體、電池、APK。
> 證據以原始碼 `檔案:行號` 為主（路徑皆相對於 `app/src/main/java/com/enwei/moneymanager/`，除非另註）；官方文件只用來佐證建議。
> 沒有實機量測（無 Macrobenchmark／Perfetto 追蹤），所有「影響估計」都是依程式結構推論，標為「推論」。資料量假設：重度使用者 5 年、每天約 10 筆 ≈ 1.8 萬筆交易（假設值，非實測）。

## 一、資料庫存取模式：全表載入後在 Kotlin 過濾

### Takeaway
`db.txns().all()`（`SELECT * FROM transactions`，無 WHERE）在 `data/Repository.kt` 出現 31 次，另有 UI／小工具／AI 工具經 `repo.allTxns()` 呼叫 8 處；其中**每則通知入帳、每次開記帳頁、每次存檔觸發預算檢查**都會整表載入一次以上，屬最大的資料庫熱點。多數條件（金額、時間窗、狀態、來源、externalKey 前綴）都可改成有索引的 SQL。

### Cited Findings
- DAO 定義：`TxnDao.all()` 為 `@Query("SELECT * FROM transactions")`，無任何條件 — `data/Daos.kt:88-89`；已有一個針對性的 `findSimilar(type, amount, from, to)` 查詢 — `data/Daos.kt:94-95`，但入帳流程大多沒用它。
- 交易表索引只有 `date`、`accountId`、`toAccountId`、`externalKey(unique)` — `data/Entities.kt:79`；沒有 `status`、`type`、`source`、`categoryId`、`merchant`、`amount` 索引。`accounts`、`categories`、`recurring`、`merchant_rules` 無索引（表小，影響低） — `data/Entities.kt:33,64,107,180`。
- `grep -c "db.txns().all()" data/Repository.kt` = **31**；`repo.allTxns()` 另見 `ui/screens/TxnEditor.kt:329`、`ui/screens/TxnEditor.kt:1299`、`ui/screens/MoreScreens.kt:860`、`data/AdvisorTools.kt:164`、`widget/Widgets.kt:84`、`widget/Widgets.kt:224`、`widget/SummaryWidget.kt:63`（原始碼 grep 結果）。

#### 熱路徑 1：每則通知入帳 `ingestNotification`（`data/Repository.kt:1045` 起）
- 進入時就對**任何 App 的任何通知**做 `countSame` 查詢＋兩次 `DELETE ... prune` — `data/Repository.kt:1058-1061`；並載入整個 accounts 表 — `:1068`。這發生在判斷「這個 App 是否啟用」(`:1069-1070`、`:1128` 的 `if (!enabled)`) 之前，所以聊天、新聞推播也會付出這幾次 DB 寫入成本。
- 批次分類前再載入一次 accounts — `data/Repository.kt:1024`。
- 判讀成功後至少 3 次整表 `db.txns().all()`：原文去重 `:1170`、附近 10 分鐘同金額 `:1193`、手動／畫面先記合併 `:1347`；另依情境再加 `:1259`（儲值）、`:1319`（卡費 5 天窗）、`:1338`（退佣）、`:1420`（位置推測時 `allTx`）。另外 `db.stocks().allTrades()` 整表 — `:1180`。
- 寫入後 `saveTxn → checkBudgetAlert → budgetUse` 又再整表載入交易與分類 — `data/Repository.kt:211`、`data/Budget.kt:24,28`；`learnMerchant`／`suggestCategory` 也會整表載入 — `data/Repository.kt:301-305`。
- 推論：單則付款通知最多可觸發約 5–7 次整表 SELECT＋物件反序列化。以 1.8 萬筆、每筆 ~20 欄（含 `rawText` 長字串）估計，每次可能是數 MB 的 CursorWindow 讀取與數萬個物件配置；在背景 `Dispatchers.Default`（`MoneyApp.kt` appScope）執行，不卡 UI，但耗電、增加 GC，並延後通知上的「一鍵分類」按鈕出現時間。

#### 熱路徑 2：通知快速動作
- `frequentCategories` 每次整表載入交易＋分類只為了算「近 90 天最常用分類」 — `data/Repository.kt:235-243`；`notify/QuickActions.kt:51-52` 再載入 categories、accounts 全表。可改成 `SELECT categoryId, COUNT(*) ... WHERE type=? AND date>=? GROUP BY categoryId ORDER BY 2 DESC LIMIT ?`。

#### 熱路徑 3：開啟記帳頁
- `TxnEditScreen` 同時 (a) 以 Flow 收集全部交易 `history` — `ui/screens/TxnEditor.kt:154`，(b) 位置推薦時再 `repo.allTxns()` 一次 — `:329`，(c) 轉帳常用帳戶再一次 — `:1299`，(d) 預算 `budgetUse` 再一次 — `:268` → `data/Budget.kt:28`。推論：開一次記帳頁 = 3–4 份全表交易清單同時在記憶體中。

#### 其他
- `confirmAllPending` 在同一個 transaction 中整表載入後逐筆 `upsert`，之後再整表載入一次 — `data/Repository.kt:257-266`；可用 `UPDATE transactions SET status='CONFIRMED' WHERE status='PENDING'` 一次完成（`learnMerchant` 另以 `SELECT ... WHERE status='PENDING'` 取得）。
- `reconcileAutopay` 在迴圈中每吸收一筆就重新 `db.txns().all()` — `data/Repository.kt:1850-1853`，最壞 O(N²) I/O。
- `deleteCategory`、`pruneRules`、`debtMatch` 等也是全表 — `data/Repository.kt:292-293,626,673`（非熱路徑）。
- `notificationLog().all()` 只為取某 txnId 的最後一筆 — `data/Repository.kt:504`，而 DAO 已有 `byTxn(txnId)`（`data/Daos.kt:246-247`）。
- 官方 Room 觀念：在 SQL 端過濾與彙總、只取需要的欄位，是 Room 的設計初衷（本次未另外抓取 Room 文件全文，屬一般知識，見 Gaps）。

### Inferences
- 優先度 P0：為入帳路徑建立專用 DAO 查詢，例如
  - `findByRawWindow(from,to)`（`WHERE rawText IS NOT NULL AND date BETWEEN ...`，再在 Kotlin 做 `contains`）取代 `:1170`；
  - `nearbyNotif(amount, from, to)` 取代 `:1193`（`WHERE source='NOTIFICATION' AND amount=? AND date BETWEEN`）；
  - 用既有 `findSimilar` 取代 `:1347`；
  - `autopayNear(cardId, from, to)`、`rebateEstimates(accountId, from, to)` 取代 `:1319`、`:1338`。
  - 加複合索引 `Index("type","amount","date")`、`Index("source","date")`、`Index("status")`（需 Room migration 6→7）。
- 把 `isEnabled` 判斷（套件名稱是否在 `notifPackages`／銀行目錄）移到 `countSame/prune` 之前；`prune` 改為每天最多一次（例如記錄上次清理時間）。預期：非記帳 App 的通知 DB 工作量降到 0。
- `budgetUse` 改用 `SELECT categoryId, SUM(amount) ... WHERE type='EXPENSE' AND date BETWEEN ? AND ? GROUP BY categoryId, currency`，避免每次存檔整表掃描。
- 整體預期（推論）：通知入帳的 DB 讀取量可從「數次全表」降到「數次索引範圍查詢（通常 < 10 列）」，對低階機背景耗電與通知按鈕延遲有感。

### Gaps
- 沒有實際資料庫大小與單次 `all()` 耗時的量測；建議用 Android Studio Database Inspector／`EXPLAIN QUERY PLAN` 與 Perfetto 驗證。
- 本次未取得 Room 官方「只查需要欄位／在 SQL 過濾」的原文引述。

## 二、Flow 架構：冷 Flow 重複訂閱＋重算在主執行緒

### Takeaway
`Repository` 的 `balances`、`holdings`、`holdingsByBroker`、`fx` 都是**未共享的冷 `combine` Flow**（全專案沒有任何 `stateIn`/`shareIn`/`flowOn`），每個畫面／每個 composable 訂閱一次就各自啟動一組 Room 查詢並各自重算；且 `combine` 的轉換在收集者的 context（Compose 的主執行緒）執行，因此「全部交易算餘額」這類 O(N) 計算跑在 UI 執行緒上。

### Cited Findings
- 冷 Flow 定義：`balances = combine(accounts, transactions, trades, fx) { computeBalances(...) }` — `data/Repository.kt:121-123`；`holdings`、`holdingsByBroker` 同樣 `combine(trades, quotes, accounts, settings.flow)` — `data/Repository.kt:150-160`；`fx = combine(fxRates, settings.flow)` — `:114-116`。
- `grep -rn "flowOn\|stateIn\|shareIn\|SharingStarted"` 全專案 0 筆（原始碼 grep）。
- `computeBalances` 走訪所有 CONFIRMED 交易並做幣別換算 — `data/Repository.kt:125-147`。
- 同一畫面重複訂閱例：`AccountsTab` 同時收集 `balances`、`holdings`、`holdingsByBroker`、`transactions` — `ui/screens/AccountsTab.kt:174-177`（`balances` 內部又訂閱一次 `transactions`，等於交易表被查兩次），再加 `rememberLookups()` 內的 accounts/categories/fx — `ui/screens/Common.kt:32-37`。`TransactionsTab` 收集 `transactions`、`pending`、`balances`、`trades`、`recurring` — `ui/screens/TransactionsTab.kt:183-193`。`repo.transactions` 被 15+ 個畫面各自收集（ConfigScreens:514、StatsTab:149/367、ReviewScreen:98、AccountsTab:177/495/807、DebtScreens:67、MoreScreens:237/327、TxnEditor:154、MerchantPlacesScreen:56、SpendMapScreen:99）。
- `FxConverter` 是一般 class（非 data class、無 equals） — `core/src/main/kotlin/com/enwei/moneymanager/core/Money.kt:63`；`Lookups` 也是一般 class — `ui/screens/Common.kt:19`。因此 `settings.flow` 任何變動 → `fx` 產生新 `FxConverter` → `balances` 全部重算，且 `rememberLookups` 產生新 `Lookups` → 以 `lk` 為參數或 remember key 的 composable 全部重組（例：`remember(all, categoryId, kind, lk)` — `ui/screens/StatsTab.kt:370`）。
- 官方說明：`flowOn` 只改變上游的執行 context，「values are collected in another coroutine using the original collector's context」，下游不受影響 — [kotlinx.coroutines flowOn](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/flow-on.html)。
- 官方建議以 `shareIn`「instead of having each collector create a new flow, you can share the data ... between collectors」，並可用 `SharingStarted.WhileSubscribed()` — [Android Developers：StateFlow and SharedFlow](https://developer.android.com/kotlin/flow/stateflow-and-sharedflow)。
- Strong skipping（Kotlin 2.0.20 起預設開啟；本專案 Kotlin 2.0.21 — `gradle/libs.versions.toml:3`）下，「Unstable parameters are compared using instance equality (===)」 — [Android Developers：Strong skipping](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping)。所以每次產生新的 `Lookups`/`FxConverter` 實例都會讓接收它的 composable 無法跳過。

### Inferences
- P0：在 `Repository` 對 `transactions`、`balances`、`holdings`、`holdingsByBroker`、`fx`、`accounts`、`categories` 加上 `.flowOn(Dispatchers.Default).stateIn(appScope, SharingStarted.WhileSubscribed(5_000), initial)`。預期：交易表變動時只查一次、只算一次，且運算離開主執行緒；多畫面（NavHost 後堆疊仍在 STARTED 的頁面）不再重複計算。
- P1：讓 `FxConverter` 成為 `data class`（或以 `distinctUntilChanged` 比較 base＋rates），`fx` Flow 加 `.map { base to rates }.distinctUntilChanged()`，避免與匯率無關的設定（例如 `lastQuoteUpdate`）觸發重算。`Lookups` 可標 `@Immutable` 並實作便宜的 equals，或只依 `accounts/categories/fx` 實例變化重建。
- 影響估計（推論）：以 1.8 萬筆交易，`computeBalances` 每次約數毫秒到十數毫秒（低階機更久），乘上同時訂閱數與每 30 秒報價刷新（見第四節），足以在股票頁／帳戶頁造成可感的掉幀。

### Gaps
- 未實測每次 `computeBalances`／`buildHoldings` 的毫秒數；建議用 `Trace.beginSection` 或 Macrobenchmark `FrameTimingMetric` 驗證。

## 三、Compose：組合期間的重計算、清單 key、Canvas

### Takeaway
記帳頁在**每次按鍵**（金額計算機、店家、說明輸入）都在主執行緒對全部歷史交易做序列掃描／分組／排序；`remember` 雖有用，但 key 本身就是正在變化的輸入，等同每鍵重算。統計頁的分類彙總沒有 `remember`。清單 key 大致有做，但交易列逐列收集 settings Flow。

### Cited Findings
#### TxnEditor（記帳頁，最常用畫面）
- `guesses = remember(amountMinor, type, history, accountId) { history.asSequence().filter...groupBy...map{ sumOf { Instant...atZone(...) } } }` — `ui/screens/TxnEditor.kt:384-400`；每按一個數字鍵 `amountMinor` 變一次就全表掃描，且每筆做 `Instant.atZone` 時區轉換。
- 店家自動完成 `remember(merchant, history, type) { history.asSequence().filter { it.merchant.contains(merchant, true) }... }` — `:759-763`，每打一個字全表掃描。
- 說明推薦 `remember(m, typed, history, type)` 內，排序比較器用 `mine.any { it == e.key }`（`mine` 為 Sequence，每次比較都重新掃 pool） — `:801-813`，最壞 O(K log K × N)。
- `stallOwner = remember(history)` 對全部交易 split／groupBy — `:288-297`；`history` 每次交易表變動（包括背景通知入帳）都是新 List，會重算。
- `LaunchedEffect(merchant, type, history.size)` 在主執行緒（LaunchedEffect 預設 Main）對全表 filter＋sort — `:251-262`。
- `knownPlaces = remember { PlaceHints.merchantGeo()... }` 首次組合時同步讀 SharedPreferences `geoPrefs.all` 並解析 — `:283`、`data/PlaceHints.kt:53`。
- 官方：「Composable functions can run very frequently ... you should do as little calculation in the body of your composable as you can」，並建議「it's best to move calculations outside of the composable altogether ... like in your ViewModel」 — [Android Developers：Compose performance best practices](https://developer.android.com/develop/ui/compose/performance/bestpractices)。

#### StatsTab / TransactionsTab
- `StatsTab`：`inRange` 有 remember，但 `totalsOf(inRange, lk.fx)` 與 `byCat = inRange.filter.groupBy.map.sortedByDescending` 直接寫在組合主體、**沒有 remember** — `ui/screens/StatsTab.kt:153-158`；任何重組（例如切換下拉選單、Tab 動畫）都會重算。`CategoryStatScreen` 的 6 期 `values`、`current` 同樣未 remember — `:373-375`。
- `TransactionsTab`：`upcoming = recurring.filter.mapNotNull.sortedBy` 未 remember — `ui/screens/TransactionsTab.kt:500-503`；月度年表 `remember(all, year, startDay)` 內對 12 個月各自 `all.filter` — `:1151-1152`（12×N，可接受但可一次 groupBy）。
- `DayBlock` 內每天的交易 `txns.sortedByDescending { it.date }` 在組合中執行 — `:613`；並在每個 DayBlock 內 `repo.settings.flow.collectAsStateWithLifecycle()` — `:607`；`MmTxnRow` **每一列**都收集一次 settings Flow — `:666`。官方建議「Collect shared Flow instances ... once in the parent composable above the lazy layout and pass the resolved values down」 — [Compose performance best practices](https://developer.android.com/develop/ui/compose/performance/bestpractices)。
- LazyColumn：主列表以「每天一個 item」並給 key `"d$day"` — `ui/screens/TransactionsTab.kt:541`（好）；全專案 `items(` 48 處中 34 處有 key，`contentType` 0 處，`derivedStateOf` 僅 1 處（grep）。官方建議異質清單「Always specify contentType」 — 同上文件。
- 正面案例：新聞篩選用 `produceState` + `withContext(Dispatchers.Default)` — `ui/screens/AdvisorScreen.kt:1116-1118`；`unknownCount`、`findDuplicates`、`cardStatus`、`loanStatuses` 等也包了 `withContext(Dispatchers.Default)` — `data/Repository.kt:318,392,1878,1940`。可作為其他重計算的範本。

#### K 線 Canvas（StockDetailScreen）
- 指標以 `remember(System.identityHashCode(b))` 快取（布林、MA20/60、各 MA、MACD、RSI、KD） — `ui/screens/StockDetailScreen.kt:728-732, 935-937`（行號依 grep 相對位置推算），計算本身不在每幀。但 `Technicals.sma(b.close, len, i+1)` 對每個 index 重算視窗和，為 O(n·len)。
- 即時迴圈每 30 秒 `bars = bars?.withLive(l)` 產生新物件 → identityHashCode 改變 → 全部指標重算一次 — `:168-182`。
- DrawScope 內有 `android.graphics.Paint().apply { ... }` 每次繪製新配置 — `:832`；文字以 `nativeCanvas.drawText` 繪製（可接受）。

### Inferences
- P0（記帳頁）：把建議計算移到 ViewModel／`produceState` + `Dispatchers.Default`，並以 **debounce（150–250ms）** 處理打字；更好的是在 DB 層預先建好「店家 → (最常用分類, 帳戶, 次數)」與「金額區間 → 分類」的彙總（`SELECT merchant, categoryId, accountId, COUNT(*) ... GROUP BY`），開頁時查一次即可。`history` 改為只取近 365 天、必要欄位的投影（`data class HistoryLite(merchant, note, categoryId, accountId, amount, date, type, status)`）。
- P1（統計頁）：`totals`、`byCat` 加 `remember(inRange, kind, lk.fx)`，或下移到 Flow 層。
- P1（列表）：settings 在 `TransactionsTab` 頂層讀一次，將 `rowStyle`、`showDescription` 作為參數傳入 `DayBlock`／`MmTxnRow`；異質 item 加 `contentType`。
- P2（K 線）：`sma` 改滑動視窗 O(n)；live 更新只改最後一根並用增量更新指標；`Paint` 物件 remember。
- 影響估計（推論）：記帳頁按鍵延遲是使用者最直接感受的「卡」，1 萬筆以上資料在中低階手機可能每鍵 > 16ms，造成輸入掉幀。

### Gaps
- 無實機 Layout Inspector 重組次數或 JankStats 資料；StockDetailScreen 指標行號為推算（`sed -n 690,800p` 相對行號 + 690），撰寫報告時建議再確認。

## 四、網路：輪詢、平行、快取、重複請求

### Takeaway
股票頁與個股頁開著時各自每 30 秒抓價（且不分是否開盤），每次刷新都會寫一次完整設定檔（`lastQuoteUpdate`）、觸發所有 combine Flow 重算並刷新桌面小工具；抓價範圍是「曾經持有過的所有代號」，包含已出清的。OkHttp 未設定 HTTP 快取（只有地圖圖磚有）。

### Cited Findings
- 股票頁輪詢：`while (true) { SyncWorker.refreshQuotes(repo); delay(30_000) }` — `ui/screens/InvestScreens.kt:126-138`；無台股／美股交易時段判斷。
- 個股頁另一個 30 秒迴圈 `QuoteService.live(market, symbol)` 並 `repo.saveQuotes` — `ui/screens/StockDetailScreen.kt:166-182`。兩頁在 NavHost 堆疊中同時處於 STARTED 時會疊加（推論；LaunchedEffect 隨組合存活）。
- 匯率頁每 60 秒 `refreshFx`，其中 `fetchRealtime` 對每個幣別平行打一次 Yahoo — `ui/screens/MoreScreens.kt:784-789`、`net/MarketData.kt:30-41`。
- `refreshQuotes` 的代號清單 = `repo.allTrades()` 中所有出現過的代號＋觀察清單 — `work/SyncWorker.kt:73-74`；之後 `repo.settings.update { lastQuoteUpdate = now }` 與 `Widgets.refreshAll` — `:77-79`。
- `SettingsStore.update` 每次都把約 28 個 JSON 欄位（包含 `advisorReport`、`reviews`、`aiSuggestions`、`memos` 等大型物件）重新 `encodeToString` 並整份 `prefs.edit()...apply()` — `data/Settings.kt:715-830`（`encodeToString` 在該區段出現 28 次）。
- `QuoteService.fetch`：證交所批次與每支 Yahoo 同時發出（`async`），台股每支最多兩次 Yahoo（.TW 失敗再 .TWO） — `net/MarketData.kt:48-60`（MarketData 內 QuoteService 段落）。平行度高，沒有併發上限。
- OkHttp：`Http.client` 只設逾時，沒有 `.cache(...)`；`fast` 客戶端有記憶體 Cookie — `net/Http.kt:17-29`。唯一有磁碟快取的是地圖圖磚 60MB — `ui/screens/SpendMapScreen.kt:377`。記憶體 LRU：GooglePlaces/Mapbox 各 200 筆 — `net/GooglePlaces.kt:33`、`net/Mapbox.kt:65`；月營收 `ConcurrentHashMap` 無上限 — `net/TwData.kt:27`。
- 正面：`Http.fast` 有 6 秒 callTimeout，來源卡住會快速改用備援 — `net/Http.kt:26-29`；`StockAlertWorker` 在非交易日／非盤中時間直接返回 — `work/StockAlertWorker.kt:30-35`。

### Inferences

## 五、啟動（MoneyApp.onCreate）與主執行緒阻塞

### Takeaway
資料庫種子、定期交易、退佣已放在背景 `appScope`（`Dispatchers.Default`），但 `onCreate` 主執行緒上仍同步做：載入整份 SharedPreferences 並解析約 28 個 JSON 欄位、解析 3,273 行英文翻譯 TSV 並排序（**即使使用者用中文**）、建立通知頻道、排程 5 個 WorkManager 工作。由於通知監聽服務也會冷啟動行程，這些成本在背景通知時也會付出。

### Cited Findings
- `onCreate` 主執行緒序列：`Repository(AppDatabase.build(this), SettingsStore(this))` → `NewsDataset(this)` → `I18n.init` → `TaiwanHolidays.update(decode(...))` → `applyAppLocale` → `createChannels` → `SyncWorker.schedule`、`scheduleTyphoon`、`NewsWorker.schedule`、`StockAlertWorker.schedule`、`BackupWorker.schedule` → `registerDefaultNetworkCallback` — `MoneyApp.kt:47-87`。
- `SettingsStore` 建構時 `MutableStateFlow(read())`，`read()` 同步 `getSharedPreferences` 並 `json.decodeFromString` 約 28 個欄位，必要時還同步重寫 — `data/Settings.kt:467-530, 531-660`。
- `I18n.init`：`if (exact.isEmpty())` 就讀 `assets/i18n_en.tsv`（181,524 bytes、3,273 行）並 `keys = map.keys.sortedByDescending { it.length }` — `ui/I18n.kt:23-35`；`english` 旗標在讀完後才設定，所以中文使用者也會解析 — `:35`。`tr()` 在非英文時直接 return — `:49-50`。
- 背景工作：`ensureSeedData/runRecurring/runFeeRebates` 在 appScope — `MoneyApp.kt:58-62`；`runRecurring`、`runFeeRebates`、`removeUnusedSeedAccounts` 內含多次全表載入 — `data/Repository.kt:711-714, 1692-1721, 1764-1783`。
- 啟動時另外啟動一個永久 collector：`repo.transactions.debounce(1500).collect { Widgets.refreshAll }` — `MoneyApp.kt:79-81`，即 App 行程存活期間 Room 會一直觀察整個交易表並在每次變動時載入全表（`observeAll` = `SELECT * ... ORDER BY date DESC`，`data/Daos.kt:76-77`）。
- 正面：`AppDatabase.build` 未使用 `allowMainThreadQueries` — `data/AppDatabase.kt:30-33`；`NewsDataset` 建構子不讀檔，`load()` 在 `Dispatchers.IO` 且有 `Mutex` — `data/NewsDataset.kt:294,309`。
- 官方：Baseline Profile 可讓程式碼「improve code execution speed by about 30% from the first launch」；另外「Non-Google-Play-Store app distribution channels might not support using Baseline Profiles at installation」，Android 7–8.1 需 `androidx.profileinstaller` — [Android Developers：Baseline Profiles overview](https://developer.android.com/topic/performance/baselineprofiles/overview)。

### Inferences
- P1：`I18n.init` 只在 `isEnglish(language)` 時載入，或改為 lazy 在背景執行緒載入；預期中文使用者冷啟動省下一次 180KB 解析＋3,000 鍵排序（推論數十毫秒等級，低階機更多）。
- P1：`SettingsStore` 的大型 JSON 欄位（`advisorReport`、`reviews`、`aiSuggestions`、`dupVerdicts`、`memos`）改 lazy 解析或移到 Room／獨立檔案；長期改用 DataStore。
- P2：WorkManager 排程（皆為 `KEEP`）可移到 `appScope` 或 `androidx.startup` 延後；Widget 觀察者改為只在有小工具時才收集（`getAppWidgetIds` 非空），或改用 `InvalidationTracker` 只觸發不載入全表。
- P2：`TaiwanHolidays.update(decode(holidayCache))` 也是主執行緒 JSON 解析，可延後。

### Gaps
- 沒有冷啟動時間量測（`adb shell am start -W` 或 Macrobenchmark `StartupTimingMetric`）；MainActivity `onCreate`（`ui/MainActivity.kt:115-124`）內 setContent 前的工作未逐行審查。

## 六、新聞資料集（NewsDataset）大小、讀寫與記憶體

### Takeaway
資料集上限 12,000 則，已改為分片（grid/block/inbox/chat/threads 多檔）並只寫有變動的分片，寫入成本控制得不錯；但一旦載入，整份 `NewsStore`（12,000 則含內文）常駐在 App 單例的 `cache` 與 `StateFlow` 中，直到行程結束。

### Cited Findings
- `MAX_ITEMS = 12000` — `data/NewsDataset.kt:471`；收集後 `sortedByDescending { it.epochSec }.take(MAX_ITEMS)` — `:580`。
- 舊且不重要（tagged、3 天前、importance ≤ 2）的新聞會清掉 `content` — `:579`，降低體積。
- `NewsItem` 欄位含 `title`、`content`、`note`、`url`、`symbols` 等字串 — `data/NewsDataset.kt:19-40`。
- 分片寫入：只在 `savedBlocks[b.key] != b` 時重寫該 block，刪除不再存在的 block，`inbox/chats/chat/grid` 也各自比較後才寫 — `:409-427`；以 `.tmp` + rename 原子寫入 — `:391-392`。
- `save()` 在 `Dispatchers.IO`，寫完設定 `cache = s`、`_flow.value = s` — `:435-440`；`update` 以 `Mutex` 序列化 — `:442`。
- `AdvisorScreen` 以 `MoneyApp.news.flow.collectAsStateWithLifecycle()` 收集整份 store — `ui/screens/AdvisorScreen.kt:141, 626, 1596`；篩選在 `Dispatchers.Default` — `:1116-1118`（好）。但篩選 key 用 `System.identityHashCode(store)`，每次 store 更新（例如背景 AI 標註每處理一批就 `update`）都會整份重新篩選＋排序。
- 每次比較 `savedBlocks[b.key] != b` 需要 data class 深度 equals（推論：12,000 則逐欄比較，CPU 成本中等，在 IO 執行緒）。

### Inferences
- 記憶體估計（推論）：假設平均每則 title 60 字、content 保留者約 500–1,500 字、Java String UTF-16 + 物件開銷，12,000 則約 10–40MB 常駐 heap；中低階裝置（heap 上限 256MB）可接受但偏重。建議：
  - P2：`cache` 在離開助理頁一段時間後釋放（`onTrimMemory` 時清除），或列表只載入「標題索引」，內文按需讀 block。
  - P2：AI 標註過程以批次結束時才 `update` 一次，降低 store 變動頻率與 UI 重新篩選。
- 正面：分片＋差異寫入設計已避免「每次改一則就重寫 12,000 則」的問題。

### Gaps
- 未取得實機上 `files/news` 目錄大小；平均 content 長度未知，記憶體數字為假設推估。
