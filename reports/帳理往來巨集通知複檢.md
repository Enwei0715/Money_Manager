## 代墊改用編號後，店名學習與舊資料遷移成為新破口

編號制的方向正確。所有會建立代墊的程式路徑只有三處：編輯器、巨集、多選分帳，全都經過 `saveWithSplits`，新資料一律帶 `SPLIT:`、`ADV:` 或沿用通知的 `N:` 鍵（[TxnEditor.kt:573](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)、[Repository.kt:873](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[TransactionsTab.kt:1430](../app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)）。往來頁與借貸頁的「記錄代墊」只是導到編輯器。「我付、和別人分」「整筆幫別人付」「別人付、我有份」三條主路徑在 HEAD 都符合規格；三個一次性遷移彼此不踩對方的資料，也有 `used` 集合避開唯一索引衝突。

問題出在「整筆幫別人付」的新實作。0e3ff7a 讓 own==0 時把既有支出**就地改成轉帳**、保留 id，手續費 `FEE:<id>` 與通知紀錄因此不會斷，這解決了上一份的第 6 項。但改型別是透過 `saveTxn` 寫入（[Repository.kt:767-768](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），而 `saveTxn` 對來源為通知的既有交易一律呼叫 `learnMerchantAlias(before.merchant, t.merchant)`（[Repository.kt:294](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。只要舊店名看起來像分店（「…店」「…分公司」「店名(地點)」），就學到「全家便利商店台北師大店 → 代墊：全家便利商店台北師大店」，並立刻 `renameNotificationMerchant` 改寫**所有**通知記下的同名交易（[Repository.kt:311-324](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[Daos.kt:120-122](../app/src/main/java/com/enwei/moneymanager/data/Daos.kt)）。之後這家店的每一則新通知也會以「代墊：全家…」記成自己的支出（[Repository.kt:1754-1755](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。重現方式很日常：通知記下一筆超商支出，在清單多選它、按「一起分帳」選室友、「全由他們」；在編輯器把「他欠你」填成整筆也會觸發。使用者會看到清單店名大量改變，消費地圖不再顯示這家店（地圖排除含「代墊」的店名，[SpendMapScreen.kt:79](../app/src/main/java/com/enwei/moneymanager/ui/screens/SpendMapScreen.kt)），分類規則也對不到。舊程式是刪除重建（沒有 `before`），不會觸發，所以這是**新引入**的 P1。同一次 `saveTxn` 還會把這次轉換計為「通知記錯被修改」（[Repository.kt:287](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。

就地轉換還有兩個後果。轉換後的交易以轉帳載入編輯器，但分帳區只在原交易是支出時顯示（[TxnEditor.kt:978](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)），誤按「他們全付」後**無法改回分帳支出**，原分類也已清空。多人時第二人以後的轉帳用 `ADV:<nanoTime>:<人>`，與原筆沒有編號關聯（[Repository.kt:771-775](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），刪除原筆或巨集的「復原」都只動第一人那筆（[MacroScreens.kt:115-116](../app/src/main/java/com/enwei/moneymanager/ui/screens/MacroScreens.kt)）。`debtMoves` 判斷代墊只看「店名以代墊開頭」或「鍵以 `SPLIT:` 開頭」（[Repository.kt:165](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[Repository.kt:176](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），不認 `ADV:`；使用者把「代墊：午餐」改成「午餐」，往來標籤就從「幫 A 代墊」變成「借給 A」，同日排序也跟著變。

第二個新 P1 在舊資料遷移 `keyLegacyAdvances`。它替沒有鍵、店名以「代墊」開頭的舊轉帳找母單，條件是 `all.firstOrNull { 支出 && 同毫秒 && 同帳戶 }`（[Repository.kt:796-809](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），而 `all()` 沒有 ORDER BY（[Daos.kt:88-89](../app/src/main/java/com/enwei/moneymanager/data/Daos.kt)）。這正是上一份審查第 2、13 項的誤認條件，只是現在被**一次寫成正式的 `SPLIT:` 連結**。舊版「整筆幫朋友轉 1,000 加手續費 15」的資料中，手續費與代墊同毫秒同帳戶，遷移會把代墊補成 `SPLIT:<手續費id>:朋友`：清單兩列仍一起消失，打開手續費顯示總額 1,015 與「朋友欠你 1,000」，刪手續費連帶刪掉代墊。「繼續記帳」或巨集共用同一個 now 的無關支出，也會被選成母單。遷移只跑一次，大多數已升級使用者的旗標會變 true，之後的錯誤連結只能靠第二次遷移修正，所以**這一項必須在下一版發佈前修**。

其餘往來問題是舊 bug 遇到新呼叫點。0e3ff7a 讓「改成付款人＝對方」與「改成收入」都會先 `deleteTxn(代墊)`，而 `deleteTxn` 先查 `feeOf(代墊)`；查不到 `FEE:<代墊id>` 時，後備規則找「同毫秒、同帳戶、店名以手續費結尾的支出」，正好是主單的手續費（[Repository.kt:349-352](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[Repository.kt:377](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。付款人路徑之後會以新 id 重建手續費（分類重設），改成收入則 `saveFee` 直接 return（[TxnEditor.kt:508-509](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)），**手續費永久消失**；在帳戶明細刪一筆代墊也會帶走主單手續費。多選分帳方面，選了 3 筆台幣加 2 筆美金時，標題只寫「3 筆支出一起分帳」，美金那 2 筆無聲排除，完成後選取又被清空，使用者會以為 5 筆都分了（[TransactionsTab.kt:434-439](../app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)）；手續費列沒排除，已有代墊的筆仍計入預覽與累計分配（[TransactionsTab.kt:1380-1392](../app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)），「全由他們」的零頭每筆都給名單最後一人（[TransactionsTab.kt:1375-1379](../app/src/main/java/com/enwei/moneymanager/ui/screens/TransactionsTab.kt)）。背景執行沒有完成提示也沒有 Undo，和其他批次操作不一致。

違反規格、但完全沒動的是兩個舊 P1。「複製」一筆房租 25,500（自己 8,500）仍以 `repo.saveTxn(t.copy(id = 0, …))` 記成今天一筆 −25,500 的自己支出（[TxnEditor.kt:1019-1025](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。別人幫付的支出重開時付款人顯示「我」、付款帳戶顯示對方；往來頁「他幫我付」只帶往來帳戶，整筆算成我的支出與欠款，違反「別人付、我有份：只欠我那份」的規格（[DebtScreens.kt:153](../app/src/main/java/com/enwei/moneymanager/ui/screens/DebtScreens.kt)）。「繼續」的實害則縮小為下一筆再記一次同額手續費（[TxnEditor.kt:576-580](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)），因為同毫秒已不再造成代墊誤認。

## 通知去重改成「寧可多記」，但只改了一半

修正的方向符合上一份審查：重送改看通知編號 `sbn.key`，「仍要記帳」會略過所有去重，沒寫時間的相同內文改記成待確認而不是丟掉。問題在於三個缺口：去重仍然不寫任何紀錄；新的放寬只接在最後一條一般路徑；新的正規式比對錯了。結果是上一份的「消失而且看不到紀錄」以新形式重現，「記兩次」則在巨集與跨 App 情境持續發生。

監聽端新增的 `recentKeys` 以「通知編號 → 標題\0內文」判斷同一則通知更新且內容沒變，命中就直接 `return`（[TxnNotificationListener.kt:83-92](../app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)）。執行緒同步沒有問題，但它**沒有時間上限，也不寫紀錄**。若某銀行或支付 App 固定用同一個通知 id、內文又不含時間與餘額，早上 8 點與下午 3 點在同一家店各付 NT$50，第二則取代第一則且內容完全相同，就被無聲吞掉，紀錄頁也找不到（推論，取決於 App 的通知 id 策略）。資料庫端的 `countSame(..., postedAt - 1)` 本意是「只比對同一則」，但 SQL 只有 `postedAt > :since` 下界（[Daos.kt:278-279](../app/src/main/java/com/enwei/moneymanager/data/Daos.kt)），實際比的是「本則或更晚的相同內容」；斷線後補讀若先處理較新的那則，舊的那則會被無聲略過。補讀本身仍用 60 秒視窗（[TxnNotificationListener.kt:41-43](../app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)），語意與新規則不一致。

放寬只套在一般路徑，是最容易造成重複記帳的缺口。修正前，沒寫時間的通知 30 分鐘內內文相同就判 DUPLICATE；現在只有寫了時間才判 DUPLICATE，沒寫時間的交給最後的 `unsure` 清單改成待確認（[Repository.kt:1478-1482](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[Repository.kt:1827-1831](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。但巨集（[Repository.kt:1549-1563](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）、往來還款、提款、儲值、轉帳配對、卡費（[Repository.kt:1566-1675](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）都在那之前提早 return，不經過 `unsure`。房租巨集開啟通知自動套用，銀行通知「轉帳 NT$25,500 成功」沒寫時間，10 分鐘後以新的通知 id 重送：**巨集整套再跑一次，主支出與兩筆代墊全部記成已確認**，不在待確認裡，很難發現。提款通知重送同樣多一筆已確認的提款。

跨 App 的同一筆消費也仍會記兩次，而且和分帳有關。新增的 `sameFromOther` 在 3 分鐘內已有同額（或「主支出＋代墊＝同額」）的通知交易時跳過巨集，交給下面的 nearby 合併（[Repository.kt:1549-1551](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。但 nearby 只收 `amount == 通知金額` 且同類型的交易（[Repository.kt:1510-1512](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)、[Repository.kt:1716](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），而巨集記下的主支出金額是自己那份（[Repository.kt:777](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），own==0 時更是轉帳。房租 25,500、A 欠 9,500、B 欠 7,500：銀行通知觸發巨集記下 8,500，1 分鐘後 LINE Pay 也通知 25,500，巨集被跳過，nearby 對不到 8,500，**新記一筆 25,500 支出**。往來分帳那邊的「整筆幫別人付」轉換有同樣效果：轉換後的通知交易金額變成第一人份額，同一消費的第二則通知不會被合併（推論）。

秒數判斷則把卡號當成時間。新規則要求對方的鍵也有秒數才視為不同筆，用的是 `Regex("""T\d{2}:\d{2}:\d{2}""")`（[Repository.kt:1714-1715](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），而鍵的格式是 `N:<金額>:<LocalDateTime>:<末四碼>`（[Repository.kt:1473](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。`LocalDateTime.toString()` 在秒數為 0 時省略「:00」，於是只到分鐘的 `N:-12000:2026-11-21T12:30:1234` 會被讀成 `T12:30:12`。信用卡通知「末四碼 1234 12:30 消費 NT$120」先記，支付 App 通知「12:30:42 付款 NT$120」再到，兩邊都被當成有秒數、相差 30 秒，**記成兩筆**；反過來，真的到秒但剛好 00 秒的鍵會被當成只到分鐘。

AI 自動整理是唯一仍屬 P0 的殘留。新條件只在「兩筆都來自通知、rawText 不同且互不包含、同一個 App」時略過（[Repository.kt:581-586](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），但上一份審查的典型情境是同店同額、通知不寫時間，所以**內文完全相同**，照樣送去給 AI 判斷。`mergeDuplicate` 仍直接 `db.txns().delete`，不寫 `MERGED_BY_AI`、不更新通知紀錄、無法還原（[Repository.kt:592-604](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)），`aiAutoTidy` 也沒排除待確認的第二筆（[Repository.kt:657-666](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。因為沒寫時間的相同內文現在記成待確認、不再直接判重，送進 AI 配對的候選反而更多（推論）。使用者在紀錄頁按「仍要記帳」救回的那筆，沒有寫進 `dupDismissed`，下一次自動整理可能再把它刪掉。紀錄頁本身仍是整列點擊就執行、沒有確認、可以連點出多筆，`Undo` 只保留最後一次，原本那列也不會改成 RECORDED（[MoreScreens.kt:673-683](../app/src/main/java/com/enwei/moneymanager/ui/screens/MoreScreens.kt)）。

可靠度相關的第 21 項完全沒動：`onDestroy` 仍清空 `pendingNotes`，`requestRebind` 只在 `onListenerDisconnected` 呼叫，AI 批次仍在 `ingestLock` 內（[TxnNotificationListener.kt:52-60](../app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)、[Repository.kt:1291-1294](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。全文擷取仍是 `BIG_TEXT ?: TEXT`，紀錄仍只讀 200 列（[TxnNotificationListener.kt:66-76](../app/src/main/java/com/enwei/moneymanager/notify/TxnNotificationListener.kt)、[Daos.kt:254](../app/src/main/java/com/enwei/moneymanager/data/Daos.kt)）。這些修法多半只要改一兩行，建議先補三個 Repository 層測試：沒寫時間、間隔 10 分鐘、命中巨集的第二則不會再跑巨集；巨集代墊加第二個 App 同額通知，總支出不變；「12:30＋末四碼」的卡片通知加「12:30:42」的錢包通知只產生一筆。

## 記帳頁：按「=」會清空金額，推薦列仍會跳一格

金額欄的修法是在 `amountFresh` 時加一條 `v0 == old -> ""`（[TxnEditor.kt:1044-1050](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）：舊值已有兩位小數、`Calculator.append` 拒收按鍵時，先清空欄位，不再卡死。但「=」也走同一個 `onExpr`（[TxnEditor.kt:1381-1383](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。打開一筆 1,200 的交易、點金額、在計算機模式按「=」，`format(evaluate("1200"))` 等於舊值，**金額被清空**；舊值 12.99 或 0.5 時按「.」也一樣。這是新回歸。原本要修的問題只修了一半：舊值 12.99 時按「5」，欄位變空、5 沒有輸入，要再按一次。「=」後也仍未重設 fresh，再按數字會接在結果後面。根本的修法是把 fresh 判斷移進 Keypad：只有數字與「.」在 fresh 時從空字串開始 `append`（「.」變「0.」），運算子與「=」照舊作用在舊值，移除「先 append 再取尾巴」的推算。

帳戶「自動」帶入的清除邏輯正確：找不到習慣、且目前帳戶就是自動帶入的那個才清空，手動選的帳戶與導航帶入的初始帳戶都不會被動到（[TxnEditor.kt:288-301](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。殘留的是 `autoAccount` 只用 `remember`，旋轉或切深色模式後帳戶仍在、「自動」身分卻消失，之後換店也不再更新（[TxnEditor.kt:287](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）；effect 以 `merchant` 每個字元為 key，打「全聯」帶入、刪一字清空、再打回又帶入，欄位會跳動。點「由 X 付」切回自己付，X 仍留在分帳列，憑空多一筆「X 欠你」（[TxnEditor.kt:844](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。

推薦列的 `withBest` 讓已在列上的店維持相對順序，但仍會位移（[TxnEditor.kt:385](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。先列出記過的店 A、B、C，之後才找到最可能的 X，列表變成 X、A、B、C，正要點 A 的手指點到 X；有 Google 金鑰時，新清單只留最近 6 家加 2 家紀錄，原本列上的其他 chip 被移除，後面的往左移（[TxnEditor.kt:402-417](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。第一個 chip 仍沒有「最可能」標示，三處註解與教學仍描述舊的「直接帶入店名」行為（[TxnEditor.kt:255-258](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)、[TxnEditor.kt:379-408](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)）。新增的「別人欠你的合計超過總額」擋存只跳 snackbar、不打開分帳欄，使用者不知道哪一列超過；檢查又加總所有 `splitRows`，存檔時卻略過沒有對象的列（[TxnEditor.kt:498-501](../app/src/main/java/com/enwei/moneymanager/ui/screens/TxnEditor.kt)），留一列只有金額的空列就可能被看不懂地擋下。

## 股價不再等 Yahoo，卻每 30 秒對每一檔白打一次

報價修正讓證交所價格合理時直接 `continue`，不再等 Yahoo（[MarketData.kt:62-70](../app/src/main/java/com/enwei/moneymanager/net/MarketData.kt)），觀察清單確實更快更新。但 Yahoo 請求仍對**每一檔**同時發出（.TW 失敗再 .TWO），開在一個從不取消的 `CoroutineScope(Dispatchers.IO)` 裡（[MarketData.kt:53-59](../app/src/main/java/com/enwei/moneymanager/net/MarketData.kt)）；註解說「取消這檔的 Yahoo 查詢」，實際上沒有任何 `cancel()`。股票頁開著時台股盤中每 30 秒刷新全部持股與觀察清單（[InvestScreens.kt:127-138](../app/src/main/java/com/enwei/moneymanager/ui/screens/InvestScreens.kt)），觀察清單 30 檔就是每分鐘約 60～120 個結果全被丟掉的請求。每個請求都包在 `runCatching` 且最多約 12 秒結束，不會洩漏例外或長期佔用資源，但會耗電耗流量，並提高被 Yahoo 限流的機率，真正需要備援時反而失敗（推論）。

其餘股價問題多屬舊項。股票助理的「持股」卡仍算 `price / avgCost - 1`，`HoldingPlan.gainPct` 也把同一個數字送進 AI 文字（[AdvisorScreen.kt:2267](../app/src/main/java/com/enwei/moneymanager/ui/screens/AdvisorScreen.kt)、[Advisor.kt:42](../app/src/main/java/com/enwei/moneymanager/data/Advisor.kt)、[Advisor.kt:280](../app/src/main/java/com/enwei/moneymanager/data/Advisor.kt)），不扣股利與賣出費用，領過股利的長期持股和個股頁可差數個百分點。其他四處已統一成 `Σunrealized / ΣnetCost`，跨券商合併時等於加權平均，語意正確（[Repository.kt:65-73](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。`saveQuotes` 仍讓「比現有舊 30 分鐘以上」的報價覆蓋新報價，Yahoo 資料卡在 09:20 時，10:00 的證交所價格會被蓋回去（[Repository.kt:2626-2633](../app/src/main/java/com/enwei/moneymanager/data/Repository.kt)）。個股頁仍等五年日 K 才結束 loading；昨收仍取 K 線倒數第二根、時間標籤用抓取時間、美股永遠寫「即時」（[StockDetailScreen.kt:148](../app/src/main/java/com/enwei/moneymanager/ui/screens/StockDetailScreen.kt)、[StockDetailScreen.kt:254-265](../app/src/main/java/com/enwei/moneymanager/ui/screens/StockDetailScreen.kt)）。新的灰字規則只在觀察清單、只看台股，且以資料時間判斷（[InvestScreens.kt:284-288](../app/src/main/java/com/enwei/moneymanager/ui/screens/InvestScreens.kt)）。Yahoo 的 `regularMarketTime` 是最後成交時間（[MarketData.kt:242](../app/src/main/java/com/enwei/moneymanager/net/MarketData.kt)），盤中 5 分鐘沒成交的冷門上櫃股價格其實是最新的，卻會變灰；同一檔在持股列表與個股頁則不會變灰（推論，證交所 `tlong` 的確切語意未查證）。紀律卡的損益% 用資料庫報價、同卡的價位圖用 K 線現價，即時價更新時兩者可能差一跳；均價 100、現價 100.5 時顯示為負，因為扣了約 0.585% 的預估賣出費用，建議標籤改成「預估損益（扣賣出費用）」。美股持股卡路由已正確改用 `marketOf(symbol)`（[StockDetailScreen.kt:101](../app/src/main/java/com/enwei/moneymanager/ui/screens/StockDetailScreen.kt)、[StockDetailScreen.kt:288](../app/src/main/java/com/enwei/moneymanager/ui/screens/StockDetailScreen.kt)）。

## 結論

這輪修正證明「改用明確身分」的方向是對的：代墊改用編號後，上一份審查往來分帳的六個 P0 有五個直接消失。但新問題幾乎都出現在**舊機制與新身分的交界**：就地轉型碰到店名學習，舊資料遷移沿用被淘汰的毫秒比對，新的去重只接在最後一條路徑，新的秒數判斷從字串反推精度。每一個都是在「新規則旁邊還留著一條舊規則」的地方出錯。下一輪最有槓桿的工作不是逐項補洞，而是收斂成單一入口：所有判重都在分支之前執行一次並寫下原因；所有連帶寫入（轉型、刪代墊、補編號）都不經 `saveTxn` 的學習副作用；時間精度在寫入時就存下來，而不是之後從字串推回。

時序上有一件事不能等。`keyLegacyAdvances` 是只跑一次的遷移，每多一個使用者升級，就多一份無法自動更正的錯誤連結；店名對照污染則會隨每次「全由他們」擴散到歷史資料。這兩項應先於其他 P1 修好並發佈。其餘項目可以依本報告排序處理，但修之前建議為每個 P1 先寫一個會失敗的 Repository 層測試。這次三個提交沒有更動任何測試檔（`git show --stat` 不含 test 路徑），而新引入的 6 個 P1 都發生在 Repository 與監聽端的純邏輯，可以在單元測試層重現。本報告沒有實機驗證，各銀行通知 id 策略、Android 補讀排序、圓餅標籤實際落點與證交所 `tlong` 語意都需要在裝置上確認；這些推論影響的是發生機率，不改變排序最前面幾項的結論，因為它們都由程式碼路徑直接確認。
