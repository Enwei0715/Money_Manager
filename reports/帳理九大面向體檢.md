# 帳理體檢：先堵住靜默漏帳，再談成長變現

帳理（Ledgerly）的功能廣度與自動化程度已經超過多數台灣記帳 App。通知自動記帳、信用卡週期與自動扣繳、股票 FIFO 損益、AI 斷路器、分片寫入的新聞資料集都有成熟實作。最大的風險不在功能不夠，而在三種「使用者看不到的錯」。第一種是**資料靜默遺失或記錯**：提款卡消費被記成提款、「買賣別：賣出」被解析成買進、3 分鐘內同額消費被當重複丟掉、自動扣繳吸收會直接刪掉真實支出、雲端自動備份先清空再寫入。第二種是**資安與上架合規缺口**：簽章金鑰的密碼寫在公開 workflow 裡、4 位數 PIN 只用固定鹽 SHA-256、明文備份含通知原文與定位、隱私權政策與實際行為至少 8 處不符。第三種是**完全沒有回饋閉環**：沒有任何回報入口，正式版 stack trace 因混淆又沒保存 mapping 而幾乎無法解讀，所以前兩類錯誤即使發生了，開發者也不會知道。因此優化順序應該是：先用 1～2 週修掉會讓資料遺失、記錯或金鑰外洩的 P0 項目，同時補上可讀的閃退紀錄與回報管道；接著 1～2 個月處理隱私政策、效能熱點、無障礙與說明文字；最後才做留存提醒與「一次性 Pro＋可選託管 AI」的變現。變現前必須先調整每日投資報告的指令性內容，因為收費提供具體選股與投入金額，可能落入《投信投顧法》第 107 條。本報告的證據來自原始碼靜態閱讀與 core 模組的實測探針，沒有實機量測或使用者數據；涉及頻率與效能幅度的地方都是推論，文中會標明。

> 嚴重度定義（全文一致）：**P0**＝會造成資料遺失、金額或方向錯誤、金鑰或個資外洩，或直接阻擋上架；**P1**＝功能錯誤、靜默失效或使用者看得到的明顯缺陷；**P2**＝體驗、維護性與邊角情況。程式碼連結路徑相對於 repo 根目錄（本檔位於 `reports/`）。

### 建議做法與優先順序

先處理通知流程的穩定性（P1，第 1 階段）：在 `Repository` 用一個 `Mutex` 串行化 `ingestNotification`，每則通知各自 try/catch 並寫入 `ERROR` 紀錄供重試。接著把 ingest 的「決策」抽成 core 模組的純函式，輸入是解析結果加候選交易，輸出是 Insert／Merge／Duplicate／Delete 指令。這樣第 4 節所有 P0 情境都能用 JUnit 覆蓋。同時在 `app/build.gradle.kts` 設 `room.schemaLocation`，把 schema JSON 納入版控，再加一個 v1→v6 的 migration 測試。三個閃退點改用 `isNotEmpty()`、`firstOrNull`、`toLongOrNull()`，失敗就 `popBackStack()`，每處只需幾行。入口問題屬第 2 階段：讓 AI 中心改用 `openRoute()`、「App 更新」卡改開 `config?g=update`、刪除或接上孤兒路由與欄位，並把 `featureStocks` 拆成「股票記帳」與「投資助理」兩個開關。

### 建議做法與優先順序

所有 P0 都可以用同一個原則修：**寫暫存、驗證、再取代，破壞性操作前先自動快照**。這些項目放在第 0 階段（1～2 週）。自動備份先 export 到 `cacheDir/backup.tmp`，用 `FullBackupIO.read()` 讀回並核對筆數後才複製到目標 URI，或改成 A/B 兩份輪替。匯出改用 `encodeToStream` 直接寫進 GZIP，還原改用 `decodeFromStream`。還原前把目前狀態 export 到 `filesDir/pre_restore.lgbak`，改在 `appScope`（或 `NonCancellable`）中執行並顯示不可取消的進度框，失敗時提供一鍵回復。設定解碼失敗時，把原字串搬到 `"$key.corrupt"` 鍵保存，並在設定頁提示「部分設定讀取失敗」。長期再把 budgets、loans 等大型 JSON 從 SharedPreferences 移到 Room 或 DataStore。

第 1 階段處理 P1。離線重試改成 `enqueueUniqueWork("offline-notif")` 加 `NetworkType.CONNECTED`，失敗時累加嘗試次數，超過 3 次才標 `FAILED` 並通知使用者，超過 48 小時的項目改列「待確認」附原文。BackupWorker 依錯誤類型分流：`SecurityException` 回 `failure()` 並發系統通知請使用者重新選位置，`IOException` 才 retry。報價非當日時顯示日期與「可能過時」標記。`toMinor` 改用 `longValueExact()`，計算機設上限（例如 1e12 元）。

## 3. 資安防護與隱私合規：開發者不經手資料，但本機與備份全是明文

### 現況

帳理沒有開發者伺服器，程式中也找不到開發者自有端點；完整備份刻意排除 AI 金鑰與 GitHub Token；元件大多 `exported=false`；PendingIntent 只在 RemoteInput 必要處可變，且使用明確 Intent；debug receiver 只存在於 debug source set，CI 不會出貨 ([Settings.kt:664-666](../app/src/main/java/com/enwei/moneymanager/data/Settings.kt); [AndroidManifest.xml](../app/src/main/AndroidManifest.xml); [QuickActions.kt:85-100](../app/src/main/java/com/enwei/moneymanager/notify/QuickActions.kt))。但所有敏感資料都以明文存在：API 金鑰在一般 SharedPreferences、Room 未加密、備份是未加密 gzip JSON；全專案沒有 EncryptedSharedPreferences、Keystore、SQLCipher 或 `FLAG_SECURE`。Android 官方建議敏感資料依密碼學指引加密，並用 Keystore 保護金鑰 ([Android Developers: Backup best practices](https://developer.android.com/privacy-and-security/risks/backup-best-practices))。

### 建議做法與優先順序

第 0 階段要**立刻處理簽章金鑰**：改用 GitHub Secrets 存 `KEYSTORE_BASE64` 加隨機強密碼、刪除草稿 Release 的金鑰資產，並讓「沒有金鑰就建置失敗」，不再退回 debug key。如果懷疑舊金鑰已外洩，Play 版改用 Play App Signing，GitHub 版評估 APK Signature Scheme v3 的金鑰輪替。PIN 改用 PBKDF2 或 Argon2，每裝置隨機鹽、高迭代、至少 6 位數、連續輸錯遞增延遲，並把 `passcodeHash` 加入備份排除名單。這些改動成本低、風險高，應與第 2 節的備份修正一起出貨。

第 1 階段（送審前必完成）有五項。第一，逐列重寫 `PRIVACY_POLICY.md`，建議比照個資法第 8 條的告知格式（蒐集目的、類別、利用對象、當事人權利）撰寫。研究筆記指出，使用者自行記帳屬個資法第 51 條的個人或家庭活動除外，開發者不經手資料，原則上不是蒐集者；但未來只要加入任何遙測或託管服務，就會成為非公務機關，需履行告知與安全維護義務 ([全國法規資料庫 個人資料保護法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021))。第二，Play 版移除 `ACCESS_BACKGROUND_LOCATION`，改成使用者點通知時再以前景定位補上；GitHub 版可保留，但要補定位專用的顯著揭露。第三，`.lgbak` 支援以使用者密碼做 AES-GCM 加密，自動備份預設加密。第四，`cleartextTrafficPermitted` 改回 `false`，明文只在 `LocalAi` 驗證主機為私有 IP 時放行。第五，首次啟用 AI 時跳出同意框，列出會送出的資料類別；送出前遮罩 OTP、卡號與人名，持股只送比例。Play 版移除 Shizuku 敏感通知功能，並刪除 WalletScreenReader 死碼。Room 加密（SQLCipher）屬第 3 階段，因為 Android 本機檔案加密對一般威脅已經足夠。

## 4. 生成資料的準確性：最大風險是不會出現在待確認清單的錯

### 現況

### 建議做法與優先順序

第 0 階段做成本最低、收益最高的一步：`proguard-rules.pro` 加上 `-keepattributes SourceFile,LineNumberTable`，CI 把 `mapping.txt` 隨 Release 上傳，Play 上傳步驟加 `mappingFile`。同時修 `acceptAiSuggestion`，改走 `saveTxn`，只需一行。

第 1 階段建立「零 SDK」的回饋管道。這與「沒有伺服器、沒有分析追蹤」的承諾相容。在「設定→關於」與閃退對話框加「回報問題」，產生**不含財務資料**的診斷包，送出前全文預覽，可以逐項取消。診斷包內容包括版本、flavor、Android 版本、功能開關布林值、近 30 天指標比率與最近閃退。一律排除金額、商家、帳戶名、通知原文、卡號、座標與金鑰。研究筆記指出一般使用者多半沒有 GitHub 帳號，所以送出管道預設用 Email（`ACTION_SENDTO` 附檔），GitHub issue 預填網址作為進階選項 ([GitHub: 建立 issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue))。repo 端新增 `bug_report.yml` 與 `notification_format.yml` 模板，後者讓使用者用遮罩過的格式回報看不懂的銀行通知，例如「您的信用卡 **** 於 ### 消費 NT$###」。Play 版的當機率與 ANR 可直接從 Android vitals 取得，但 vitals 只涵蓋 Play 安裝且同意分享的使用者，小眾 App 也可能因資料量不足而不顯示 ([Android vitals](https://developer.android.com/topic/performance/vitals))，所以仍要加上 `ApplicationExitInfo` 的本機擷取，閃退紀錄保留 5 筆。

第 2 階段新增一張只存數字的 `metric_daily(day, key, count)` 表，突破 7 天保留期，並做一個「診斷與統計」頁，顯示通知辨識率、規則與 AI 辨識比、待確認存量、自動填入接受率、AI 各平台失敗率、AI 建議接受率。`AiSuggestion` 拆成 OPEN／ACCEPTED／REJECTED 三種狀態；「不是重複」寫回 `dupVerdicts`；商家規則改存 (merchant, category, count) 取多數。推薦追蹤顯示超額報酬，資料中已有推薦時的大盤點位。不建議導入 Firebase Crashlytics：它預設自動收集，與現行隱私承諾衝突 ([Crashlytics 自訂報告](https://firebase.google.com/docs/crashlytics/android/customize-crash-reports))。若日後使用者變多需要自動化，可在同一份診斷包格式上加一個「預設關閉」的 Bugsink 或 Sentry 選項，並用 `beforeSend` 在本機清洗資料 ([Sentry: 敏感資料](https://docs.sentry.io/platforms/android//data-management/sensitive-data/))。

## 9. 用戶留存與商業變現：自動擷取已是護城河，付費要避開投顧法紅線

### 現況

財務類 App 的自然留存很低。Adjust 2025 的資料是 D1 12%、D7 6%、D30 2%；Statista 2025 則是 D30 約 8%，兩者落差大 ([Getstream 2026 App Retention Guide](https://getstream.io/blog/app-retention-guide))。台灣市場公認「手動記帳不到一個月就放棄」，麻布記帳就是以此推全自動記帳 ([INSIDE: Moneybook](https://www.inside.com.tw/article/3911-moneybook-introduction))；遊戲化的記帳城市公布一般用戶平均只連續記帳 4 天 ([INSIDE 記帳城市](https://www.inside.com.tw/article/8467-fourdeisre-fortunecity))。帳理已經用通知自動記帳、週期交易、信用卡自動扣繳、預算 80%／100% 提醒、6 種小工具、月季年檢討與 .mmbak 搬家匯入，處理掉最難的「自動擷取」與「轉換成本」([Budget.kt:60](../app/src/main/java/com/enwei/moneymanager/data/Budget.kt); [Widgets.kt](../app/src/main/java/com/enwei/moneymanager/widget/Widgets.kt))。缺的是低成本的習慣迴圈：每日記帳提醒已移除，`ReminderWorker` 只剩舊版清理；沒有主動推送的週報或月報；也無法量測自己的留存 ([ReminderWorker.kt](../app/src/main/java/com/enwei/moneymanager/work/ReminderWorker.kt))。目前沒有任何計費程式。

### 問題（依嚴重度）

### 建議做法與優先順序

留存補強可以完全在本機用 WorkManager 加通知完成，不需要任何追蹤，排在第 2 階段。重點是「條件式」，避免騷擾已經自動記帳的使用者：只在「有待確認交易」或「今天沒有任何紀錄」時提醒；每週日晚上推送本機週報（本週支出、預算進度、最大分類）；每月 1 日推送「上月收支分析已準備好」，並深連結到該頁。財務類 App 很少使用連續天數，而且 2025 年 streak 在 App 中的普及率已從 14.0% 降到 8.1% ([Lazyweb](https://www.lazyweb.com/research/how-common-are-streak-screens-outside-duolingo))；斷掉的連續天數也會讓自動記帳的人感到壓力。建議改用「連續 N 週未超支」「本月預算達成」這類成就。留存指標應定義為「週活躍確認」與「月分析開啟率」，不是每日開啟，因為自動記帳的使用者本來就不需要每天打開。

變現排在第 3 階段，前提是第 0～1 階段的資料正確性與隱私修正都已完成。台灣進階記帳的價格錨點是年費約 NT$690，CWMoney VIP 與麻布都採這個價位 ([App Store CWMoney](https://apps.apple.com/tw/app/cwmoney-%E7%90%86%E8%B2%A1%E7%AD%86%E8%A8%98/id1029760973); [麻布 訂閱相關問題](https://blog.moneybook.com.tw/?page_id=4400))。麻布 2026 年起未訂閱就不能手動記帳，引發「續訂還是換掉」的討論 ([Maplefeather 2026](https://maplefeather.com/article/taiwan-bookkeeping-app-2026-moneybook-cwmoney-einvoice))。這正是帳理的差異化機會：**核心記帳、匯入匯出、備份永久免費，不鎖資料**。建議路線是先在 Play 版推出一次性「帳理 Pro」（約 NT$290～590，內容為主題、小工具樣式、進階報表與 CSV／PDF 匯出、不限數量的預算與紀律規則），GitHub 版維持全功能並加贊助按鈕。Play 版販售數位功能必須使用 Play Billing，台灣不在使用者選擇計費的開放名單中 ([TechCrunch 2025](https://techcrunch.com/2025/03/28/google-rolls-out-user-choice-billing-on-google-play-in-the-uk))；一次性內購在前 100 萬美元收入的服務費為 15%，需要註冊 ([Android Developers Blog 2021](https://android-developers.googleblog.com/2021/03/boosting-dev-success.html?m=0))。

中期可評估「託管 AI」訂閱（約 NT$60～99／月或 NT$490～690／年），讓使用者不必自備金鑰。這是唯一能形成持續收入、又能解決最大上手門檻的選項，但**範圍只限記帳相關 AI**（通知判讀、收支分析、自動整理），不包含選股。上線前需要成本模型、律師諮詢，並重寫隱私政策與 Data safety，因為交易資料會經過開發者伺服器，開發者就會成為個資法上的蒐集者。不論是否收費，都建議把 `dailyReport` 改成資訊整理與教育性質，移除具體選股、進場價、停損價、建議投入金額與指令式持股動作，只保留市場摘要、新聞重點與使用者自訂規則的機械式檢查。廣告與券商、信用卡導購都不建議：直接違反「沒有廣告或分析追蹤」的承諾，而且會讓 AI 選股看起來像收錢推介。

## Conclusion

這次體檢改變了對帳理的判斷重點。它的瓶頸不是功能，而是**「自動化的信任成本」**：通知自動記帳既是帳理最強的留存護城河，也是最大的準確度風險。去重、吸收與忽略這三個機制都以「默默不記」的方式出錯，而 App 又沒有任何管道讓開發者得知。因此，修正單一 bug 的價值低於建立一個原則：**每一次自動決定「不記」或「刪除」，都必須留下可見、可還原的紀錄**。只要這個原則與 core 層的決策純函式測試到位，新增銀行格式或 AI 能力的風險就能被控制，第 8 節的辨識率與修正率指標也才有意義。

第二個值得注意的觀察是，帳理的隱私定位（無伺服器、無追蹤、資料只在手機）同時限制也保護了它的商業選項：雲端同步、家庭共享、廣告都不適合，但「核心永久免費、不鎖資料」在麻布轉向全面收費之後，反而成為一個清楚的市場位置。真正的界線在投資 AI：免費且使用者自備金鑰時，它是工具；一旦收費託管，就會變成開發者提供的服務，法律性質隨之改變。仍不確定的事項包括各問題的實際觸發頻率（沒有實機故障注入與使用者數據）、效能改善的實際幅度、Play 現行政策原文（本次環境無法連線 support.google.com），以及個人開發者 Play 收入的稅務類別。這些都應在第 1 階段建立量測與諮詢後再校正。
